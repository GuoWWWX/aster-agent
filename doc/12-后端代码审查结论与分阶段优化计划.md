> 复核日期：2026-08-17

> 执行方式：一次只实施一个批次；自动测试通过并由用户手工确认后，才能开始下一批
> 相关规范：[后端编码规范](./13-后端编码规范.md)

## 1. 最终结论

当前后端已经形成可运行的本地 Agent 闭环，不属于需要推倒重写的项目。协议校验、IPC 错误边界、模型流式适配、SQLite 多写事务、文件搜索、命令超时与取消等局部实现是合理的，说明项目具备继续演进的基础。

初始审查发现 5 个会影响可靠性或运行事实的 P1 问题。第一批已修复设置测试漂移、IPC 注册/注销不对称和 Capability 错报；第二批已把会话与附件删除改为持久、可恢复的清理流程。当前仍有 1 个后端 P1 需要按批处理：

1. 最终 Assistant 消息、Run 终态和 Subagent 结果没有原子提交，崩溃恢复可能制造错误状态。

根级 Lint 仍被 Web 设置页和配置文件树中的 3 个 error、2 个 warning 阻断。Desktop 与 Protocol Lint 均通过，该前端问题不混入后端优化批次。

设计模式的总体判断是“方向正确、落地不完整”：Ports and Adapters、Strategy、Repository、Command/Event 已在部分边界出现，但 Tool 派发、模型协议、数据库职责和 Run 状态机仍有中央模块承担过多变化。应该按真实故障和变化轴逐步收口，不应立即建立插件平台，也不应为了匹配规划文档一次性创建所有 `packages/*`。

## 4. 最终审查发现

### 4.1 P1：后端类型检查和测试基线未通过（第一批已修复）

`ApplicationSettings.general` 已包含 `defaultPermissionMode`、`defaultMessageDeliveryMode`、`sendShortcut` 和 `showContextUsage`，但测试仍构造和断言旧结构，导致 Desktop 类型检查失败和 2 个测试失败。

代码依据：

- `apps/desktop/src/main/settings/application-settings-store.test.ts:55`
- `apps/desktop/src/main/settings/application-settings-store.test.ts:73`
- `packages/protocol/src/application-settings.ts:145`

处理结果：测试夹具改为复用 `DEFAULT_APPLICATION_SETTINGS.general`，兼容迁移断言同步覆盖全部默认字段；未修改生产设置行为。Desktop Typecheck 和 166 项测试已通过。

### 4.2 P1：IPC Handler 注销集合缺少 14 个 Channel（第一批已修复）

初审时静态统计为注册 69 个、注销 55 个。遗漏如下：

```text
applicationSettingsGetConfiguration
applicationSettingsSaveConfiguration
contextCompressionGetConfiguration
contextCompressionSaveConfiguration
conversationReorder
conversationSetArchived
conversationSetPinned
conversationSetProject
modelTestConnection
projectCreateEntry
projectRemove
projectRename
projectReorder
projectSetPinned
```

窗口关闭时会执行 disposer；macOS 再次激活创建窗口后会重新注册 Handler。手写两份清单已经发生漂移，继续补一行 `removeHandler` 只能修复本次遗漏，不能防止再次发生。

代码依据：

- `apps/desktop/src/main/ipc/register-main-ipc.ts:228`
- `apps/desktop/src/main/ipc/register-main-ipc.ts:956`
- `apps/desktop/src/main/bootstrap/index.ts:264`

处理结果：新增窄 `createIpcHandlerRegistrar()`，实际注册集合同时用于完整性断言和 disposer。启动时必须恰好注册 69 个可调用 Channel；缺失或多出 Channel 会释放本次注册并失败。手写注销清单已删除，69 个 Channel 对称性测试通过。

### 4.3 P1：会话和附件删除不可恢复

手动删除先执行 `database.deleteConversation()`，再删除附件文件；文件删除失败只记录警告。归档到期清理同样先删除数据库行，再删除附件。数据库引用消失后，系统无法可靠知道哪些文件属于本次失败，也无法进行幂等重试或审计。

代码依据：

- `apps/desktop/src/main/ipc/register-main-ipc.ts:452`
- `apps/desktop/src/main/bootstrap/index.ts:50`
- `apps/desktop/src/main/storage/agent-database.ts:995`

结论：文件系统与 SQLite 无法共享事务，不能假装一次事务解决。应使用“逻辑删除/清理任务 -> 幂等删除无引用文件 -> 最终删除数据库记录”的可恢复流程。

### 4.4 P1：Run 最终提交不原子，状态转换无保护

最终模型内容先由 `appendAssistantTurn()` 写入模型消息、Timeline 和会话时间；随后 `finishRunAndNotifySubagent()` 才更新 Run 终态并投递 Subagent 结果。如果进程在两步之间退出，恢复逻辑可能看到已存在最终回答但 Run 仍为 `running`，并将其当作异常中断。

此外，`updateRun()` 接受任意字符串状态，只检查 Run 是否存在，没有校验合法前置状态。终态 Run 理论上可再次变为 `running`。

代码依据：

- `apps/desktop/src/main/agent/agent-runtime.ts:799`
- `apps/desktop/src/main/agent/agent-runtime.ts:838`
- `apps/desktop/src/main/agent/agent-runtime.ts:1211`
- `apps/desktop/src/main/storage/agent-database.ts:2062`
- `apps/desktop/src/main/storage/agent-database.ts:2867`

结论：数据库层需要一个面向 Run 聚合的终态提交操作；数据库事实提交后再发送内存通知。状态转换必须由显式状态表校验。

### 4.5 P1：Capability 与实际能力不一致（第一批已修复）

初审时项目工具已经暴露 `run_command`、`wait_for_commands` 和 `stop_command`，但 Desktop Capability 仍声明 `process: false`。UI 如果完全按 Capability 控制入口，会隐藏可用能力；如果忽略 Capability，则该合同失去意义。

代码依据：

- `apps/desktop/src/main/ipc/register-main-ipc.ts:101`
- `apps/desktop/src/main/tools/project-tool-registry.ts:288`
- `apps/desktop/src/main/tools/project-tool-registry.ts:455`

处理结果：Desktop `process` 已改为 `true` 并增加合同测试；`pty`、`git`、`mcp`、`skills` 继续保持 `false`，没有误报未完成能力。

### 4.6 P2：核心模块按多个变化原因共同增长

当前规模：

| 文件 | 行数 | 混合职责 |
| --- | ---: | --- |
| `agent-runtime.ts` | 1889 | Agent Loop、上下文、工具派发、重试、消息队列、Subagent/Agent 通知 |
| `agent-database.ts` | 2893 | 77 个公开方法；项目、会话、Run、消息、附件、任务、Subagent、迁移 |
| `project-tool-registry.ts` | 1447 | 工具定义、参数、文件变更、Patch、命令会话、等待和项目操作锁 |
| `register-main-ipc.ts` | 955 | 所有 IPC Channel 注册与适配；注册和释放已由单一事实管理 |
| `model-protocol-adapter.ts` | 870 | 三种协议的请求构造、流解析和状态恢复 |

文件行数不是单独的整改理由。真正的问题是新增一种工具、协议或持久状态时需要修改多个中央分支，且不同职责无法独立做合同测试。

结论：按变化轴拆分，保留现有 Facade 作为迁移边界；禁止一次性大重写。

### 4.7 P2：工具派发没有统一执行合同

AgentRuntime 需要识别 TaskList、Subagent、Agent Communication、Attachment 和 Project 工具族。工具定义、名称判断、参数解析和执行分散在各模块。新增工具族时必须修改 Runtime 中央派发。

结论：引入轻量 `ToolHandler` 注册表是合理的 Registry/Strategy 应用；当前不需要动态插件加载器。

### 4.8 P2：数据库是万能 Repository，迁移没有版本事实

`AgentDatabase` 负责多个聚合和迁移。迁移通过 `PRAGMA table_info` 逐列探测并执行 `ALTER TABLE`，当前没有 `schema_migrations` 版本记录。随着字段增多，无法可靠回答某个数据库已执行到哪一版，也难以覆盖失败恢复。

代码依据：

- `apps/desktop/src/main/storage/agent-database.ts:340`
- `apps/desktop/src/main/storage/agent-database.ts:2291`
- `apps/desktop/src/main/storage/agent-database.ts:2462`

结论：先建立只向前的 Migration Runner，再按事务聚合拆 Repository；不要机械地“一张表一个 Repository”。

### 4.9 P2：模型 Strategy 只完成一部分

OpenAI Chat Completions 已有独立 Adapter；OpenAI Responses、Anthropic Messages 和 Gemini 仍集中在 `ModelProtocolAdapter` 的中央 `switch`。公共 `ModelProviderAdapter`、消息和工具类型又定义在名为 `openai-compatible-adapter.ts` 的具体实现文件，并反向依赖 Storage 类型。

代码依据：

- `apps/desktop/src/main/model/model-protocol-adapter.ts:5`
- `apps/desktop/src/main/model/model-protocol-adapter.ts:421`
- `apps/desktop/src/main/model/openai-compatible-adapter.ts:4`

结论：抽出中立模型合同，每种 API 格式一个 Strategy，由小型 Registry 选择；不要合并各厂商请求和事件语义。

### 4.10 P2：共性底座存在复制和行为漂移

| 共性能力 | 当前位置 | 已出现的差异 |
| --- | --- | --- |
| 路径包含与符号链接校验 | `project-registry.ts`、`configuration-workspace-store.ts` | 后者用 `startsWith("..")`，会把合法的 `..name` 子路径也判为越界 |
| JSON 配置读写 | 4 个 Settings Store，另有模型 Store | 重复默认值、解析、Zod、固定 `.tmp`、重命名和 clone |
| SSE 分帧 | 两个模型 Adapter | 两套 Reader、UTF-8、CRLF、多行 `data:` 和结束刷新逻辑 |
| 工具参数解析 | 4 个工具模块 | Subagent 不把空字符串视为 `{}`，与其他工具不一致 |
| 有界文件预览 | Project 与 Configuration Workspace | 重复字节上限、NUL、严格 UTF-8、二进制和截断判断 |

结论：只抽取容易发生安全或协议漂移的窄函数，保留各领域的授权规则、DTO 和协议解析。禁止建立无所有权的 `common.ts` 或 `utils.ts`。

### 4.11 P2：后端依赖边界没有自动门禁

现有 ESLint `no-restricted-imports` 只作用于 `apps/web`。文档中描述了 Desktop、Agent、Storage、Tool 和 Protocol 依赖方向，但代码没有自动约束，当前已经出现模型合同依赖 Storage 类型的反向耦合。

结论：等目标目录边界稳定后再加 Desktop 受限导入规则；过早加规则只会固化尚未完成的目录迁移。

## 5. 已有设计中应保留的部分

- `packages/protocol` 集中 Zod Schema、IPC Channel 和跨进程 DTO，方向正确。
- IPC 入口统一经过可信窗口检查和错误映射，Renderer 不直接获得 Node 权限。
- 模型请求错误、主进程错误和敏感信息脱敏已经有集中入口。
- SQLite 中若干多表写入已使用 `BEGIN IMMEDIATE` 事务。
- `@vscode/ripgrep` 已作为独立文本搜索实现，文件搜索和文本搜索没有退化成全量 JavaScript 扫描。
- 命令执行具备超时、取消、输出限制、编码处理和 Windows 进程树终止基础。
- 附件、任务清单、Subagent、Agent 消息、队列/Steer 和上下文 Checkpoint 已有明确数据对象，不应在重构中改变用户可见语义。
- 没有提前引入 Java、微服务、消息中间件或动态插件系统，这个克制是合理的。

## 8. 暂缓事项

以下能力没有证据表明必须在本轮后端治理中实现：

- 把 Agent Runtime 拆成独立进程或远程服务。
- 为每个 Agent 创建 OS 线程、Worker 或子进程。
- 动态插件市场和热加载工具。
- Java/Python 后端、消息队列或分布式事务。
- 向量数据库和跨项目自动长期记忆。
- 完整 PTY、Git、MCP、受管浏览器 Runtime。

只有出现第二个真实宿主、明确性能瓶颈、崩溃隔离要求或已验证的并发压力后，才重新评估这些设计。
