# 后端编码规范

> 适用范围：`apps/desktop/src/main`、`apps/desktop/src/preload`、`packages/protocol` 以及后续真实需要的后端 Package  
> 技术基线：Node.js 24、TypeScript 6、Electron 43、Zod 4、Vitest 4、SQLite  
> 上位规则：[前后端模块与编码规范](./06-前后端模块与编码规范.md)  
> 业务语义：[业务上下文](./14-业务上下文.md)  
> 整改计划：[后端代码审查结论与分阶段优化计划](./12-后端代码审查结论与分阶段优化计划.md)  
> 配套 Codex Skill：`$agent-backend-coding-guidelines`

## 1. 目的与优先级

本规范用于约束 Electron Main、Agent Runtime、存储、模型 Adapter 和本机工具的实现。目标不是增加抽象数量，而是保证：

- 用户可见行为不会因新增功能发生隐式回归。
- 状态、文件和外部副作用可以恢复、重试和审计。
- 新增工具或模型协议只修改所属变化点。
- Protocol、权限和数据库事实只有一个来源。
- 测试可以在不调用真实模型的情况下稳定复现关键流程。

规则冲突时按以下顺序处理：

1. 用户已经确认的业务行为和验收标准。
2. `packages/protocol` 中的跨进程 Schema 与版本合同。
3. 数据库 Migration 和已持久化数据兼容要求。
4. 本规范。
5. 局部代码风格偏好。

当前代码行为是“已实现事实”的来源，但不是错误行为永久保留的理由。发现代码、协议和业务上下文不一致时，先记录差异并通过测试确认，再选择修代码或修文档。

## 2. 开发环境与质量门禁

### 2.1 环境

| 工具 | 要求 |
| --- | --- |
| Node.js | `>=24 <25` |
| pnpm | `>=10 <11` |
| TypeScript | Strict 模式，禁止用构建转译代替类型检查 |
| Electron | Main/Preload 使用 Node 环境；Renderer 不获得 Node 权限 |

常用命令：

```powershell
pnpm install
pnpm --filter @agent/desktop lint
pnpm --filter @agent/desktop typecheck
pnpm --filter @agent/desktop test
pnpm lint
pnpm typecheck
pnpm test
pnpm build
```

### 2.2 合入门禁

- `lint`、`typecheck`、`test`、`build` 必须分别执行并通过。
- Build 通过不能替代 Typecheck；当前 tsup 可以在测试类型错误时仍构建成功。
- Bug 修复优先先写失败复现，再做最小修复。
- 无法自动化的行为必须记录可重复手工步骤、环境和实际结果。
- 测试失败不得通过放宽 Schema、增加 `any`、跳过测试或吞掉错误来修绿。

## 3. 后端边界与依赖方向

### 3.1 目标依赖

```text
Electron Bootstrap（Composition Root）
  -> IPC Adapter
      -> Application / Agent Use Case
          -> Protocol 和领域合同
          -> Storage Port
          -> Model Port
          -> Tool Port

Storage / Model / Tool Adapter
  -> Protocol 和各自窄合同
  -X-> Renderer / React
```

约束：

- `bootstrap` 只创建依赖、管理应用生命周期和后台任务，不包含业务决策。
- IPC Handler 只做来源校验、Schema 解析、调用 Use Case、响应校验和错误映射。
- Agent Runtime 负责循环和编排，不直接拼 SQL、不解析厂商私有事件、不处理 UI 展示结构。
- Storage 不依赖 Model、Tool、Electron Window 或 UI 状态。
- Model Adapter 不依赖具体 Repository 类型；公共模型 DTO 放在中立合同文件。
- Tool 不直接修改 React/Zustand 状态，也不能绕过权限和工作区解析。
- `packages/protocol` 不导入 `apps/*`，不包含 Electron、SQLite、文件系统或网络实现。

### 3.2 何时创建 Package

默认先在 `apps/desktop/src/main/<domain>` 内形成清晰边界。只有满足至少一项时才迁入 `packages/*`：

- 已有第二个真实宿主或调用方。
- 需要独立发布、独立版本或独立构建。
- 需要通过包边界阻止已发生的循环依赖。

“规划文档中画了一个 Package”不构成拆包理由。当前不得为了形式一次性创建 `agent-core`、`storage`、`local-tools` 空壳。

## 4. 文件放置与命名

| 内容 | 位置 | 命名示例 |
| --- | --- | --- |
| 应用装配、生命周期 | `main/bootstrap` | `index.ts`、`desktop-services.ts` |
| IPC 注册与适配 | `main/ipc` | `register-conversation-ipc.ts` |
| Agent 编排 | `main/agent` | `agent-runtime.ts`、`subagent-tool.ts` |
| 任务清单 | `main/tasks` | `task-list-tool.ts` |
| 模型协议 | `main/model` | `anthropic-messages-adapter.ts` |
| 项目与工作区 | `main/projects` | `project-registry.ts` |
| 文件、命令、搜索工具 | `main/tools` | `command-tool-handler.ts` |
| SQLite 与 Artifact | `main/storage` | `run-repository.ts`、`migration-runner.ts` |
| 安全原语 | `main/security` | `workspace-path.ts`、`redact-secret.ts` |
| 设置与配置 | `main/settings` | `terminal-configuration-store.ts` |
| 跨进程 Schema/DTO | `packages/protocol/src` | `conversation.ts`、`ipc-channels.ts` |

命名规则：

- 文件名使用 kebab-case；类、类型和 Schema 使用 PascalCase/camelCase 现有约定。
- `Manager`、`Service`、`Helper`、`Utils` 不能作为无法说明职责时的兜底名称。
- `Registry` 只负责注册、选择或查找，不同时承担完整业务流程。
- `Store` 用于配置或简单持久状态；复杂 SQL 聚合使用 `Repository`。
- `Adapter` 表示把外部协议转换为内部合同；不得把领域规则塞进 Adapter。
- `Controller` 只用于生命周期/协调，不作为万能类名称。
- 测试与源文件同目录，命名 `<source>.test.ts`。

文件没有强制行数上限。出现以下任一信号时必须评估拆分：

- 同一文件有两个以上互不相关的变化原因。
- 新增一种协议/工具必须修改中央 `switch` 和多个实现文件。
- 测试只能构造整个应用才能覆盖一个局部行为。
- 资源生命周期、领域状态和序列化逻辑混在同一类。

## 5. TypeScript 与 Schema

### 5.1 类型规则

- 禁止显式 `any`；边界输入使用 `unknown`，随后由 Zod 或类型守卫收窄。
- 禁止用 `as SomeType` 跳过不可信输入校验。数据库 Row 和外部响应必须先校验或显式读取字段。
- 可辨识联合类型先判断 `kind`/`type` 再访问成员字段。
- 稳定状态和协议值使用字符串联合或 Zod enum，不使用无约束 `string`。
- 时间统一保存 ISO UTC 字符串；ID 使用应用生成的 UUID。
- 不将 `Error`、`Buffer`、Stream、进程对象或数据库 Row 穿过 IPC。
- `undefined` 表示字段未提供，持久业务中的“明确没有”优先使用 `null`；同一合同内不能混用。

### 5.2 边界校验

以下边界必须校验：

- Renderer -> Preload -> Main IPC 参数。
- Main -> Renderer IPC 响应和事件。
- 模型 Provider 请求配置和返回事件。
- Tool arguments、MCP 结果和 Skill 元数据。
- JSON 配置文件和数据库迁移后的 Row。

正确：

```ts
const [input] = conversationReferenceIpcArgumentsSchema.parse(args);
const result = conversationSummarySchema.parse(useCase.execute(input));
return result;
```

错误：

```ts
const input = args[0] as ConversationReferenceInput;
return database.getConversation(input.conversationId);
```

原因：Renderer 和旧持久数据都属于不可信输入；类型断言只让编译器闭嘴，不提供运行时保证。

## 6. 设计模式使用规则

### 6.1 Ports and Adapters

适用于外部变化明显的边界：模型、SQLite、文件系统、命令、Electron IPC。Port 应表达业务需要，不应照抄第三方 SDK。

只有一个简单纯函数实现且没有外部副作用时，不建立 Port/Adapter 层。

### 6.2 Strategy 与 Registry

模型 API 格式和 Tool Handler 使用 Strategy。Registry 只根据稳定键选择实现，并在启动时拒绝重复键。

```ts
export interface ToolHandler {
  definitions(): readonly ModelToolDefinition[];
  handles(name: string): boolean;
  execute(input: ToolExecutionInput): Promise<ToolExecution>;
}
```

Runtime 的正确用法：

```ts
const handler = toolHandlers.find((candidate) => candidate.handles(call.name));
if (handler === undefined) throw new UnknownToolError(call.name);
return handler.execute(executionInput);
```

禁止 Runtime 导入每个具体工具并增加一串工具族判断。

### 6.3 Repository 与 Unit of Work

- Repository 按聚合和事务边界划分，不按每张表机械拆分。
- Run 终态、最终消息和关联事件属于同一原子事实，应由一个事务方法提交。
- 跨 Repository 事务由显式 Unit of Work 或数据库事务协调器执行。
- Repository 返回领域 DTO，不把 SQL、列名和 Row 泄漏到 Runtime。

### 6.4 State Machine

Run、ToolCall、Subagent、Task 和删除任务必须有显式状态转换。转换函数同时校验当前状态和目标状态。

```ts
const RUN_TRANSITIONS = {
  queued: ["running", "cancelled"],
  running: ["completed", "failed", "cancelled"],
  completed: [],
  failed: [],
  cancelled: [],
} as const;
```

禁止：

```ts
updateRun(runId, statusFromCaller);
```

原因：无约束字符串会允许终态回退，破坏恢复和幂等语义。

### 6.5 Command/Event

- IPC 是外部命令入口；领域状态改变后可产生事件。
- 数据库状态和作为恢复事实的持久事件必须同事务提交。
- Renderer EventEmitter 通知只能在数据库提交后发送。
- 事件消费者必须能去重；事件不得充当数据库写入成功前的唯一事实。

### 6.6 禁止为了模式而模式

- 不建立多层 Abstract Factory 只为创建一个类。
- 不用继承树表达 Agent 角色，使用 Profile 与能力组合。
- 不用全局 Service Locator 或 Event Bus 隐藏依赖。
- 不创建 `common.ts`、`utils.ts` 收容无 owner 的函数。
- 不提前实现动态插件系统；当前 Tool Registry 是静态装配。

### 6.7 工具权限与审批

- Renderer 只能提交 `approved + scope + runId + toolId`，Main 必须根据 `conversationId` 解析当前 Agent，不能接受调用方指定任意 Agent。
- `scope=once`、`session`、`agent` 分别对应当前 Tool Call、当前 conversation 的内存授权和 Agent Profile 的持久化 allow 规则。
- 命令规则只允许完全匹配或末尾 `*` 前缀匹配；不得使用 `includes`、中间通配或模糊正则放行。
- allow 规则未命中时继续审批；应用策略 `unavailable` 在工具副作用前直接拒绝。工作区外读取必须在读取正文前审批，且只允许本次授权。
- 会话授权不能写入聊天历史或 SQLite 业务事实；应用重启后自然失效。Agent 规则通过 `ApplicationSettingsStore` 原子保存，并在变更后通知 Renderer 刷新对应 Agent 配置，避免旧快照覆盖新规则。

## 7. Electron 与 IPC

### 7.1 安全边界

- Renderer 开启 `contextIsolation`，关闭 `nodeIntegration`。
- Preload 只暴露最小、版本化 API，不暴露原始 `ipcRenderer`。
- 每个 IPC Handler 先验证 Sender 来自当前可信窗口。
- Renderer 传入的项目 ID、路径、Actor 和权限结果不能直接信任。
- API Key 和受管绝对路径不得返回 Renderer。

### 7.2 注册与释放

注册和注销必须来自同一事实：

```ts
const registeredChannels = new Set<string>();

function register(channel: string, handler: IpcHandler): void {
  ipcMain.handle(channel, handler);
  registeredChannels.add(channel);
}

return () => {
  for (const channel of registeredChannels) ipcMain.removeHandler(channel);
};
```

- 禁止手写一份注册清单再手写一份注销清单。
- Handler 注册集合必须有一致性测试。
- 窗口关闭、应用退出、macOS 重新激活都要覆盖资源释放。

### 7.3 Handler 复杂度

Handler 不处理长事务和复杂流程。超过“解析 -> 调用 -> 校验 -> 返回”的逻辑应进入 Use Case。文件清理、Run 执行和模型调用不能在 IPC 中复制业务规则。

## 8. 存储、事务与 Migration

### 8.1 SQLite

- 多表状态改变使用 `BEGIN IMMEDIATE` 并保证异常回滚。
- 事务内不等待网络、模型、Shell 或不可控文件 I/O。
- 写入方法必须验证受影响行数；零行或多行应显式失败。
- 并发入口必须定义串行化位置，不依赖“通常只有一个调用”。
- SQL 参数必须绑定，禁止拼接用户输入。

### 8.2 Migration

- 使用 `schema_migrations(version, name, applied_at)` 记录只向前版本。
- 每个 Migration 文件一经进入共享基线不得修改，只能追加新版本。
- Migration 在事务中执行；失败不得记录为已完成。
- 测试覆盖空库、上一版库、重复启动、失败回滚和未来版本拒绝。
- 迁移前备份用户数据库；不得用删除用户数据库解决兼容问题。

### 8.3 文件系统与数据库

SQLite 事务不能覆盖文件系统操作。跨两者的删除/发布采用可恢复任务：

```text
事务 1：写入 deleting 状态和 cleanup job
文件阶段：幂等删除无引用文件
事务 2：删除/完成数据库事实并关闭 job
启动恢复：继续未完成 job
```

禁止先永久删除数据库引用，再把文件失败降级为一条 `console.warn`。

### 8.4 JSON 配置

- 使用组合式 `readJsonConfiguration()` 和 `writeJsonConfigurationAtomic()`。
- 临时文件名包含 PID/随机值，防止并发写互相覆盖。
- 写临时文件、必要时同步、原子 rename；失败清理临时文件。
- 读取先 JSON parse，再 Zod parse；错误附带配置类型和路径，但不含密钥。
- 返回可变对象时使用 `structuredClone`，不泄漏默认对象引用。

## 9. 文件与工作区安全

- 项目会话的工作区由 `conversationId -> projectId -> canonical root` 解析，模型不能传绝对根路径。
- 临时对话只有用户显式选择目录后才获得工作区。
- 工具参数路径统一为相对 POSIX 路径；Runtime 转换为平台路径。
- 对已存在目标使用 `realpath`；新建目标校验最近已存在父目录的真实路径。
- 路径包含判断使用 `path.relative`，只拒绝精确 `..`、`..${sep}` 前缀和绝对结果；不能误拒绝 `..name`。
- 目录和文件符号链接都必须测试，Windows 大小写和盘符边界必须测试。
- Project 与 Configuration Workspace 只共享路径安全原语，不共享授权策略。

有界文件预览统一返回：

```ts
type BoundedFilePreview = {
  byteLength: number;
  content: string | null;
  isBinary: boolean;
  truncated: boolean;
};
```

NUL 或严格 UTF-8 解码失败视为二进制。调用方负责补充 Project/Configuration DTO。

## 10. 工具实现规范

### 10.1 工具合同

每个工具必须声明：名称、描述、输入 Schema、权限种类、是否可取消、超时、结果限制。名称全局唯一，发布后视为模型协议的一部分。

- 参数先统一解析 JSON，再由工具专属 Zod Schema 校验。
- 空参数 `""` 与 `"{}"` 对无参数工具语义一致。
- 成功和失败均返回可序列化结构；错误不能只放在 stdout 文本中。
- 大输出截断并写 Artifact；模型只接收摘要和引用。
- Tool Result 包含状态、耗时、退出码/变更摘要、是否截断和稳定错误。

### 10.2 权限

- `read`、`write`、`execute`、`network` 分开判断。
- 权限由本地确定性代码决定，模型不能声明“用户已同意”。
- Tool Handler 获得的是 Runtime 已解析的工作区和审批结果，不接受模型指定的任意根目录。
- 文件写入和命令执行必须与当前权限模式一致。

### 10.3 并发与生命周期

- 读目录、读文件、文本搜索和文件查找可并发。
- 同项目文件写、Patch 和可能修改工作区的命令必须进入冲突协调。
- 同一物理工作区可能对应不同 conversation/project ID；协调键必须使用规范化真实根路径，不能只比较业务 ID。
- 文件变更采用乐观并发检查：冲突时立即作废当前已准备的参数，不排队、不自动重放；写入前比较 `expectedContent`，模型必须重新读取最新文件后生成新的变更。
- 长命令返回 operation/session ID；等待和停止是独立生命周期操作。
- 取消要终止完整进程树并等待退出，不能只停止 stdout 读取。
- 同一模型轮可以混合发起多个互不冲突的工具，但必须设置总量上限；当前最多 32 个，超限时整批拒绝且不能执行前缀副作用。结果按 tool call ID 关联，不依赖完成顺序。
- Tool Handler 必须声明调度策略：只读可并发、非只读模式下独立命令可并发（询问模式逐条审批后执行）、状态/文件副作用默认有序；Runtime 不得对全部 Tool Call 直接使用 `Promise.all`。并发组必须有显式宽度上限，当前只读为 8、命令为 4，超出部分按原顺序进入下一 LangGraph `ToolNode` 窗口。审批中断重放时必须复用运行中 ToolCall 的 Promise 或已完成结果，不能重复启动副作用。
- 同一批文件变更在首个应用前准备全部 Diff 和 `expectedContent`；后续同文件调用若基线过期必须返回 `FILE_CHANGED`，不能静默重新读取并重建参数。多文件应用不承诺原子事务。
- 任何后台 operation 必须有终态和资源清理，应用退出不得遗留子进程。

### 10.4 搜索

- 文本搜索优先使用随应用分发的 `@vscode/ripgrep`，不假设用户 PATH 已安装 `rg`。
- `search_text` 用于内容搜索；`find_files` 用于文件名/路径匹配；模型仍可在确有必要时调用 `run_command` 执行 `rg`。
- 搜索结果必须受条数和字节上限约束，并保留相对路径和行号。

## 11. 模型 Adapter

- 每种 `apiFormat` 一个 Adapter Strategy。
- 公共合同不以某个厂商命名，也不依赖 Storage 实现。
- 厂商请求体、工具格式、图片块、Reasoning 参数和 Provider State 留在各自 Adapter。
- Reasoning 内容块与 Assistant 正文分流；Provider State 必须按模型快照匹配，并为紧邻迁移前的持久格式保留有测试的只读转换，不能依赖 SDK 自动重放非标准字段。
- HTTP、SSE 分帧、错误映射和附件说明可复用窄函数。
- SSE 分帧必须处理 UTF-8 跨块、CRLF、多行 `data:`、无空行兼容和结束尾块。
- Adapter 只负责协议转换，不决定 Agent 是否重试、是否调用工具或是否压缩上下文。
- 模型重试循环由 LangGraph `wrapModelCall` Middleware 执行，Runtime 只提供稳定错误判定、退避等待、流式保护和事件/终态回调；有副作用工具不能因模型重连自动重放。
- 新增协议必须提供请求快照、流式文本、Reasoning 分流、工具调用、附件、Provider State 当前/迁移格式、错误和取消合同测试。

## 12. Agent、消息与上下文

- 每个 Agent 对应独立逻辑对话，不对应独占 OS 线程或进程。
- 生产 Agent Loop 必须使用 LangChain `createAgent`/LangGraph，不得在 `AgentRuntime` 内并行维护手写 `for`/`while` 工具循环；必须有最大模型调用次数、取消信号和终态保证。
- Queue 消息按顺序消费；Steer 消息只在当前工具/模型边界安全注入，不中断已开始的副作用。
- Agent 间消息必须保存 sender/target conversation ID；接收方能回到来源。
- Subagent 完成向父对话投递结构化摘要和子对话引用，不复制整个子对话。
- UI 历史与模型上下文分离；压缩不删除原始消息。
- 上下文构建按 Token 预算，优先保留当前请求、用户约束、未完成任务、最近完整轮次和相关附件。
- Checkpoint 覆盖范围只能前进；写入新摘要失败不能破坏旧摘要或原始历史。
- `createAgent` 负责标准模型/工具循环、ToolNode 路由和 Checkpoint；`AgentRuntime` 仍是应用 façade，不能把权限、工作区解析、业务 SQLite 事务或 Renderer 事件塞进图节点。最大模型调用次数优先使用框架 `modelCallLimitMiddleware`，Runtime 只提供上限和稳定错误映射。
- LangChain `ToolNode`/`StructuredTool` 只负责工具名分发和消息转换；每个工具必须经过现有 Registry 的参数、权限、审计、取消、项目锁和副作用边界。审批必须使用 LangGraph `interrupt/Command`，恢复时按 interrupt 标识绑定决定，并保证已完成 ToolCall 不重复执行。
- `toolCallId` 在同一模型上下文中必须唯一。Runtime 必须在启动本轮新工具前拒绝同轮重复或跨轮复用，避免 ToolNode 把新调用匹配到旧 ToolMessage；未知工具应返回失败 ToolMessage 供模型修正，不得绕过审计直接抛成无工具事实的 Run 失败。
- Graph `thread_id` 必须使用应用生成的 Run ID。Run 结束后清理 thread；会话删除通过可重试清理端口删除关联 threads。应用重启只自动恢复尚未进入模型/工具节点的 queued Run，running Run 不得因 Checkpoint 存在而自动重放副作用。
- Skill 正文作为临时 system context 注入，不写入聊天 Timeline；Graph State 只保存 `id/version/contentHash`。ContextManager 必须在历史裁剪前预留与注入相同的 Skill Token 预算；reference 读取必须受 Skill 目录、相对路径、符号链接和字节/字符上限约束。

详细业务语义以[业务上下文](./14-业务上下文.md)为准。

## 13. 错误、日志与敏感信息

### 13.1 错误

- 使用稳定错误 `code`、用户消息、`retryable` 和错误实例 ID。
- 不通过匹配英文错误字符串决定业务分支。
- 内部 cause/stack 进入主进程日志，Renderer 只接收可序列化、安全信息。
- 错误显示归属原操作：命令错误在命令结果，文件错误在文件工具，Run 级错误在 Assistant 输出区域。
- 捕获错误后如果无法真正处理，必须重新抛出或转换；禁止静默吞掉。
- LangGraph `ToolNode` 内部的工具适配器异常必须转换为有界失败 `ToolMessage` 并持久化工具失败事实；取消和审批 `interrupt` 不得被转换或吞掉，已完成的副作用调用不得自动重放。

### 13.2 日志

- 结构化日志按可用范围包含 `conversationId`、`runId`、`toolCallId`、`taskId`、`operationId`。
- 记录状态转换和边界结果，不记录完整模型上下文、文件正文、图片 Base64 或完整终端输出。
- `authorization`、`apiKey`、`token`、cookie、`sk-` 形式密钥统一脱敏。
- `console.warn/error` 不是恢复机制；需要重试的事实必须持久化。

## 14. 注释规范

注释解释“为什么”和不变量，不复述代码。

应该注释：

- Windows 进程树、符号链接、Electron 生命周期等平台行为。
- 状态转换为什么拒绝某条路径。
- Provider 的非标准 SSE 兼容原因。
- Migration 的历史兼容约束。
- 乍看可简化但会破坏恢复/幂等的流程。

不应该注释：

```ts
// 将状态设为完成
status = "completed";
```

公共 Port、复杂 Use Case 和安全函数使用简短 JSDoc，说明输入信任级别、副作用和失败条件。`TODO` 必须有原因和跟踪标识。

## 15. 测试规范

| 范围 | 最低测试 |
| --- | --- |
| Protocol | Schema 正反例、默认值、旧数据兼容 |
| IPC | Sender 校验、参数/响应 Schema、注册注销对称 |
| Repository | 正常事务、失败回滚、并发冲突、重启恢复 |
| Migration | 空库、旧库、重复执行、失败、未来版本 |
| 文件 | 越界、符号链接、编码、二进制、原子写、外部修改冲突 |
| 命令 | 成功、非零退出、超时、取消、长输出、编码、进程树 |
| Tool Handler | 定义唯一、参数、权限、结果、未知工具 |
| Model Adapter | 请求、流式、工具、附件、错误、取消、Provider State |
| Agent Runtime | 多轮、工具上限、Queue/Steer、取消、Subagent、消息唤醒 |
| LangGraph/Checkpoint | 图循环、状态 reducer、父链、重启读取、thread 清理、queued Run 恢复 |
| 上下文 | Token 预算、最近轮次、摘要边界、附件、超限拒绝 |
| Skill Runtime | Agent/项目/团队作用域、目录摘要、正文渐进注入、哈希变化拒绝、references/templates 越界、严格 UTF-8 和上限 |

测试要求：

- 默认使用 Fake/Mock Model，真实 API 只用于明确授权的集成验收。
- 时间、UUID、网络和故障点应可注入，避免 `sleep` 和随机等待。
- 并发测试必须设置超时并验证资源终态，不能只断言返回值。
- Characterization Test 在重构前固定现有行为；重构后不得减少关键断言。
- 测试夹具使用 Protocol 默认值构造，新增字段时只在一处更新 Builder。

## 16. 依赖管理

- 优先使用 Node 标准库和现有依赖。
- 新依赖要记录用途、维护状态、许可证、包体/原生 ABI 影响和替代方案。
- 原生依赖必须验证 Electron ABI、Windows 安装包和升级路径。
- 不因一个小函数引入大型框架。
- 删除依赖前检查动态 import、构建脚本和打包资源。
- 依赖升级单独提交，不与业务重构混在同一批。

## 17. 提交与代码审查

提交标题：

```text
<type>: <中文说明>
```

一个提交只表达一个可验证意图。Migration、行为修复、结构重构、依赖升级和格式化分开提交。

代码审查清单：

- [ ] 改动能追溯到当前需求或必要配套。
- [ ] 没有顺手修改无关命名、格式或模块。
- [ ] 新增状态有合法转换、终态和恢复策略。
- [ ] 数据库与文件副作用失败后可重试或回滚。
- [ ] IPC、模型、工具和持久数据均完成边界校验。
- [ ] 权限和工作区由 Runtime 决定，模型没有扩大权限。
- [ ] 没有新增中央 `switch`、万能 Service 或无 owner Utils。
- [ ] 新抽象解决了已发生的重复/变化，不是为未来猜测。
- [ ] 定向测试和根级门禁都已执行并记录结果。
- [ ] Migration、Protocol、业务上下文和用户可见行为已同步。
- [ ] API Key、附件路径和敏感正文没有进入日志或 IPC。
- [ ] 取消、超时、并发和资源释放有验证证据。
