# AI 工具体系与生命周期设计

> 更新时间：2026-08-27
> 状态：内置工具、LangChain `createAgent`/LangGraph ToolNode、批量 Tool Call 调度、interrupt 审批恢复和 Skill 渐进加载已接入；MCP Runtime 仍未实现

## 1. 设计目标

工具层负责把模型意图转换为可授权、可观察、可取消和可审计的本机操作。它不是对 Shell 的替代，也不应为了“结构化”把成熟命令行能力拆成大量薄包装。

采用以下边界：

- 常用、结果需要有界、需要专用 UI 的操作使用结构化工具。
- 复杂搜索、Git、构建、测试和项目自带 CLI 继续使用 `run_command`。
- 文件写入必须生成 Diff，并经过当前对话权限策略。
- 长时间操作返回稳定 ID，等待超时只结束本次等待，不中止后台工作。
- 不同领域保留明确的等待工具，不合并成语义模糊的万能 `wait`。

## 2. 当前内置工具清单

Agent Runtime 的基础工具注册表包含现有项目、Agent、Subagent、任务和附件工具；启用 Skill Runtime 时另外注册 `load_skill` 与 `read_skill_reference`。Skill 工具不执行脚本，不改变项目权限。

| 类别 | 工具 | 结论 |
| --- | --- | --- |
| 即时只读 | `list_directory`、`read_file`、`search_text`、`find_files`、`read_attachment` | 保留。分别覆盖目录、文件片段、文本搜索、文件搜索和对话附件全文分段读取；除附件外需要当前工作区 |
| 受控外部读取 | `read_external_file` | 保留。只接受绝对 UTF-8 文本文件路径；审批前不读取正文，即使 `full_access` 也必须逐次审批，临时对话可用 |
| 公共网络只读 | `web_search` | 已实现。项目和临时对话均可调用；使用免费 DuckDuckGo Provider，返回有界来源摘要和 URL，不执行网页点击或页面交互 |
| 文件变更 | `write_file`、`delete_file`、`replace_in_file`、`apply_patch` | 保留。创建/全量替换、删除、精确替换和单文件多位置补丁语义不同 |
| 命令任务 | `run_command`、`wait_for_commands`、`stop_command` | 保留。短命令同步返回，长命令转后台任务，可批量等待或停止 |
| 项目冲突协调 | `list_project_operations`、`wait_for_project_operation` | 保留，但只应在冲突后使用，不要求模型每次先查询 |
| Agent 通信 | `list_agent_conversations`、`read_agent_conversation`、`send_agent_message`、`wait_for_agent_message` | 保留。查找目标、按预算读取、持久发送和有界等待职责不同 |
| Subagent | `spawn_subagent`、`list_subagents`、`wait_for_subagents` | 保留。一次性创建、状态查询和依赖等待形成完整生命周期；创建参数把 `name`、受控 `icon` 与任务正文分开 |
| Team WorkItem | `submit_team_work_item` | 仅在未归档的项目主 Conversation 中注册。模型必须在用户显式 `@团队` 或明确交办后调用；工具使用运行时团队目录的 `teamId`、冻结当前模型/推理并保存初始权限，创建可自动调度的持久 WorkItem，不能由 Team Lead 或其成员递归交办；用户可在受管成员 Tab 修改 WorkItem 的后续 Run 模型、思考和权限，当前 Run 快照不变 |
| 任务清单 | `create_task_list`、`update_task_list`、`close_task_list` | 保留。只管理当前对话的任务元数据，不授予文件或命令权限 |
| Skill 上下文 | `load_skill`、`read_skill_reference` | 可选注册。先加载 `SKILL.md` 并保存版本/哈希快照，再按相对路径读取 `references/` 或 `templates/` 下的有界文本；正文进入模型上下文，不写入聊天 Timeline |

历史 UI 中仍兼容 `get_project_info` 的旧记录，但后端不再向模型注册该工具。项目名称和根目录已经动态写入系统上下文，模型无需主动查询当前目录。

## 2.1 多 Tool Call 调度矩阵

模型一轮可以混合返回多个独立 `toolCalls`，但最多 32 个。超过上限时 Runtime 将本轮模型响应归类为 `MODEL_RESPONSE_INVALID`，整批工具均不启动，不能截断后执行前 32 个。这个批量请求不代表所有调用都可以同时执行：Runtime 先由每个 Tool Handler 声明调度策略，再把连续的同类安全调用按有界窗口交给 LangGraph `ToolNode`；结果始终按原始 `toolCallId` 回填，不能按完成先后拼接。

每条 Timeline 工具记录会保留 Runtime 的 `executionMode`（`parallel` 或 `serial`），用于前端显示实际调度结果；它不是模型参数，也不代表同批所有工具都能并行。

`toolCallId` 必须在本轮内唯一，也不能复用当前模型上下文中已经出现过的 ID。`createAgent`/ToolNode 用该 ID 关联完成结果；重复 ID 会让新调用被误判为旧调用。Runtime 在任何新工具启动前拒绝同轮重复；跨轮复用则拒绝该轮新响应，保留此前已经完成的工具事实，并统一映射为 `MODEL_RESPONSE_INVALID`。未知工具不终止整个 Run，而是持久化失败工具行并返回对应失败 `ToolMessage`，让模型下一轮修正工具名。

| 调度组 | 当前工具 | 执行规则 |
| --- | --- | --- |
| 并行只读 | `list_directory`、`read_file`、`search_text`、`find_files`、`read_attachment`、`web_search`、`list_project_operations`、`list_agent_conversations`、`read_agent_conversation`、`list_subagents`、已激活 Skill 的 `read_skill_reference` | 同一连续组按最多 8 个调用一个窗口交给 `ToolNode` 并行执行；超出部分进入下一窗口，结果独立关联，取消传播到每个调用 |
| 并行命令 | `run_command` | 非 `read_only` 模式下同一连续组的独立命令默认并行，每个窗口最多 4 个进程；依赖前序结果或共享可变状态时传 `parallel=false`；`ask_before_changes` 逐个审批，但已批准的独立命令可以重叠执行 |
| 有序副作用 | `write_file`、`delete_file`、`replace_in_file`、`apply_patch`、`send_agent_message`、`wait_for_agent_message`、`spawn_subagent`、`wait_for_subagents`、`submit_team_work_item`、任务清单、`load_skill`、各类停止/等待工具 | 按模型返回顺序执行；审批中断、消息投递、状态消费、团队入箱和 Skill 激活不能并发重排 |

文件变更批次在首个写入或审批前先读取并保存每个调用的 `expectedContent`。同一批对同一文件的后续调用不会以第一个写入后的内容重新生成基线，而是在应用时返回 `FILE_CHANGED` 并作废；模型必须重新 `read_file` 后生成新变更。多个不同文件可以逐个审批和写入，但当前不是多文件原子事务，部分成功后不会自动回滚。

## 3. 搜索与 ripgrep

`search_text` 和 `find_files` 底层均使用应用随包提供的 ripgrep，并遵守项目忽略文件和固定的重目录排除规则。

`search_text` 适合：

- 需要路径、行号和有界摘录的常规搜索；
- 字面量或正则搜索；
- smart/sensitive/insensitive 大小写策略；
- 少量 include/exclude glob。

`run_command` 直接执行 `rg` 适合：

- `-A/-B/-C` 上下文行；
- `-c/-l/--stats` 计数、文件名或统计输出；
- 多个 `-e` 表达式、复杂 glob 和类型过滤；
- 与排序、去重或其他命令形成管道；
- 用户需要查看完整原生命令与终端输出。

桌面命令环境会把内置 ripgrep 目录加入 `PATH`，因此不依赖用户另外安装 `rg`。两种搜索入口是互补关系，不互相禁止。

### 3.1 公共网页搜索

`web_search` 适用于需要当前公共网页信息、但不需要登录态或页面交互的查询。它请求 DuckDuckGo Lite，并使用 `parse5` 解析结构化 HTML，不要求 API Key 或付费搜索服务；输入支持 `query`、`maxResults`、`region` 和 `safeSearch`，请求有 20 秒超时，响应大小、结果数量、标题、摘要和 URL 均有上限。搜索失败、网络不可用或被限流时，工具返回统一错误信封，模型可以调整查询后重试，但 Runtime 不自动重放已经完成的网络请求。

该工具不读取项目文件、不要求临时对话附加工作区，也不承担浏览器导航、点击、登录、下载或页面脚本执行；这些能力仍属于后续受管浏览器工具范围。

### 3.2 临时对话的工作区边界

临时对话的定义是“没有关联项目/工作区”，而不是“不能使用工具”。没有工作区时：

- `run_command`、`wait_for_commands` 和 `stop_command` 仍可用，命令在该对话独立的系统临时目录中执行，不能访问其他临时对话的命令会话；
- `web_search`、Agent/Subagent、任务清单和已配置的附件工具仍按各自合同可用；
- `list_directory`、`read_file`、`search_text`、`find_files`、文件变更和项目冲突工具需要先附加工作区；
- `read_external_file` 不需要工作区，但读取工作区外文件前必须逐次审批；
- 命令仍受当前权限模式约束：只读模式拒绝副作用命令，询问模式逐次审批，完全访问模式只在隔离临时目录内直接执行。

附加或替换目录后，Runtime 才把文件工具和项目操作协调绑定到该目录；移除目录后，后续临时命令继续使用隔离临时目录，不回退到任意用户目录。

## 4. 生命周期合同

### 4.0 Tool Call 审计顺序

每个模型 Tool Call 以 `runId + toolCallId` 作为重放幂等键。运行时先追加 `tool_call_requested`，Handler 产生可执行提案后追加一次 `tool_execution_prepared`；需要授权时，副作用发生前依次追加 `tool_approval_requested` 和用户的 `tool_approval_decided`，完成或失败后再追加 `tool_result`。若 Run 在决定前停止、失败或重启中断，则追加 `tool_approval_expired` 并把 Tool 行终态化为 `cancelled`；该卡片不再接收审批。LangGraph 因审批恢复而重放 ToolNode 时，已完成结果会直接返回，已记录的执行意图也不会重复追加或重新执行副作用。〔FACT｜`apps/desktop/src/main/agent/agent-runtime.ts`；`apps/desktop/src/main/storage/thread-log.ts`〕

这些事件目前写入 ThreadLog 的影子审计链，并被 `EventProjector` 幂等索引；SQLite 的 Timeline/Tool 行仍是现有 UI 业务写入链。因而日志写入失败会被记录为 Main 诊断，不能据此假设 SQLite 业务事实已经可以完全由事件重建。〔FACT｜`apps/desktop/src/main/agent/agent-runtime.ts`；`apps/desktop/src/main/storage/event-projector.ts`〕

### 4.1 即时只读

```text
调用 -> 校验项目边界和参数 -> 执行 -> { ok, value }
```

结果必须有数量、行数、字节数或字符数上限。取消信号应终止仍在运行的 ripgrep 或读取操作。

### 4.2 文件变更

```text
读取当前内容 -> 准备变更和 Diff -> 等待权限审批 ->
检查文件未被外部修改 -> 临时文件写入并原子替换 -> 完成事件
```

拒绝、文件已变化、路径越界和项目操作冲突均作为当前工具失败显示。`apply_patch` 当前支持一个既有文件中的多个修改位置；新建和删除分别使用 `write_file`、`delete_file`。

### 4.3 命令任务

```text
准备命令 -> 等待权限审批 -> 启动进程 ->
在 yieldTimeMs 内结束则直接返回
否则返回 commandId -> wait_for_commands / stop_command
```

`wait_for_commands.waitFor` 支持 `any` 和 `all`。等待超时不停止命令；命令自身超时才会终止进程树。多个独立命令使用同一轮工具调用和较短 `yieldTimeMs` 启动；非 `read_only` 模式下默认并行，询问模式先逐条审批，审批通过后仍进入同一并行窗口；依赖命令显式传 `parallel=false`，再统一等待。

### 4.4 项目冲突

```text
文件变更发现冲突 -> 当前变更请求立即作废，返回 operationId 和占用对话 ->
必要时等待占用操作结束 -> 重新读取文件并生成新的变更
命令发现冲突 -> 当前命令请求立即作废 -> 必要时等待 -> 重新评估项目状态并生成新命令
```

协调器以规范化后的真实工作区根路径识别同一项目，不依赖 conversation/project ID；结构化文件变更再按规范化文件路径互斥，命令默认与项目写操作互斥。同一 Run 中独立命令默认进入并行窗口，`parallel=false` 才降级为串行；不同对话仍不能无感知地同时修改项目。冲突不会排队或重放已基于旧状态生成的参数；写入前还会比较 `expectedContent`，发现文件已变化时返回 `FILE_CHANGED`，要求 `read_file` 后重新生成 Diff。等待工具只用于观察占用操作状态，不能恢复被丢弃的旧请求。

### 4.5 Agent 与 Subagent

Agent 消息和 Subagent 都持久化到独立对话。跨对话读取受 token 预算约束。Subagent 是一次性任务，完成后对话只读；简要结果自动回传，完整历史由主 Agent 按需调用 `read_agent_conversation`。Team Lead 与团队成员不使用 Subagent：同一来源主对话与 Team 复用持久 Team Lead/成员 Conversation，Lead 只通过 `send_agent_message` 和 `wait_for_agent_message` 分派、等待和汇总；成员最终结果自动以 Agent 消息回传。团队成员消息只能投递给同一持久 Team 的参与者，且每条任务分派绑定 WorkItem 记录以供审计。

`spawn_subagent.icon` 由协议枚举和执行端 Zod Schema 共同约束，Renderer 只映射本地 Lucide SVG 组件，不接收模型提供的任意 SVG、图片 URL 或组件名。未提供图标时 Runtime 使用所选 Agent 的预设图标或稳定回退，并把最终图标随子 Conversation 持久化。`name` 只负责身份展示，`task` 继续作为实际模型输入。

等待超时只表示当前 Agent 暂不继续阻塞。Subagent 或目标对话完成后仍可通过运行时事件唤醒来源对话。

### 4.6 任务清单

```text
create -> update（最多一个 running）-> close
```

任务清单只适用于确实需要多步推进的任务。简单任务不应为了调用工具而创建清单。完成后模型可以主动关闭，用户也可以手动关闭。`blocked` 和 `failed` 步骤必须通过 `reason` 提供一条简短原因；其他状态不携带该字段，详细诊断仍归属 Assistant 或工具 Timeline。

### 4.7 Skill 上下文

```text
系统上下文注入 Skill 目录摘要
  -> 模型调用 load_skill(skillId)
  -> Runtime 校验作用域、启用状态、MCP 依赖并读取 SKILL.md
  -> Graph State 保存 id/version/contentHash
  -> 下一轮模型请求临时注入正文
  -> 按需调用 read_skill_reference(skillId, relativePath)
```

Skill 正文是本轮模型输入，不是聊天历史。每个 Skill 必须位于与 Frontmatter `name` 同名的父目录中；Runtime 首次登记时由该名称生成稳定 `skillId`，全局重名使用数字后缀区分，模型只能从当前目录摘要选择 ID，不能猜测文件路径。ContextManager 在历史裁剪前固定预留正文预算，正文实际注入和用量展示使用同一预算；无模型窗口时按 48,000 Token 计算。工具结果只返回加载摘要和哈希；`read_skill_reference` 只允许已激活 Skill 的 `references/`、`templates/` 相对 UTF-8 文本文件，读取前检查字节上限，并拒绝绝对路径、遍历、符号链接、NUL、非法 UTF-8 和超大内容。`custom` Agent 的 `skillIds` 必须统一约束目录、加载、reference 与恢复注入，不能只隐藏目录；`inherit_all` 才继承全部满足作用域的 Skill。`project`/`team` Skill 分别要求项目工作区/团队会话。Skill 内容不能覆盖系统安全规则、项目授权范围或审批策略。Run 结束后 Graph thread 会清理；会话删除任务也会清理对应 threads。

### 4.6 权限授权范围

审批卡提供“本次允许”“本会话允许”“Agent 一直允许”和“拒绝”。前两者由 Runtime 按 conversation 管理；Agent 规则持久化在应用配置的 Agent Profile 中。命令规则使用完整命令精确匹配，或仅允许末尾 `*` 的前缀匹配，例如 `mvn package *`；不做中间通配和模糊包含匹配。没有匹配规则的命令、文件变更继续请求审批。工作区外读取只允许本次授权，不保存长期规则。

Subagent 只继承创建时的权限模式，父对话的 `once`/`session` 规则不会跨 conversation 复制；同一 Agent 的持久 allow 规则可以共享。审批事实始终属于子 Tool/Run，子页面保留完整卡片，父页面只从活动子 Run 的 `awaiting_approval` Tool 派生一个输入框上方的操作入口。两个入口提交同一 `runId + toolId`，先处理后再次提交返回 `APPROVAL_EXPIRED`。

## 5. 统一结果与展示

### 5.1 模型可见工具合同

模型请求只发送工具名、用途描述和输入 JSON Schema。输入 Schema 由执行端的 Zod Schema 使用 `io=input` 自动生成，并移除 provider 无需的 `$schema` 元字段；因此默认值、必填字段、枚举、UUID、长度上限和对象的 `additionalProperties` 与实际执行校验保持同一来源。无法用 JSON Schema 表达的跨字段规则、规范化和安全校验（例如 `read_file` 的 `startLine/endLine` 范围、任务清单最多一个 `running` 步骤、字符串 `trim` 和工作区路径边界）继续由执行端 Zod 或领域校验，并在工具描述或错误结果中说明；能定位到具体字段的规则应通过字段级 issue 返回。Provider 返回的参数先由统一解析器处理；非法 JSON 或非对象参数使用稳定的 `TOOL_ARGUMENTS_INVALID` 错误码和字段问题，不依赖错误文案分类。

工具校验失败时，除现有 `agentError`、`error` 和 `ok=false` 外，模型可获得有界的：

```json
{
  "recovery": {
    "action": "fix_arguments",
    "instruction": "根据 issues 修正本次工具参数后重试；不要重复提交相同参数。",
    "issues": [
      { "code": "invalid_format", "path": ["commandId"], "message": "Invalid UUID" }
    ],
    "retryable": true
  }
}
```

`issues` 最多保留 8 项，字段路径、校验代码和消息均有长度上限。`recovery.retryable=true` 只表示模型可以根据问题修正参数后发起一个新请求；它不等于运行时自动重放，文件、命令和审批等有副作用操作仍必须遵守其原有权限和生命周期。文件版本过期或文件变更发生项目操作冲突时使用 `recovery.action=reread_and_rebuild_change`，明确要求丢弃旧参数、重新读取当前文件并生成新的变更；命令冲突只返回等待和重新评估指引，不伪装成文件恢复。

内置工具成功结果统一使用：

```json
{ "ok": true, "value": {} }
```

参数校验和非预期执行异常使用统一 AgentError 信封；审批拒绝、命令非零退出和项目操作冲突等预期生命周期结果使用 `{ ok: false }`，并在 `value` 中保留退出码、标准输出、标准错误、超时、截断或占用者信息。经过 LangGraph `ToolNode` 的工具适配器如果抛出非取消、非审批 `interrupt` 异常，Runtime 必须转换为有界的失败 `ToolMessage`，将工具行持久化为 `status=failed` 并发送一次 `tool.completed`；不得把诊断异常吞掉，也不得自动重放该副作用调用。取消和审批中断必须传播给图执行器；如果上游编译图把顶层 `GraphInterrupt` 作为异常抛出，执行边界必须把它归一为同一审批暂停/恢复流程，不能将 Run 标记为内部错误。Subagent 已改为相同成功信封，避免专用 UI 无法解析。

UI 展示规则：

- 命令展示 Shell、完整命令、stdout/stderr、退出状态和 `commandId`。
- 文件变更展示红色删除、绿色新增的 Diff；错误留在同一变更卡内。
- 目录、搜索、附件和跨对话读取使用有界结构化结果。
- 项目占用展示操作内容、占用对话和状态。
- 多工具调用按批次折叠，用户按需展开，不默认铺开所有原始 JSON。

## 6. 当前缺口与扩展顺序

### 6.1 下一阶段必须补齐

1. MCP Runtime：当前已有配置、编辑和存储，但桌面能力标记仍为 `mcp: false`，还没有动态发现和执行 MCP 工具。
2. Skill Runtime：已接入 `AgentRuntime + LangGraph`。目录摘要、`load_skill`、正文哈希快照、统一预算的正文临时注入和受控 reference 读取已有自动测试；运行中的 Skill 文件发生变化会拒绝静默恢复。仍未实现 Skill 脚本执行、真正的 MCP Runtime 依赖和 running Run 的自动重放。
3. 多文件补丁事务：一次审批多个文件时，需要批量 Diff、逐文件并发冲突检查、失败回滚和多文件刷新事件，不能直接复用单文件 `PreparedFileChange`。

### 6.2 按需求再增加

- 浏览器自动化工具：导航、DOM 快照、点击、输入、截图和下载。
- 交互式 PTY：仅在必须运行交互程序时增加；普通构建和测试继续使用后台命令任务。
- Git 专用结果：只有需要结构化状态、提交图或可点击 hunk 时再增加；目前 `run_command` 足以运行 `git status/diff/log`。
- 二进制文件写入、移动和复制：明确产品场景后设计审批和预览，当前不通过文本工具伪装支持。

### 6.3 当前不引入

- 不增加 `get_current_directory` 或 `get_project_info`。项目对话已经绑定动态工作目录。
- 不增加 `run_rg`、`run_git`、`run_test` 等 Shell 薄包装。
- 不增加万能 `wait`。命令、Agent 消息、Subagent 和项目冲突的完成条件及返回值不同。
- 不引入向量检索工具替代代码搜索。文件名、文本和符号定位优先使用 ripgrep；达到明确语义检索需求后再评估索引。

### 6.4 外部开源实现的复用边界

- 不直接搬运 PI Agent / Codex 的完整工具运行时：它们分别绑定自己的 TypeScript Harness 与 Rust CLI / Sandbox 生命周期，直接复用会绕开本项目既有的审批、项目锁、Timeline 和 IPC 合同。
- 优先复用已经处于稳定边界的底层库，并保留本项目的适配层：例如 `@vscode/ripgrep` 用于受限搜索、`diff` 用于变更展示、`file-type` / `mammoth` / `unpdf` 用于文件识别与提取。库升级或替换只影响对应 Handler，不改变 `ToolRuntime` 的统一权限和结果合同。
- 新引入第三方工具前先补“Schema、权限、幂等、结果上限、取消、错误信封、测试矩阵”；没有通过该矩阵，不因为开源项目热门而接入生产主链。

## 7. 测试门禁

每次调整工具至少验证：

1. 参数 Schema 与模型看到的 JSON Schema 一致。
2. 项目路径不能越界，忽略规则和结果上限生效。
3. 成功和失败信封能被 Agent Runtime 与 UI 同时解析。
4. 审批拒绝、文件外部变化、命令非零退出和超时显示在原工具卡中。
5. 后台命令可以等待、停止；并行命令不会串输出或复用错误 ID。
6. 两个对话操作同一项目时能返回占用者，并在等待后重试。
7. Subagent 和 Agent 消息等待超时不会取消后台任务或丢失后续唤醒。
8. Skill 的正文不进入 Timeline；reference 只能读取允许目录的有界文本，文件变化和越界路径返回可恢复错误。
