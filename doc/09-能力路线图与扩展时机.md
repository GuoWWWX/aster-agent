# 能力路线图与扩展时机

> 文档状态：产品路线与架构决策基线  
> 更新时间：2026-08-15  
> 目标：在不扩大首个代码批次的前提下，明确主流能力、优先级和扩展触发条件

## 1. 结论

当前规划已经覆盖本地编码 Agent 的核心闭环，不应该继续把所有主流功能塞进 MVP。接下来采用三类处理方式：

1. **现在实现**：没有它就无法形成可靠闭环，或后补会破坏数据与权限模型。
2. **现在留边界，触发后实现**：先稳定 Port、事件或能力声明，出现真实需求再增加实现。
3. **暂不建设**：需要云服务、第三方生态或大量运维投入，当前没有证据支持。

“具备扩展性”不等于所有模块都做成插件。项目只在外部协议、运行策略、状态生命周期和资源创建处使用模式；页面内部和单次业务逻辑继续使用直接实现。

## 2. 主流产品已验证的能力方向

截至 2026-08-15，公开文档能确认的共同方向包括：

| 能力 | 公开产品表现 | 对本项目的意义 |
| --- | --- | --- |
| 可检查的 Subagent | Codex 展示独立 Subagent Thread；Claude Code 支持独立上下文和直接查看成员 | 我们保留每个 Agent 的逻辑对话和运行记录 |
| 按角色配置模型和工具 | Codex/Claude Code 的自定义 Agent 可配置模型、说明和工具 | 使用 Agent Profile + Model Policy + Tool/Skill Scope |
| Skill 渐进加载 | Codex 和 Claude Code 都只先加载 Skill 摘要，需要时再读取正文 | Skill 不能全部塞进每轮上下文 |
| 项目规则与记忆 | Claude Code 支持 CLAUDE.md/AGENTS.md、规则和可审计记忆；Cursor 支持项目/用户/团队规则 | 需要确定性规则层级和用户可编辑记忆 |
| 计划与审批 | Claude Code 团队支持计划批准；Cursor 提供 Planning/Review 工作流 | 把“先计划”和“直接执行”做成显式模式 |
| Hooks 与自动化 | Claude Code/Cursor 都暴露生命周期 Hook | 先稳定内部事件，再开放受控 Hook |
| 检查点和回退 | Claude Code 可恢复文件和对话检查点 | Patch 审批之外还需要本轮撤销与恢复 |
| 沙箱和权限 | 主流本地 Agent 区分权限模式、工作区边界和沙箱 | 确定性权限不能只靠模型或 Prompt |
| MCP | Cursor、Codex、Claude Code 均将 MCP 作为外部工具与数据入口 | MCP 是基础能力，但不能隐式扩大权限 |
| 浏览器与多模态 | Cursor 等产品提供浏览器控制、截图、图片理解 | 与已确定的受管浏览器和视觉模型能力一致 |

不是所有公开能力都已成熟。例如 Claude Code 将完整 Agent Teams 标记为实验性，并列出恢复、协调和关闭方面的限制。因此本项目应借鉴任务、通信和可见性设计，不照搬无限成员团队。

## 3. 现在必须实现的能力

这里的“必须”指进入本地 Agent 闭环，不代表进入第一个 UI 代码批次。

### 3.1 项目规则与指令层级

支持以下来源，并显示每条规则的来源：

```text
应用安全规则
  > 用户规则
  > Team 规则
  > Project AGENTS.md / 项目规则
  > 路径范围规则
  > Agent Profile
  > 当前任务明确约束
```

规则要求：

- 安全规则不能被下层覆盖。
- 项目规则随仓库版本控制，用户规则保存在本机。
- 路径规则只在当前 Task 涉及对应路径时加载。
- 冲突规则在 UI 显示来源与最终取值，不把所有文本无序拼接。
- 大规则文件按上下文预算裁剪或按需加载。

第一版兼容 `AGENTS.md` 即可，不同时发明多种项目规则格式。出现路径级规则需求后，再增加项目内专用目录。

### 3.2 Ask、Plan、Act 与 Review 模式

用户和 Team Lead 应能选择：

| 模式 | 允许行为 |
| --- | --- |
| Ask | 只读分析和回答，不修改文件或执行有副作用命令 |
| Plan | 调查并生成任务、影响范围、风险和验收标准，计划批准前不写入 |
| Act | 在权限和审批合同内执行 |
| Review | 只审查 Diff、结果和证据，不直接修改 |

简单任务默认可以直接进入 Act；范围大、跨模块或高风险任务先进入 Plan。模式是权限和工作流状态，不只是 Prompt 中一句话。

Plan 可以产生活动 Task 列表，但两者不是同一个概念：计划描述方案和风险，任务列表负责可恢复执行。AI 可以为多阶段任务主动创建列表，由同一 Agent 顺序执行；只有出现并行收益或能力差异时才委派。

### 3.3 检查点、撤销和恢复

- 每次用户请求和每组已批准 Patch 前建立逻辑检查点。
- 检查点记录文件基线哈希、Patch、相关消息序号和 Artifact。
- 支持只恢复对话、只撤销本轮 Agent 文件修改、或两者同时恢复。
- 不覆盖用户在检查点之后的外部修改；检测冲突后改为展示反向 Patch。
- Shell、外部程序、数据库和网页副作用不能宣称可自动撤销；只记录证据并提供对应补救操作。
- 检查点不是 Git 替代品，跨会话长期历史仍依赖 Git 与 Artifact。

### 3.4 可观测执行链

每个 Run 必须能回答：

- 使用了哪个模型、协议、上下文预算和选择理由。
- 加载了哪些规则、Skill、MCP 和工具定义。
- 为什么创建或没有创建 Subagent。
- 发生了哪些审批、重试、压缩、截断和回退。
- 消耗的时间、Token、工具次数和失败类型。

UI 默认展示摘要，详细 Trace 按需展开。Trace 需要结构化事件，不依赖拼接控制台日志。

### 3.5 确定性评测与回放

- 使用 MockModel、固定工具结果和临时仓库重放关键工作流。
- 为任务拆分、模型路由、上下文压缩、权限和状态恢复建立固定场景。
- 真实模型评测与确定性测试分开；前者观察成功率和成本，后者作为 CI 门禁。
- 保存失败 Run 的脱敏输入、模型快照、工具 Schema 和事件，能够复现但不保存明文密钥。
- 新模型、Prompt、Skill 或压缩策略上线前运行同一评测集，比较完成率、工具错误、Token 和耗时。

## 4. 现在留边界，满足条件再实现

### 4.1 代码语义能力与 LSP

第一版使用文件树、ripgrep、Git Diff、编译器和测试即可。满足以下任一条件再接 LSP：

- 大型项目中纯文本搜索频繁定位错误。
- 用户明确需要定义、引用、符号重命名和诊断。
- Agent 修改后需要低延迟增量诊断，而完整构建过慢。

接入时通过 `CodeIntelligencePort`，不同语言服务器作为 Adapter，不让 LSP 协议进入 Agent Core。

### 4.2 自动记忆

第一版先做用户明确保存、可查看、可编辑、可删除的 Team/Project/Agent 记忆。只有满足以下条件才启用自动写入：

- 已有记忆来源、时间、项目和置信度字段。
- 用户可以审计、纠正和禁用自动记忆。
- 评测证明自动记忆减少重复说明，且没有明显传播过期事实。

规则、事实、用户偏好和任务摘要必须分开，不能都写进一段“长期记忆”。

### 4.3 Hooks 与自动化

内部先发布稳定事件，例如 `run.started`、`tool.before_execute`、`tool.completed`、`task.completed`。满足以下条件再开放用户 Hook：

- 事件 Schema 和取消语义已经稳定。
- Hook 超时、失败、权限和重入规则已经测试。
- 能明确区分同步阻断 Hook 与异步通知 Hook。

第一版公开 Hook 只允许受控命令或 HTTP/MCP 调用，不允许任意代码注入 Electron Main。典型用途是格式化、测试、质量门禁和通知。

### 4.4 后台运行与通知

本地可恢复 Run 稳定后，再增加系统通知、最小化后台执行和定时任务。触发条件：

- 退出、睡眠、网络中断和重启恢复已经可靠。
- 用户能够设置时间、Token、工具和项目预算。
- 后台任务不会绕过前台审批；等待审批时暂停并通知。

### 4.5 语义索引与知识检索

先使用结构、文本搜索和显式文档引用。只有大仓库或跨项目知识确实无法满足时，才引入增量索引、Embedding 和向量检索。引入前必须定义更新、删除、分支隔离、权限和磁盘成本。

### 4.6 OS 级沙箱

MVP 先使用项目根目录、命令参数、审批和独立浏览器 Profile 建立确定性边界。Windows 本地工具需要更强隔离，或进入无人值守执行后，再评估 Windows Sandbox、容器、WSL、虚拟机或原生辅助程序。不能为了“有沙箱”同时维护多套不等价执行环境。

### 4.7 会话分支与任务 Fork

当前已实现“从创建时刻分叉”的侧边 Conversation Fork：继承当时的 Checkpoint/未压缩上下文和工作区，继承历史不重复显示，Fork 后事件独立。它与一次性任务 Subagent 分离。

尚未实现 Codex 式“从指定用户/Assistant 消息节点分叉”的入口、分支导航和管理。只有用户确实需要从旧节点反复尝试不同方案时再扩展；届时必须明确节点边界、工具副作用和文件工作区是否同时回溯，不能把补一个图标当成完整实现。

## 5. 暂不建设的能力

- 开放插件市场和任意第三方 UI 注入。
- 云端多租户 Agent 集群和远程工作区托管。
- 自建模型训练、推理和通用向量数据库平台。
- 无审批的自动发布、自动付款或高风险网页提交。
- 为所有语言预装 LSP、调试器和构建环境。
- 初始化时创建大量固定岗位或让 Agent 无限递归招聘。

这些能力不是永远不做，而是当前没有足够使用证据，不应影响本地闭环交付。

## 6. 设计模式与扩展时机

| 变化点 | 现在采用 | 何时继续扩展 | 不应做的事 |
| --- | --- | --- | --- |
| 模型协议 | Port + Adapter | 新协议确有不同请求/流事件时新增 Adapter | 在 Agent Loop 中按厂商写 `if` |
| 上下文/路由 | Strategy | 至少有两种真实策略并需要运行时选择 | 为尚不存在的算法建立多层工厂 |
| Task/Run/Approval | State Machine | 增加新状态前先补迁移与转换测试 | 用多个布尔值表达状态 |
| 持久化 | Repository + Migration | 新聚合出现独立事务边界时增加 Repository | 每张表机械包装一个 Service |
| Agent 创建 | Factory | 创建过程出现模型、权限、Skill 和资源不变量时集中 | 建立 Agent 继承树 |
| 工具副作用 | Command + Event | 需要审计、恢复和回放的动作进入事件 | 用全局事件总线隐藏直接依赖 |
| 生命周期扩展 | 内部结构化事件 | Schema 稳定且有真实自动化需求后开放 Hook | 第一版开放任意 Main 进程代码 |
| 隔离 | Scheduler + 资源池 | 崩溃或性能数据证明需要时拆 utility process | 一个 Agent 一个线程/进程 |
| 插件 | MCP + Skill | 出现第三方分发、版本和兼容需求后设计插件 SDK | 把所有内部模块先插件化 |

每次新增抽象前必须能回答：正在隔离哪一个真实变化点、现有第二种实现是什么、如何通过合同测试证明可替换。回答不出来时先使用直接实现。

## 7. 推荐的版本切分

这里的 `v0.1`、`v0.2` 是内部交付里程碑；[第一阶段需求与验收标准](./01-第一阶段需求与验收标准.md)中的完整 MVP 对应完成至 `v0.2`，不能把仅完成 `v0.1` 宣称为已达到完整 MVP。

### v0.1 本地闭环

- 已规划的 UI、会话、文件、Patch、命令、Git、审批、模型和恢复。
- 项目规则最小支持。
- Ask/Plan/Act/Review 模式。
- 基础检查点和本轮撤销。
- 结构化 Trace 与确定性测试夹具。

### v0.2 团队与扩展

- 全 Agent 逻辑对话、Subagent、调度和多项目。
- 多 Provider、MCP、Skill 和模型动态切换。
- 用户可管理记忆、Hooks、后台通知。
- 按实际项目选择性接入 LSP。

### v0.3 规模化

- 语义索引、会话分支、资源自适应调度。
- 更强沙箱、远程执行和 CI/代码审查集成。
- 经真实第三方需求验证后再考虑插件分发体系。

版本号表示能力组合，不要求一次性做完所有条目。每个版本仍按独立代码批次和验收场景交付。
