# 前后端模块与编码规范

> 文档类型：编码指南  
> 文档状态：开工强制规范  
> 更新时间：2026-08-17  
> 适用范围：`apps/web`、`apps/desktop`、`packages/*`、`tests/*`

## 1. 目的

本文档约束 Agent 项目的代码结构、模块依赖、实现方式、注释、测试和变更流程。目标不是提前建立庞大框架，而是保证：

- 新功能放在明确模块中，不跨层直接调用。
- UI、Agent、存储和本机工具可以独立测试和替换。
- 多 Agent、多个项目和长任务增加后，代码仍能定位、恢复和审查。
- 修改新功能时，不破坏既有 Markdown、布局、工具、审批和会话能力。
- 设计模式只解决已经存在的变化点，不为了“看起来高级”增加抽象。

本规范中的“必须/禁止”属于代码审查门禁；“建议”可以在有实证理由时偏离，但需要在变更说明中记录原因。

本文档继续作为全栈总规范。Electron Main、Agent Runtime、模型、工具、SQLite、Migration、IPC 和后端测试的详细规则以[后端编码规范](./13-后端编码规范.md)为准；当前问题和分批实施顺序见[后端代码审查结论与分阶段优化计划](./12-后端代码审查结论与分阶段优化计划.md)。规划中的 `packages/agent-core`、`packages/storage` 和 `packages/local-tools` 是目标边界，不要求在没有第二个真实调用方时提前创建空壳 Package。

## 2. 基本原则

### 2.1 先收敛再实现

每个功能开始前写清：目标、非目标、数据归属、受影响模块、失败行为和验证方式。存在两个合理解释时先澄清，不让实现细节代替产品决定。

### 2.2 简单优先

- 单次使用的逻辑不提前抽象成框架。
- 不为假设中的未来供应商、平台或插件增加空接口。
- 能用清晰函数解决时，不建立类继承体系。
- 能用判别联合和状态机表达时，不堆叠互相制约的布尔值。
- 新增抽象必须至少满足一个条件：隔离外部依赖、消除真实重复、形成可测试边界或匹配既有模式。

### 2.3 单一事实来源

- SQLite 和 Artifact 是团队、任务、会话与工具结果的事实来源。
- Zustand 只保存当前 UI 状态和可重建缓存。
- 模型上下文是事实的临时投影，不是数据库。
- React 组件不得自行维护一份与 Runtime 不同步的任务状态机。

### 2.4 副作用集中

文件、Git、命令、浏览器、密钥和数据库都通过具名端口访问。纯领域代码不得直接读取环境变量、文件系统、Electron 或网络。

### 2.5 行为兼容优先

迁移或修改已有功能时先建立行为基线，再改实现。不能用“代码更整洁”作为删除现有交互、快捷行为、性能保护或错误处理的理由。

## 3. 工程门禁

根工程必须提供并在提交前通过：

```text
pnpm lint
pnpm typecheck
pnpm test
pnpm build
```

发布或涉及 Electron、本机工具、数据库时还必须运行对应集成/E2E 测试。CI 建立后，任何门禁失败均不得合并。

基础配置：

- TypeScript `strict`、`noUnusedLocals`、`noUnusedParameters`、`noFallthroughCasesInSwitch`。
- ESLint 使用 flat config，并启用 TypeScript、React Hooks、无效 Promise 和受限导入检查。
- `.editorconfig` 固定 UTF-8、LF、2 空格缩进和文件末尾换行。
- 不在迁移批次中对无关源文件做全量格式化。
- 依赖版本由 `pnpm-lock.yaml` 固定，禁止以“最新版”作为可复现构建条件。

## 4. 模块依赖

允许的主依赖方向：

```text
apps/web
  -> packages/protocol

apps/desktop/main
  -> packages/agent-core
  -> packages/storage
  -> packages/local-tools
  -> packages/browser-runtime
  -> packages/protocol

packages/agent-core
  -> packages/protocol
  -> 只依赖通过构造函数传入的 Port

packages/storage | local-tools | browser-runtime
  -> packages/protocol
```

禁止：

- `packages/*` 反向依赖 `apps/*`。
- `apps/web` 导入 Electron、Node.js、SQLite、本机工具或任意 `@tauri-apps/*`。
- `agent-core` 直接导入 `better-sqlite3`、`child_process`、Playwright 或 Electron。
- `storage` 依赖 React、UI 状态或具体模型供应商。
- `local-tools` 直接修改 Team/Task 状态；它只返回结构化工具结果。
- 通过深层相对路径绕过 package 的公开入口。

ESLint `no-restricted-imports` 必须把上述边界变成自动检查，而不是只写在文档中。

## 5. 目录与文件放置

### 5.1 `apps/web`

```text
src/
├─ app/                 # 应用装配、Provider、路由和顶层错误边界
├─ components/
│  ├─ ui/               # shadcn/ui 风格基础组件，无业务和宿主调用
│  └─ layout/           # AppShell、Titlebar、ActivityBar、面板容器
├─ features/
│  └─ <feature>/        # team、tasks、chat、editor、diff、terminal、browser
│     ├─ components/
│     ├─ hooks/
│     ├─ model/
│     └─ tests/
├─ pages/               # 页面编排，不实现工具或持久化逻辑
├─ runtime/             # AgentClient、Desktop/Mock/Web Adapter
├─ stores/              # 少量全局 UI 状态
├─ styles/              # Token、基础样式和应用外壳样式
└─ test/                # Web 测试夹具与公共测试工具
```

新代码优先放入对应 `features/<feature>`。只有被多个 Feature 使用且语义稳定的组件，才提升到 `components/ui` 或共享 `lib`。

### 5.2 `apps/desktop`

```text
src/
├─ main/
│  ├─ bootstrap/        # Composition Root 和生命周期
│  ├─ ipc/              # IPC Handler，只做校验和调用 Use Case
│  ├─ security/         # 窗口、导航、权限和密钥策略
│  └─ windows/          # BrowserWindow/WebContentsView 生命周期
└─ preload/
   ├─ index.ts
   └─ api.ts            # 最小、具名、类型化 API
```

Main 是装配层，不堆积 Agent 业务逻辑。Preload 不暴露原始 `ipcRenderer`、任意 channel、文件系统或命令执行函数。

### 5.3 `packages/protocol`

按领域分文件：`team`、`task`、`session`、`model`、`mcp`、`skill`、`tool`、`approval`、`artifact`、`error`、`envelope`。每个外部输入先定义 Zod Schema，再从 Schema 推导 TypeScript 类型，避免 Schema 与 interface 手工漂移。

### 5.4 `packages/agent-core`

```text
src/
├─ team/                # TeamSupervisor、收件和交付汇总
├─ scheduling/          # TaskScheduler、候选过滤、预算和租约接口
├─ agents/              # AgentLoop、AgentProfile、生命周期
├─ context/             # ContextBuilder、摘要和 Artifact 选取
├─ models/              # Provider Registry、ModelAdapter、能力矩阵和选择策略
├─ skills/              # Skill 发现、匹配、依赖和按需加载
├─ tools/               # ToolRegistry 与工具调用合同
├─ permissions/         # PermissionPolicy
└─ ports/               # Storage、Tool、Clock、Id、Event 等接口
```

领域状态转换必须集中在 Use Case/State Machine 中。IPC Handler、React 组件和 Repository 不得各自实现一套状态判断。

### 5.5 `packages/storage`

- `migrations/`：只向前的版本化 Migration，已执行 Migration 禁止修改。
- `repositories/`：按聚合边界提供查询和事务，不泄漏 SQL Row 到上层。
- `artifacts/`：路径、哈希、写入原子性和清理策略。
- `transactions/`：需要同步写入当前状态与事件的事务入口。

### 5.6 `packages/local-tools`

按能力分为 `filesystem`、`search`、`patch`、`git`、`process`、`mcp`。MCP Manager 只负责连接、能力发现和执行适配；公共路径边界、权限映射、输出上限、取消和审计逻辑不得在每个工具中复制。

### 5.7 `packages/browser-runtime`

分为 `profiles`、`pages`、`snapshot`、`actions`、`downloads` 和 `lifecycle`。页面操作只接收结构化参数，不接受模型提供的任意 JavaScript 字符串。

## 6. TypeScript 编码规范

### 6.1 命名

| 类型 | 规范 | 示例 |
| --- | --- | --- |
| 文件/目录 | `kebab-case` | `task-scheduler.ts` |
| React 组件/类型 | `PascalCase` | `TaskBoard`, `WorkItemStatus` |
| 函数/变量 | `camelCase` | `assignTask`, `projectId` |
| 常量 | 语义常量用 `UPPER_SNAKE_CASE` | `MAX_WORKER_COUNT` |
| Zod Schema | 名称 + `Schema` | `toolCallSchema` |
| Port | 能力名 + `Port` | `TaskRepositoryPort` |
| Adapter | 实现名 + `Adapter` | `DesktopAgentClientAdapter` |
| Repository | 聚合名 + `Repository` | `TaskRepository` |
| 事件名 | `noun.past_tense` 或既定过去式 | `task.assigned`, `agent.spawned` |

事件字符串在 `protocol` 集中定义，禁止散落硬编码。

### 6.2 类型

- 禁止无说明的 `any`；外部未知值使用 `unknown` 并在边界解析。
- 状态使用判别联合，不使用多个可能矛盾的布尔值。
- ID 保持独立字段名，不把所有 ID 都简写为 `id` 后在跨域传递。
- 公共函数显式声明返回类型；局部简单回调允许推断。
- 不滥用 `as` 和非空断言。需要断言时先证明不变量，并在边界收口。
- 对外时间统一 ISO UTC 字符串；内部需要计算时显式转换。
- 金额、Token、字节和毫秒等数值在名称中带单位，例如 `timeoutMs`、`byteSize`。

### 6.3 函数与控制流

- 函数只承担一个可描述职责。
- 先用 guard clause 处理失败和边界，避免深层嵌套。
- 副作用函数名称应体现动作，例如 `persistEvent`、`spawnProcess`。
- 超过一个异步阶段的操作必须接收 `AbortSignal` 或明确的取消合同。
- `switch` 处理判别联合时使用穷尽检查。
- 禁止空 `catch`；忽略错误必须说明为什么安全。

### 6.4 文件复杂度

以下不是机械行数上限，而是强制评审触发点：

- React 页面或业务组件超过约 `250` 行。
- 普通 TypeScript 文件超过约 `400` 行。
- 单个函数超过约 `60` 行或同时处理三个以上副作用。
- 一个文件同时包含 UI、状态机、持久化和宿主调用。

触发后必须检查是否能按职责提取；如果因 CodeMirror 扩展、Schema 集合或生成代码必须保持集中，应在文件顶部说明原因并补定向测试。

## 7. 前端实现规范

### 7.1 组件分层

- `components/ui`：无业务状态、无 AgentClient、无项目路径知识。
- `components/layout`：只负责稳定布局和插槽，不读取数据库或调用工具。
- `features/*/components`：展示业务对象，通过 props/hook 获取行为。
- `pages`：组合 Feature，不包含复杂状态转换。

### 7.2 状态管理

- React 局部交互优先使用本地 state/reducer。
- Zustand 用于跨页面且纯 UI 的状态，例如当前面板、选中项、折叠和尺寸。
- Team、Task、Session、Approval 等持久业务状态来自 AgentClient 事件和查询结果。
- 对话内任务列表和任务板必须共用 Task 查询投影，禁止在 Zustand 维护第二份 Todo 状态。
- Store 不能直接调用 Electron/Tauri/Node；异步动作放在 runtime adapter 或 feature controller。
- 使用 selector 订阅最小状态，避免整个 Store 更新导致大页面重渲染。

### 7.3 异步 UI

每个异步功能必须定义：初始、加载、空、成功、失败、取消和恢复状态。工具或 Agent 流式事件不能直接无限追加到 DOM，长列表使用分段加载或虚拟化。

### 7.4 宿主访问

正确：

```ts
const capabilities = await agentClient.getCapabilities();
```

禁止：

```ts
window.electron.ipcRenderer.send("run-anything", payload);
```

组件只依赖 `AgentClient` 或更窄的 Feature Port。浏览器 Mock 与 Desktop Adapter 必须通过同一合同测试。

## 8. Electron 与后端模块规范

### 8.1 Composition Root

依赖只在 Electron Main 的启动装配层创建。Use Case 通过构造函数或工厂接收 Port，不使用全局可变 Service Locator。

### 8.2 IPC

- Channel 在 `protocol` 集中定义和版本化。
- 请求与响应都经过 Zod 校验。
- Handler 只做解析、鉴权、调用 Use Case 和错误映射。
- Renderer 提供的 `projectId`、路径和 actor 均不能直接信任。
- IPC 不返回 Error 实例、数据库 Row 或含密钥对象。

### 8.3 存储

- Repository 返回领域对象或显式 DTO。
- 当前状态和对应追加事件在同一事务提交。
- 多表写入失败必须整体回滚。
- Artifact 使用临时文件 + 原子替换，数据库保存相对路径、大小和哈希。
- 删除采用可恢复清理流程，不能数据库已删而 Artifact 静默残留。

### 8.4 本机工具

- 命令使用 `spawn(executable, args)`，禁止拼接未经验证的 shell 字符串。
- 执行前解析 projectId、真实根路径、工作目录和审批记录。
- 路径规范化后再次确认位于授权根目录；处理符号链接和 Windows 大小写。
- stdout/stderr 流式读取但受字节上限控制，完整输出写 Artifact。
- 取消时终止完整进程树并等待退出结果。
- 工具返回结构化错误、退出码、耗时、截断信息和 Artifact 引用。

### 8.5 Agent 与调度

- TeamSupervisor 负责“是否委派”，TaskScheduler 负责“分给谁和何时运行”。
- TaskPlanner 只负责把 WorkItem 拆成可验收 Task 和依赖；创建 Task 不自动创建 Agent。
- 路由先确定性过滤，再在候选中评分或调用模型。
- Worker 不得直接创建 Worker，只能发送增员建议。
- Agent Conversation 是持久化逻辑对象，不得为每个 Agent 创建常驻 OS 线程、`worker_threads`、子进程或模型连接。
- 网络模型调用使用异步 I/O；CPU 密集工作进入固定 Worker Pool，本机进程和浏览器使用独立并发池。
- Task 状态转换必须校验前置状态和租约持有者。
- Agent 间消息不能授予权限或改变用户审批结果。
- Agent Loop、TaskScheduler 和 Repository 分别测试，不把所有逻辑写在一个循环中。
- Task 列表修订通过命令和事件进入状态机，已完成项重新打开必须保留原记录与理由。

## 9. 设计模式使用规则

项目采用以下模式解决明确问题：

| 模式 | 使用位置 | 解决的问题 |
| --- | --- | --- |
| Ports and Adapters | AgentClient、Model、Storage、Tool | 隔离 UI、Electron 和外部依赖 |
| Strategy | ModelAdapter、ContextCompression、RoutingPolicy | 运行时可替换策略 |
| Repository | Team、Task、Session、Artifact | 隔离 SQL 与领域模型 |
| State Machine | WorkItem、Task、Run、Agent 生命周期 | 防止非法状态组合和重放 |
| Command + Event | IPC 命令、领域事件 | 可审计、可恢复、可测试 |
| Factory | Agent Instance、Browser Profile | 集中创建约束和资源装配 |
| Observer/Event Stream | Runtime 到 UI | 流式更新且不耦合 React |
| Lease/Work Queue | Task 领取和恢复 | 防止重复执行和崩溃后永久占用 |

禁止为了模式而模式：

- 没有第二个实现时，不提前建立多层 Abstract Factory。
- 不用继承树表达 Agent 角色，使用 Profile + 组合能力。
- 不使用全局事件总线掩盖模块依赖；跨域事件必须有 Schema 和 owner。
- 不把所有行为塞进“万能 Manager/Service/Utils”。
- 不用 Repository 包装纯内存数组或无持久化需求的局部状态。

新抽象和扩展点的引入时机遵守[能力路线图与扩展时机](./09-能力路线图与扩展时机.md)：必须说明真实变化点、第二种实现和合同验证方式，不能以“未来可能用到”作为唯一理由。

## 10. 错误、日志与安全

### 10.1 错误

- 错误分为 `validation`、`permission`、`conflict`、`not_found`、`timeout`、`cancelled`、`provider`、`tool`、`storage`、`internal`。
- 用户可读消息与内部诊断分离。
- 禁止通过匹配错误字符串决定业务分支。
- 错误必须携带稳定 `code`、是否可重试和相关实体 ID；不得携带 API Key 或完整敏感内容。

### 10.2 日志

- 使用结构化日志，包含 `traceId`、`teamId`、`workItemId`、`taskId`、`runId` 等可用关联字段。
- 日志记录状态变化和边界结果，不重复记录完整模型上下文、文件正文或终端输出。
- 对 `authorization`、`apiKey`、`token`、cookie 和常见密钥格式统一脱敏。
- 生产日志不能依赖控制台文本作为数据库恢复依据。

### 10.3 安全

- 所有跨进程、模型、MCP、文件和网页输入均视为不可信。
- 权限判断由本地确定性代码完成，不能让模型返回“已批准”。
- Preload API 最小化，Renderer 开启 `contextIsolation`、关闭 `nodeIntegration`。
- 任何绕过项目根目录、审批、并发上限和 Artifact 根目录的路径都必须有负向测试。

## 11. 注释与文档

注释解释“为什么、约束和不变量”，不复述代码。

应该注释：

- Windows 进程树、符号链接、Electron 生命周期等非显然平台行为。
- 状态机为何拒绝某个转换。
- 性能保护阈值的来源和验证方式。
- 与外部协议、数据库 Migration 或源项目兼容相关的约束。
- 乍看可以简化、但实际会破坏行为的代码。

不应注释：

```ts
// 设置任务状态为完成
task.status = "completed";
```

公共 Port、Schema 和复杂 Use Case 使用简短 JSDoc，说明语义、失败条件和副作用。`TODO` 必须包含明确原因和跟踪标识；不能用 TODO 代替本批次必需实现。

## 12. 测试与回归规范

### 12.1 测试层级

| 层级 | 必须覆盖 |
| --- | --- |
| 单元测试 | 纯函数、状态转换、路由过滤、上下文选择、路径规则 |
| 合同测试 | Desktop/Mock/Web AgentClient、ModelAdapter、Tool、Repository Port |
| 集成测试 | SQLite Migration/事务/恢复、文件/Git/进程、Artifact |
| 组件测试 | 关键 UI 状态、审批、任务列表、键盘和无障碍语义 |
| 视觉回归 | AppShell、编辑器、Diff、终端、团队面板的固定视口 |
| E2E | 浏览器与 Electron 主流程、发布包恢复和权限边界 |

### 12.2 防止新功能破坏旧功能

每次修改已有模块按以下顺序执行：

1. 列出当前行为和受影响调用方。
2. 为缺少保护的旧行为补 characterization test 或固定截图。
3. 做最小实现，不同时重构无关代码。
4. 运行受影响模块定向测试。
5. 运行根级回归、构建和必要 E2E。
6. 对比事件、数据库、截图、DOM 规模或进程结果，不以“能编译”宣布完成。

Bug 修复必须先有可失败的复现测试；无法自动化时，记录可重复的人工检查步骤和证据。

### 12.3 高风险变更矩阵

| 变更 | 必须追加验证 |
| --- | --- |
| Protocol/Schema | Desktop/Mock 合同测试、旧事件解析、版本兼容 |
| SQLite/Migration | 空库、旧库、失败回滚、重启恢复 |
| Agent/调度 | MockModel 确定性场景、循环上限、取消、重复领取 |
| 文件/Patch | 路径逃逸、外部修改冲突、编码和原子写入 |
| 命令 | 成功/失败/超时/取消/长输出/进程树 |
| AppShell/UI Token | light/dark、多视口、面板拖拽、视觉截图 |
| Markdown/CodeMirror | 现有夹具、长文档、滚动、粘贴和渲染截图 |
| Electron/Preload | 浏览器降级、安全配置、发布包启动 |

## 13. 依赖管理

- 新依赖前先确认标准库或现有依赖是否已经解决问题。
- 记录引入目的、维护状态、包体影响、许可证和替代方案。
- UI 组件优先使用项目内 shadcn/ui 风格组件和 Radix，不并列引入第二套完整 UI 框架。
- 核心领域逻辑不绑定某个模型 SDK；SDK 放在 Adapter 内。
- Agent Loop 不按供应商名称分支；协议差异、鉴权和事件转换只能出现在 `ModelProviderAdapter`。
- Skill 说明可以参与上下文构建，但 Skill 脚本必须通过 ToolRegistry 和 PermissionPolicy，不能直接调用 Node 或 Shell。
- 原生模块必须尽早做 Electron ABI rebuild 和安装包冒烟。
- 删除依赖前搜索动态 import、构建脚本和发布资源，不只看 TypeScript 引用。

## 14. 提交与代码审查

提交标题格式：

```text
<type>: <中文说明>
```

常用类型：`feat`、`fix`、`refactor`、`test`、`docs`、`build`、`chore`。

一个提交只表达一个可验证意图。迁移、重构、功能、依赖升级和格式化不混在同一提交。

代码审查必须确认：

- 改动是否能追溯到需求。
- 是否跨越了模块依赖边界。
- 是否新增重复状态源、字符串协议或万能 Service。
- 是否正确处理错误、取消、超时和资源释放。
- 是否保留既有行为，并有对应回归证据。
- 是否新增了不必要抽象或依赖。
- UI 是否符合[界面迁移与设计系统规范](./07-界面迁移与设计系统规范.md)。
- 文档、Schema、Migration 和实际行为是否同步。
