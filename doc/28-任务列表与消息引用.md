# 任务列表与消息引用

## 用户界面

普通对话与团队群聊右上角统一使用“任务列表”。点击打开搜索卡片，支持按任务名称、目标或关联的用户消息搜索，每页五项，并显示匹配总数。点击任务或“在侧边打开”，进入既有右侧工作区的“任务列表”标签，不替换主对话，也不另外创建侧栏。关闭标签不删除任务或来源消息。

侧边工作区采用消息优先布局：左侧选择任务，右侧显示任务名称、状态、手动确认、目标、最近进展，以及按来源对话分组的用户原消息。下一步和约束仅在有内容时显示。消息可定位原文；不把成员执行日志当作用户需求。宽度不足 640px 时，列表与详情分别显示，并提供返回入口。搜索、选择和滚动由现有保留标签机制维持，隐藏时不订阅式重读任务正文。

## 完成确认

任务列表与任务清单是两个用途：本页的任务列表保存目标、状态、来源和结果，完成后仍可查询；`update_task_list` / `close_task_list` 管理对话输入区上方的任务清单，只表示当前执行步骤。子代理可以按需维护自己的局部清单，由主对话统一维护持久任务列表，避免每位执行者重复登记同一目标。快速协作先查询已有任务，再登记或更新每项已领取且要委派的目标，回执后修订实际结果；一张清单可处理多个目标，也可只属于一个目标，不按清单步骤自动创建任务。

普通任务保持 pending、running、blocked、completed、failed、cancelled 六种状态。`completionRequested` 表示 Agent 提交的结果等待确认，不是新增的任务状态。用户随时可手动修改普通任务状态或确认完成。

“允许 Agent 自动确认完成”默认关闭，仅作用于所选普通对话或群聊。许可保存在迁移 35 的 `task_completion_policies` 元数据表，普通对话与团队群聊分别保存。Agent 的 `update_task_context` 请求 completed 时，后端检查此许可；关闭时保留原运行状态并设为待确认，开启时才允许完成。工具不提供修改许可的入口，未知许可字段会被拒绝。用户操作与 Agent 操作记录 `completedBy`。团队 WorkItem 仍沿原验收流程维护，本列表不绕过工作项验收。

## 来源、分页与接口

任务详情来源补充原文、角色、时间；群消息原文仍来自既有 JSONL，普通消息来自既有消息投影，不创建另一份对话事实。列表返回 `total` 和 `userMessageCount`，匹配总数在游标分页之前计算。搜索群原消息时按关联消息位置批量读取对应 JSONL，不把群消息正文复制到 SQLite。

新增窄接口：`getTaskCompletionPolicy`、`setTaskCompletionPolicy`、`resolveChatReferences`。权限与引用接口必须且只能选择 conversationId 或 teamInstanceId；引用每次最多二十个 UUID。IPC 校验可信窗口、严格请求 Schema 和返回 Schema。引用仅在当前可访问任务范围或所选消息容器内解析，找不到的记录不返回其他私聊内容。

## 消息与任务引用

新输出可以使用 `[任务 名称](task://UUID)` 和 `[引用消息](message://UUID)` 表达引用。Renderer 把已验证任务显示为蓝色任务图标、文字“任务”和名称，点击在当前主对话的侧边打开对应任务。消息引用显示发送者和原文摘要，点击定位原消息。

旧回复中直接输出的消息或任务 UUID，包括单独的行内代码 UUID，使用同一范围解析后转成引用。没有可用来源的明确引用显示不可用状态，不伪造跳转目标。围栏代码、普通 UUID 编程示例和外部链接保持原样；不批量改写已保存的模型消息。消息引用渲染与普通 Markdown、成员提及共用同一个插槽机制。

## 验证

- Storage：消息原文搜索、游标前总数、来源角色与计数、私聊/群聊权限隔离、迁移与重启持久化。
- Tool/IPC：Agent 不能自行授权完成，可信窗口及严格参数校验，注册清理对称。
- UI：搜索分页、侧边标签打开、手动确认、来源跳转、引用安全和缓存保留。
- Headless UI：实际共享侧栏与组件，在深色、浅色、宽/窄侧栏下检查布局；测试使用内存客户端，不操作用户开发窗口或真实对话数据。

## 合并任务更新（2026-10-19）

模型的 `update_task_context` 使用 `updates: [{...}]`，一次处理 1–20 条持久任务，单条任务用单元素数组。每项仍使用真实 id 与 expectedRevision，新建时同时省略两者；状态、摘要、决策和下一步在同一项提交。同一任务不能在一批中重复出现。整批任务、来源、运行绑定和幂等记录在同一事务中提交，任一项校验或修订冲突会回滚整批；修正后可重试。返回 value.tasks 中各项的真实 ID、修订和完成确认状态。执行器继续兼容旧版单条参数，不新增工具或 IPC。

批量更新多个既有任务时，省略来源保留原引用，不把当前最新的一条独立输入自动加到所有旧任务；需要增加来源时明确提供该项真实 source。新建任务和单项当前请求仍沿原逻辑自动绑定来源。预定委派信息随初次登记提交；委派按计划发出后不再单独改写“等待反馈”，等下一项实质结果一起更新，接收者、范围或失败变化除外。重复且内容无变化的更新不新增修订；完成确认仍由原用户许可控制，待确认不需要再次提交 completed。

输入框上方的执行清单仍独立：一次 `update_task_list` 同时提交所有已知步骤变更，例如上一项完成、下一项开始。最后一次可在所有步骤均 completed 时传 `close: true`，直接关闭，不先写入一张马上删除的中间清单，也不再单独调用关闭工具；未完成步骤禁止这样关闭。旧 close_task_list 继续兼容。实际执行前后的阶段变化仍分别记录，不把减少调用当作隐藏真实阻塞或验收的理由。
