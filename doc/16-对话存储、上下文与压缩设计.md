# 对话存储、上下文与压缩设计

## 1. 目的

本文统一定义 Agent 的四个边界：

1. 用户、Agent、模型和工具产生的内容如何持久化；
2. 长对话如何压缩而不破坏原始历史；
3. 每次模型请求实际可见哪些上下文；
4. 如何在上下文不断变化时尽量保持 Provider 的前缀缓存命中。

本文描述的是运行时合同。UI 展示、Timeline 卡片和模型请求的审计元数据可以使用同一批事实，但不等于模型上下文。

## 2. 术语边界

| 术语 | 含义 |
| --- | --- |
| 完整历史 | SQLite 中持久保存的全部用户消息、Assistant 输出、Tool Call 和 Tool Result |
| 模型上下文 | 某一次 `completeTurn` 实际发送的 `ModelMessage[]` |
| Run | 一次用户需求对应的一次 Agent 执行；一个 Run 可以有多次模型请求 |
| Model Call | Run 内一次语义上的模型请求；用于审计，不发送给模型 |
| Tool Call | 某次模型请求产生的单个工具调用；通过 `tool_call_id` 与结果关联 |
| Context Checkpoint | 对较早历史的结构化增量摘要，以及它覆盖到的消息序号 |
| 任务清单 | 一个 Conversation 的可变工作状态；不是聊天历史，也不是 Checkpoint 的权威来源 |
| 工作记忆 | 当前对话的 Checkpoint、最近原文和当前 Run 状态 |
| 长期记忆 | 跨对话、跨项目主动保存并检索的知识；当前版本不实现通用长期记忆库 |

“滑动窗口”只描述最近原文的保留方式。当前完整方案应称为：

> 基于 Token 预算的分层上下文管理：最近原文窗口 + 增量摘要 + 按需关键词检索。

## 3. 持久化模型

> **迁移状态（2026-08-27）**：新建正常 Run 会向 `<AGENT_HOME>/conversations/<conversationId>.jsonl` 追加 `ThreadLog v1` 事件，并按游标索引到 SQLite 的 `thread_log_event_index`。**仅新建普通空 Conversation 不创建 JSONL；首次提交模型可见输入（或已有可恢复历史的旧 Conversation 导入）才创建。**空侧边分支为保留其父子关系，迁移时仍保留极小的关系日志。已有 JSONL / EventProjector 的普通首轮输入和被消费的 `queue` 输入使用单个 `run_queued` 写前事件，原子携带用户消息、Run、模型/权限快照和首个标题；运行中的新增、编辑、排序和升级为 Steer 的 Pending 输入均使用完整 `pending_messages_updated` 快照，并在物化时同时预约已有附件；删除 Pending 使用 `pending_message_cancelled`，保留取消审计并释放草稿附件；Steer 在真正进入活跃 Run 的模型安全边界时，转换为写前 `user_message`，原子消费 Pending 并写入模型可见消息；执行边界使用 `run_started`；模型产生工具调用或安全边界后的中途 Assistant 回合使用 `assistant_message`；真正调用处理器前的 Tool Timeline 使用 `tool_call_requested`，完成时的 Tool 状态和模型结果使用 `tool_result`；压缩 Checkpoint 使用 `context_checkpoint`；编辑最新用户消息时使用 `run_replaced`；不涉及 Subagent 跨对话交付的普通 Run 终态使用 `run_terminal`。这些写前事件均先落 JSONL，再物化为 SQLite 的 Run、Timeline、模型消息、Checkpoint 和附件绑定；`run_queued` 同时消费对应的持久队列记录。消息和 Pending 快照携带公开 `attachmentRefs`；启动投影由 `AttachmentStore` 的确定性目录规则恢复附件元数据和受管路径，但不把绝对路径或二进制写入 JSONL。Subagent 终态仍暂走既有 SQLite 原子完成与跨对话投递链路，避免把两个 Conversation 日志伪装成一个原子提交。协作、任务清单、审批决定等仍处于影子日志迁移路径。跨对话协作消息同样以 `messageId` 去重追加到接收方日志，并作为模型可见的用户消息重放。若 Conversation 只有日志元数据而核心业务投影缺失，富事件可重建 Run、Timeline、模型消息、工具结果、Checkpoint、任务清单与 Subagent 关系；已有 SQLite 业务行不会被回放覆盖。启动补投影会重新物化游标之后的写前事件，即使该 Conversation 已有较早 SQLite 业务行；`run_started` 表示已越过可安全自动恢复的边界：启动补投影后仍没有终态的这类 Run 会失败，不会重新调用模型或工具。`ContextCompiler` 在该对话存在 ThreadLog 时，以日志重放出的模型消息和 Checkpoint 编译本轮上下文；SQLite 继续承担 Timeline、Run、FTS 查询和正常业务写入，相关历史检索仍由 SQLite FTS 提供。进程内对 ThreadLog 上下文保留增量缓存：追加普通事件只更新缓存，只有一次性旧数据导入才在下一次读取时重建。附件二进制若已丢失、删除任务等仍不能由增量业务事件完整重建，因此 JSONL 尚未成为全部业务事实的唯一规范源。〔FACT｜`apps/desktop/src/main/storage/thread-log.ts`；`apps/desktop/src/main/storage/agent-database.ts`；`apps/desktop/src/main/storage/event-projector.ts`；`apps/desktop/src/main/storage/conversation-attachment-store.ts`；`apps/desktop/src/main/agent/context-compiler.ts`〕

### 3.1 原始历史永不因压缩删除

`model_messages` 是模型历史的事实来源，至少保存：

```json
{
  "sequence": 42,
  "id": "msg_042",
  "conversation_id": "conv_001",
  "run_id": "run_007",
  "role": "assistant",
  "content": "",
  "tool_calls_json": [
    {
      "id": "tc_009",
      "name": "read_file",
      "arguments": "{\"path\":\"src/login.tsx\"}"
    }
  ],
  "tool_call_id": null,
  "attachment_ids_json": [],
  "provider_state_json": null,
  "created_at": "2026-08-20T10:00:00.000Z"
}
```

`role` 的含义：

- `user`：用户消息，也包括被包装成用户消息的 Agent 协作消息和 Steer 消息；
- `assistant`：模型正文和模型发起的 Tool Call；
- `tool`：工具结果，使用 `tool_call_id` 关联对应调用。

### 3.2 运行和模型元数据不混入上下文

以下信息要持久化用于审计、恢复和 UI 展示，但不作为普通文本发送给模型：

```text
conversation_id
run_id
model_id
model_call_id
attempt_id
provider_request_id
reasoning 配置
权限模式
Token 用量
耗时和重试次数
```

其中：

```text
conversation_id  整个对话
run_id           一次用户需求的 Agent 执行
model_call_id    Run 内一次语义模型请求
attempt_id       同一请求的网络重试
tool_call_id     一次模型请求产生的单个工具调用
```

重试保持同一个 `model_call_id`，只生成新的 `attempt_id`。这些字段属于运行审计，不属于模型可见内容。

当前实现尚未新增 `model_calls` 审计表，也没有为 Run 内每次 Provider 请求持久化 `model_call_id/attempt_id`；本轮只保留这一边界，继续使用现有 `run_id`、模型消息和 `tool_call_id` 支撑上下文构建。后续若需要请求级成本、重试或 Provider Request ID 审计，再单独增加持久化批次。

### 3.3 Checkpoint

当前会话保存最新的 Context Checkpoint：

```json
{
  "conversation_id": "conv_001",
  "covered_through_sequence": 36,
  "summary": {
    "goals": ["实现登录页"],
    "requirements": ["复用现有组件"],
    "constraints": ["不能修改后端接口"],
    "decisions": ["使用现有表单校验方案"],
    "filesRead": ["src/login.tsx"],
    "filesChanged": ["src/login.tsx"],
    "commands": ["pnpm test"],
    "testResults": ["通过"],
    "errors": [],
    "pendingWork": ["补充异常状态"],
    "taskStatus": ["进行中"],
    "artifactRefs": [],
    "rejectedApproaches": []
  },
  "created_at": "2026-08-20T10:00:00.000Z",
  "updated_at": "2026-08-20T10:00:00.000Z"
}
```

`covered_through_sequence` 只能前进。压缩失败时，原始历史和旧 Checkpoint 都保持不变。

### 3.4 UI 历史、Timeline 和模型上下文分离

```text
model_messages       模型历史事实
conversation_timeline UI 展示、工具卡片、审批、Diff 和状态
context_checkpoint   历史压缩结果
LangGraph Checkpoint 当前 Run 的可恢复图状态
```

压缩不删除 Timeline 或 `model_messages`。Run 结束后，LangGraph 的临时线程状态按现有生命周期清理；可追溯事实仍在 SQLite 中。

## 4. 每次模型请求的上下文

模型请求不是“把整个会话重新发一遍”，而是每次由 Context Builder 按预算重建 `ModelMessage[]`。逻辑顺序如下：

```text
1. 稳定系统指令、会话/工作区/权限等固定运行规则
2. 当前有效任务清单（如有；动态系统块）
3. 最新 Context Checkpoint（如果存在）
4. Checkpoint 未覆盖的按时间顺序排列的完整消息
5. 按当前请求检索到的相关旧历史（动态尾部）
6. 本次 Run 内新增的 Agent/Steer 消息、Assistant Tool Call 和 Tool Result
```

工具定义通过 `tools` 参数单独发送，不伪装成聊天消息。

在运行时实现上，`LangGraphExecutor` 的 `beforeAgent` Middleware 在一个 Run 的 Graph `thread_id` 首次进入时调用 Runtime `prepareContext`，把稳定系统内容、Checkpoint 和未覆盖历史写入图状态。图状态中的 `contextPrepared` 防止同一 Run 的审批恢复或 Queue/Steer 追加重复注入历史；这些新增输入仍由每轮 `beforeModel` 在安全边界消费。**任务清单也在 `beforeModel` 从当前 Conversation 重新读取，并作为临时 `system` 消息仅送入当次 Provider 请求，不写回 LangGraph `messages`。** 因而模型在 `create_task_list`、`update_task_list`、`close_task_list` 后的下一轮看到的是最新状态，不会累积旧版本。上下文内容的选择、压缩和 Skill 预算仍由 Runtime/ContextManager 决定，Middleware 只负责生命周期挂接。〔FACT｜`apps/desktop/src/main/agent/agent-runtime.ts`；`apps/desktop/src/main/agent/langgraph-executor.ts`；`apps/desktop/src/main/agent/task-list-context.ts`〕

### 4.1 任务清单的动态上下文合同

任务清单由 `create_task_list`、`update_task_list`、`close_task_list` 操作并按 `conversationId` 保存；UI、恢复和查询仍使用其持久化事实，但模型不把 `task_list_updated` 事件或旧 Tool Result 当作状态来源。每次模型调用使用当前的 active list，按原有任务顺序只序列化 `status + title`，并且只为 `blocked`、`failed` 项追加经截断的 `reason`：不包含任务 UUID、`createdAt`、`updatedAt` 或 Run ID，以避免无意义的缓存失效。

`ContextCompiler` 只为**当前存在且 active 的**任务清单按实际序列化内容预留 Token；不存在或已关闭的清单预留为零，不能为了尚未创建的计划提前挤占历史预算。每项标题在模型块中最多 120 个字符，阻塞/失败原因最多 240 个字符，持久化原值不改；任务工具创建或更新清单后，下一次 `beforeModel` 仍重新读取并注入当前版本。〔FACT｜`apps/desktop/src/main/agent/task-list-context.ts`；`apps/desktop/src/main/agent/agent-runtime.ts`；`apps/desktop/src/main/agent/context-compiler.ts`〕

一次实际请求可以抽象为：

```json
{
  "messages": [
    {
      "role": "system",
      "content": "稳定的 Agent 规则、工具使用规则和安全边界"
    },
    {
      "role": "system",
      "content": "当前会话工作区、权限和任务状态"
    },
    {
      "role": "system",
      "content": "较早历史的结构化摘要"
    },
    {
      "role": "user",
      "content": "最近一轮用户消息"
    },
    {
      "role": "assistant",
      "content": "最近一轮模型回复"
    },
    {
      "role": "system",
      "content": "根据当前请求检索到的相关旧历史"
    },
    {
      "role": "user",
      "content": "当前用户消息"
    }
  ],
  "tools": [
    {
      "name": "read_file",
      "description": "读取工作区文件",
      "parameters": {}
    }
  ]
}
```

上面是逻辑结构；Provider Adapter 会将其转换为 OpenAI、Anthropic 或 Gemini 的原生请求格式。

## 5. 消息选择规则

### 5.1 没有超过预算时

如果系统指令、工具定义、附件、输出预留、Checkpoint 和未覆盖历史全部能放入阈值，则发送全部未覆盖历史，不人为按固定条数截断。

```text
稳定系统上下文
+ 当前运行上下文
确有 Checkpoint 时：+ Checkpoint
+ Checkpoint 之后的全部原始消息
+ 相关历史动态块（有命中时）
```

### 5.2 超过预算时

顺序固定为：

1. 旧的超长 Tool Result 先保留开头、结尾、错误/警告行，并标记已裁剪；
2. 最近约两次用户发起的完整对话轮优先保留；
3. 更早且尚未覆盖的完整轮次作为压缩候选；
4. 压缩成功后，用新 Checkpoint 代表候选前缀；
5. 重新按剩余预算从最新完整轮次向前选择；
6. 任何时候都不拆开 Assistant Tool Call 与对应 Tool Result。

这里的“最近两轮”是保护下限，不是固定最终条数。最终结果由 Token 预算决定：

```text
可用历史预算
= 压缩阈值
 - 系统内容
 - 工具定义
 - 输出预留
 - Skill 正文预留
 - 可变任务清单预留
 - Checkpoint 摘要
 - 附件和相关历史动态块
```

### 5.3 已有 Checkpoint 时

```text
covered_through_sequence = 36

序号 1..36   原始记录仍在数据库，但由 Checkpoint 代表
序号 37..N   作为新的原始上下文候选
```

如果旧序号 1..36 中有与当前请求高度匹配的事实，关键词检索可以把它作为动态相关历史重新带回本次请求；这不会改变 Checkpoint 覆盖范围。

### 5.4 相关历史检索

当前不依赖 Embedding 模型。请求文本中的以下内容作为关键词：

- 文件路径；
- 函数、类、变量和工具名；
- 错误码和命令；
- 英文、数字、路径和标识符词；
- 中文连续文本拆成有限的二/三字符片段，避免把整句当成一个不可命中的词；
- 两个字符的中文或短标识符使用 `LIKE` 兜底，检索文本同时包含消息正文和 `tool_calls_json`。

检索约束：

1. 默认只检索当前 `conversation_id`；
2. 排除已经位于最近原文窗口的消息，避免重复；
3. 按 SQLite FTS5/BM25 和时间顺序排序；
4. 命中消息格式化为一个独立的“相关历史”动态块，追加在原始历史之后；
5. Runtime 单次最多取 24 条候选，Context Manager 最多注入 12 条、12,000 字符；相关历史有独立 Token 上限，超限时直接减少命中，不影响当前请求和最近原文；
6. 相关历史计入 `estimatedReferenceTokens`，与跨对话/项目引用使用同一用量口径；
7. 检索结果只影响本次请求，不写入聊天 Timeline，不伪装成新的用户消息。

这样即使摘要没有保留某个早期具体路径，也可以按当前问题把原始事实临时取回。

## 6. 压缩维护

### 6.1 增量压缩

压缩只处理尚未进入 Checkpoint 的较早前缀，不每轮重新总结整个会话：

```text
第 1..18 条 -> checkpoint-001，covered_through_sequence=18
第 19..35 条增长后
旧摘要 + 第 19..若干条 -> checkpoint-002，covered_through_sequence=35
```

生成摘要使用严格 JSON 字段，至少保留目标、要求、约束、决定、文件、命令、测试、错误、未完成事项、附件引用和被否定方案。

### 6.2 不压缩时

没有达到阈值时，不生成 Checkpoint；Context Builder 直接使用当前已有 Checkpoint（如有）和未覆盖的原始消息。

因此“没有发生压缩”有两种正常状态：

- 没有旧 Checkpoint，且全部历史放得下；
- 已有旧 Checkpoint，但 Checkpoint 之后的新消息尚未达到下一次压缩阈值。

### 6.3 压缩失败

压缩模型返回非法 JSON、请求失败或被取消时：

- 不移动 `covered_through_sequence`；
- 不删除或修改原始消息；
- 仍可使用旧 Checkpoint、裁剪工具输出和最近完整轮次；
- 如果本轮最低预算仍无法满足，向用户返回可操作错误。

## 7. 前缀缓存约束

Provider 的缓存是前缀匹配，不是语义相似匹配。因此上下文构建必须遵守：

1. 稳定系统规则放在最前面，内容不能包含当前时间、随机 ID、Token 用量或本轮动态结果；
2. 工具定义保持稳定顺序和稳定 JSON 序列化；
3. Checkpoint、历史消息按确定性顺序输出，不按每次检索分数重新插入历史主序列；
4. 关键词检索结果只追加在上下文尾部，不能插入稳定前缀或重排最近原文；
5. 当前 Run 的 Agent/Steer、Skill 临时正文、Tool Call 和 Tool Result 追加在尾部；
6. 任务清单是唯一允许位于稳定系统规则之后的动态系统块：它只包含确定性顺序的状态、标题以及阻塞/失败项的有界原因；任务更新通常也伴随新的 Assistant Tool Call / Tool Result，因此不会额外打断已经变化的本轮历史前缀；
7. 不把审计 ID、时间戳、模型名称变化塞进稳定系统正文；
8. 只有发生真正压缩、模型配置或工作区规则变化时才接受前缀后段失效；
9. 不能为了“相关性”每次从历史中重新排序全部消息，否则会让每次请求从很早位置开始失配并增加费用。

目标请求前缀：

```text
稳定系统规则
-> 当前会话固定规则
-> 当前 Checkpoint
-> 已经发送过的历史前缀
```

动态内容：

```text
相关历史块
-> 当前用户消息
-> 本轮模型/工具循环
```

## 8. 当前版本的非目标

- 不引入本地 Embedding 模型；
- 不引入向量数据库或跨项目语义记忆；
- 不把完整 Subagent 对话复制到父 Agent 上下文；
- 不让摘要覆盖原始事实；
- 不把模型 ID、Run ID 或 Tool Call ID作为普通上下文文本发送；
- 不用固定“最近 N 条”替代 Token 预算。

## 9. 验收标准

1. 重启数据库后原始消息、Checkpoint 和关键词索引仍可读取；
2. 压缩后原始历史数量不减少，Checkpoint 覆盖序号只前进；
3. 未超预算时发送全部未覆盖完整历史；超预算时保留最近完整轮并压缩较早轮次；
4. 相关关键词可从已覆盖的旧历史中命中，且不会重复最近原文；
5. 相关历史只出现在动态尾部，不改变稳定前缀和原始消息顺序；
