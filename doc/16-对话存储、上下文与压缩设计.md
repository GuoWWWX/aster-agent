# 对话存储、上下文与压缩设计

启动恢复时，若轻量 `state_checkpoint` 之后存在 `context_checkpoint`，必须从原始 JSONL 分批重放完整历史，再解析压缩覆盖位置；轻量状态没有模型消息，不能直接解析历史边界。此回退不删除或改写原始消息。

协作恢复仍以 JSONL 为准：`conversation_execution_paused` 持久保存用户停止状态；`agent_messages_consumed` 记录消息 ID 与接收 `runId`，不删除原消息。`run_terminal` 先保存真实终态，再向主对话交付回执；消费归属支持恢复尚未回传的后续协作结果。检查点保留停止状态和每轮最多 1,000 字符的结束摘要，完整输出留在原事件中；这些控制事件不进入模型上下文。

已读状态通过 `conversation_result_viewed` 追加到对话 JSONL，按事件顺序恢复；检查点保存当前 `hasUnreadResult`。该事件不进入消息时间线或模型上下文，也不修改旧消息。

Steer 的 `user_message` 写前事件按历史事实幂等恢复：校验对话、轮次及 Pending 归属，但不要求旧轮次仍在运行。启动或缓存淘汰后的懒加载保留轮次终态，不重复注入消息或执行工具；新的实时 Steer 仍必须匹配当前活跃轮次。

> 存储方案阅读入口（2026-09-07）：本文记录迁移中的 JSONL/SQLite 混合存储与上下文合同。最终“完整对话由 JSONL 保存并直接加载”的格式见[JSONL 对话存储与归属设计](./22-JSONL对话存储与归属设计.md)；SQLite 对话投影尚未移除。

> 当前实现补充（2026-09-08）：对话持久化只用 JSONL；模型编译按文件位置读取压缩摘要及未覆盖消息，相关旧内容按需检索，统计读取轻量用量索引，不加载全部正文或回退 SQL。任务清单运行态已改内存 Map，其他运行态仍有 TEMP 投影。本文下方旧 SQL 存储描述仅作迁移背景，现状与限制以第 22 篇 §1、§5 为准。〔FACT｜`thread-log.ts`；`context-compiler.ts`；`agent-database.ts`〕

> 完整 v2 事件合同及五类场景样例见[JSONL 完整事件格式与全场景样例](./23-JSONL完整事件格式与全场景样例.md)，包括持久化实际返回的输出分段、思考摘要、审批和可靠回传；这是后续设计，不代表本文现有实现已覆盖这些事件。

## 1. 目的

待发送内容及顺序继续由 JSONL 保存。队列自动续发许可只在当前 Runtime 内有效，重启后凡有遗留待发送消息均默认暂停，不从历史恢复“继续执行”的授权；用户点击继续后，等待当前或下一次手动 Run 正常结束才消费。此策略不新增 SQLite 对话状态，也不改变已接受 Run 的检查点恢复机制。

本文统一定义 Agent 的四个边界：

1. 用户、Agent、模型和工具产生的内容如何持久化；
2. 长对话如何压缩而不破坏原始历史；
3. 每次模型请求实际可见哪些上下文；
4. 如何在上下文不断变化时尽量保持 Provider 的前缀缓存命中。

本文描述的是运行时合同。UI 展示、Timeline 卡片和模型请求的审计元数据可以使用同一批事实，但不等于模型上下文。

## 2. 术语边界

| 术语 | 含义 |
| --- | --- |
| 完整历史 | SQLite 中持久保存的全部用户消息、Assistant 输出、Tool Call 和 Tool Result |
| 模型上下文 | 某一次 `completeTurn` 实际发送的 `ModelMessage[]` |
| Run | 一次用户需求对应的一次 Agent 执行；一个 Run 可以有多次模型请求 |
| Model Call | Run 内一次语义上的模型请求；用于审计，不发送给模型 |
| Tool Call | 某次模型请求产生的单个工具调用；通过 `tool_call_id` 与结果关联 |
| Context Checkpoint | 对较早历史的结构化增量摘要，以及它覆盖到的消息序号 |
| 任务清单 | 一个 Conversation 的可变工作状态；不是聊天历史，也不是 Checkpoint 的权威来源 |
| 工作记忆 | 当前对话的 Checkpoint、最近原文和当前 Run 状态 |
| 长期记忆 | 跨对话、跨项目主动保存并检索的知识；当前版本不实现通用长期记忆库 |

“滑动窗口”只描述最近原文的保留方式。当前完整方案应称为：

> 基于 Token 预算的分层上下文管理：最近原文窗口 + 增量摘要 + 按需关键词检索。

## 3. 持久化模型

> **迁移状态（2026-09-07）**：新对话立即写入 `<ASTER_HOME>/conversations/<conversationId>/conversation.jsonl`，旧平铺日志自动迁入。常用 Run、消息、工具、Pending 与压缩事件走 JSONL 写前投影；标题、项目/工作区、Agent、模型/思考、权限、归档和置顶追加 `conversation_properties_changed` 完整快照，可在 SQLite 值损坏后恢复。Subagent 跨对话终态、团队关系、列表与全文搜索仍暂用 SQLite 投影。`ContextCompiler` 在日志存在时由 JSONL 重建模型历史；SQLite 投影移除边界见第 22 篇。〔FACT｜`thread-log.ts`；`conversation-lifecycle-service.ts`；`event-projector.ts`〕

> **Aster 目录迁移（2026-09-07）**：管理目录默认使用 `<home>/.aster`，环境变量优先使用 `ASTER_HOME` 并兼容 `AGENT_HOME`。旧管理数据只复制、不删除；原 `conversation-files` 迁移为持久 `attachments`。ThreadLog 规范位置为 `<ASTER_HOME>/conversations/<conversationId>/conversation.jsonl`。

模型自动重试另以 `model_retry_updated` 写前事件追加到 ThreadLog，并幂等更新 SQLite 中同一个 `model_retry` Timeline 项。它是 UI/审计事实，不写入 `model_messages`，因此刷新或重启后仍可见，但不会污染下一次模型上下文。

### 3.1 原始历史永不因压缩删除

`model_messages` 是模型历史的事实来源，至少保存：

```json
{
  "sequence": 42,
  "id": "msg_042",
  "conversation_id": "conv_001",
  "run_id": "run_007",
  "role": "assistant",
  "content": "",
  "tool_calls_json": [
    {
      "id": "tc_009",
      "name": "read_file",
      "arguments": "{\"path\":\"src/login.tsx\"}"
    }
  ],
  "tool_call_id": null,
  "attachment_ids_json": [],
  "provider_state_json": null,
  "created_at": "2026-08-20T10:00:00.000Z"
}
```

`role` 的含义：

- `user`：用户消息，也包括被包装成用户消息的 Agent 协作消息和 Steer 消息；
- `assistant`：模型正文和模型发起的 Tool Call；
- `tool`：工具结果，使用 `tool_call_id` 关联对应调用。

### 3.2 运行和模型元数据不混入上下文

以下信息要持久化用于审计、恢复和 UI 展示，但不作为普通文本发送给模型：

```text
conversation_id
run_id
model_id
model_call_id
attempt_id
provider_request_id
reasoning 配置
权限模式
Token 用量
耗时和重试次数
```

其中：

```text
conversation_id  整个对话
run_id           一次用户需求的 Agent 执行
model_call_id    Run 内一次语义模型请求
attempt_id       同一请求的网络重试
tool_call_id     一次模型请求产生的单个工具调用
```

重试保持同一个 `model_call_id`，只生成新的 `attempt_id`。这些字段属于运行审计，不属于模型可见内容。

当前实现尚未新增 `model_calls` 审计表，也没有为每次 Provider 尝试持久化独立 `model_call_id/attempt_id`。已实现的 `model_retry` Timeline 只按一次语义请求保存最新次数、等待时间、状态和脱敏错误，并以内部稳定请求 ID 关联同一生命周期；它不替代请求级成本审计。Provider 返回的标准化输入、输出、总 Token，以及可选缓存读取/写入 Token，保存在 Assistant `provider_state_json.usage` 中供当前对话的缓存命中展示使用，但不回放给模型。后续若需要逐次 Provider Request ID 或成本审计，再单独增加持久化批次。

### 3.3 Checkpoint

当前会话保存最新的 Context Checkpoint：

```json
{
  "conversation_id": "conv_001",
  "covered_through_sequence": 36,
  "summary": {
    "goals": ["实现登录页"],
    "requirements": ["复用现有组件"],
    "constraints": ["不能修改后端接口"],
    "decisions": ["使用现有表单校验方案"],
    "filesRead": ["src/login.tsx"],
    "filesChanged": ["src/login.tsx"],
    "commands": ["pnpm test"],
    "testResults": ["通过"],
    "errors": [],
    "pendingWork": ["补充异常状态"],
    "taskStatus": ["进行中"],
    "artifactRefs": [],
    "rejectedApproaches": []
  },
  "created_at": "2026-08-20T10:00:00.000Z",
  "updated_at": "2026-08-20T10:00:00.000Z"
}
```

`covered_through_sequence` 只能前进。压缩失败时，原始历史和旧 Checkpoint 都保持不变。

ThreadLog 重放使用对话内从 1 开始的本地消息序号，以便在编辑或废弃 Run 后重新形成连续上下文；SQLite 的 `model_messages.sequence` 是跨对话共享的全局序号。保存 Checkpoint 前，Runtime 必须把 ThreadLog 的本地覆盖位置转换成当前 Conversation 对应的 SQLite 全局序号，不能直接把两种序号混用。`context_checkpoint` 事件同时保存本地覆盖位置，重放时只覆盖实际参与摘要的旧前缀，不能把仍需原文保留的最近轮次一起标记为已覆盖。

### 3.4 UI 历史、Timeline 和模型上下文分离

```text
model_messages       模型历史事实
conversation_timeline UI 展示、工具卡片、审批、Diff 和状态
conversation_turn_summaries 每个已完成 Run 的隐藏结构化轮次摘要（可再生成的 SQLite 加速数据）
context_checkpoint   历史压缩结果
LangGraph Checkpoint 当前 Run 的可恢复图状态
```

压缩不删除 Timeline 或 `model_messages`。供应商主动返回的完整 `reasoning content` 只作为 Assistant Timeline 的可选展示字段持久化，不写入 `model_messages.content`，因此不会被当作普通模型正文参与检索或压缩；实时 `reasoning summary` 和面向用户的短进度不要求持久化。不可读的推理签名、加密内容和工具调用签名属于 Provider State，不参与正文检索、摘要压缩或界面展示；新 Run 编译历史上下文时，只有仍保留完整 Tool Call/Tool Result 对应关系的 Assistant 工具回合，才在 API 格式、地址和模型均匹配时原样重放该状态，已经形成最终回复且没有工具调用的 Assistant 不再携带旧推理状态。Run 结束后，LangGraph 的临时线程状态按现有生命周期清理；可追溯事实仍在 SQLite 中。

### 3.5 侧边聊天的临时上下文快照

侧边聊天是父对话右侧工作区中的临时 Conversation，不进入左侧对话树。创建时复制父对话当前有效模型上下文：无 Checkpoint 时复制全部模型消息；有 Checkpoint 时复制摘要、覆盖边界的最后一条消息作为新 Checkpoint 锚点，以及边界之后的未覆盖消息。锚点不会进入模型请求，因此模型实际看到的是“摘要 + 未覆盖消息”。源对话的 Timeline 和后续消息不随之复制或同步。

侧边聊天仍使用独立 SQLite 记录和 ThreadLog JSONL，以保证打开期间的正常运行与恢复。用户关闭其页面标签即发起可恢复删除，成功后删除 Conversation、运行数据、无共享引用的附件和对应 JSONL；删除失败时保留标签并等待重试。

### 3.6 Subagent 的隔离上下文

Subagent 与父对话只保留 `parentConversationId` 和任务生命周期关系。创建时不复制父对话的 `model_messages`、Context Checkpoint、Timeline 或附件引用；首条模型可见用户消息是 `spawn_subagent.task`。父 Agent 如果需要委派上下文，必须把必要事实、约束和验收条件显式写入任务。该规则不影响 3.5 中普通侧边聊天的创建时快照继承。

一轮完成后，父 Agent 的返工消息继续投递到同一个 Subagent Conversation，并在该对话创建新的 Run；因此子对话已形成的稳定系统前缀、历史和 Checkpoint 可以继续参与上下文编译，也具备 Provider 前缀缓存复用的条件。系统不承诺供应商一定命中缓存，但不得为了返工重新创建空白 Subagent。Main Agent 显式 `end_subagent` 后才把子对话转为只读，用户删除才移除其持久历史。

## 4. 每次模型请求的上下文

模型请求不是“把整个会话重新发一遍”，而是每次由 Context Builder 按预算重建 `ModelMessage[]`。逻辑顺序如下：

```text
1. 稳定系统指令、会话/工作区/权限等固定运行规则
2. 最新 Context Checkpoint（如果存在）
3. Checkpoint 未覆盖的按时间顺序排列的完整消息，但暂不放入最新用户回合
4. 按当前请求检索到的相关旧历史（动态尾部）
5. 最新用户回合
6. 本次 Run 内新增的 Agent/Steer 消息、Assistant Tool Call 和 Tool Result
7. 当前 Run 已激活的 Skill 指令（如有；临时用户运行上下文尾部）
8. 当前有效任务清单（如有；临时用户运行上下文尾部）
```

工具定义通过 `tools` 参数单独发送，不伪装成聊天消息。

Runtime 自己维护的稳定系统规则、动态上下文包装文本和 Tool Schema 使用简洁英文；用户消息、历史事实以及 Agent/Skill 自定义正文保持原文。长而稳定的基础系统 Prompt 和压缩 Prompt 保存为 `main/agent/prompts/*.md`，由 tsup 在构建阶段作为文本内嵌；运行时不读取源码目录。TypeScript 继续组合动态身份、权限、工作区、能力和预算，Tool Schema 继续与工具合同共置。输出语言由稳定系统前缀中的独立英文规则指定。当前应用仅支持 `zh-CN`，所以规则要求模型默认使用简体中文；用户明确要求其他语言时可以覆盖。这样提示层语言和用户可见回复语言彼此解耦，也不需要在发送前翻译历史内容。

在运行时实现上，`LangGraphExecutor` 的 `beforeAgent` Middleware 在一个 Run 的 Graph `thread_id` 首次进入时调用 Runtime `prepareContext`，把稳定系统内容、Checkpoint 和未覆盖历史写入图状态。图状态中的 `contextPrepared` 防止同一 Run 的审批恢复或 Queue/Steer 追加重复注入历史；这些新增输入仍由每轮 `beforeModel` 在安全边界消费。**已激活 Skill 正文和任务清单都在 `beforeModel` 作为临时 `user` 运行上下文追加到稳定历史和当前 Run 消息之后，只送入当次 Provider 请求，不写回 LangGraph `messages`。** 因而 Skill 加载集合或任务状态改变只影响请求尾部，不会打断前面的稳定系统规则、Checkpoint 和完整历史缓存。单个 Run 内累积消息超过当前编译预算时，`beforeModel` 会在工具批次结束后的安全边界重新编译 Context；LangGraph 以新 Checkpoint 和保留尾部整体替换旧累积消息，避免摘要与被摘要的全文同时发送。〔FACT｜`apps/desktop/src/main/agent/agent-runtime.ts`；`apps/desktop/src/main/agent/langgraph-executor.ts`；`apps/desktop/src/main/agent/task-list-context.ts`〕

Steer 的 Timeline 正文保持用户原文；进入模型历史的 `modelContent` 会在原文前附加 Runtime 承接说明，明确当前请求尚未完成，并要求模型结合原请求、已有 Assistant/Tool 结果判断新消息是补充、纠正、替换还是新的优先事项。明确纠正、替换或冲突时以后到消息为准；否则继续仍适用的未完成工作或清楚说明剩余项。该说明随 Steer 的模型消息一起持久化，因此后续轮次和上下文重建仍保留这次承接语义，但不会污染用户可见消息正文。

### 4.1 任务清单的动态上下文合同

任务清单由 `update_task_list`、`close_task_list` 操作；更新时不存在则创建，存在则更新，并按 `conversationId` 保存；UI、恢复和查询仍使用其持久化事实，但模型不把 `task_list_updated` 事件或旧 Tool Result 当作状态来源。每次模型调用使用当前的 active list，按原有任务顺序只序列化 `status + title`，并且只为 `blocked`、`failed` 项追加经截断的 `reason`：不包含任务 UUID、`createdAt`、`updatedAt` 或 Run ID，以避免无意义的缓存失效。

任务清单工具成功后只向模型返回 `updated + taskCount` 或 `closed` 确认；完整清单通过下一次 `beforeModel` 的动态尾部提供。工具结果不重复携带任务 UUID、时间戳和所有标题，UI 仍直接使用持久化的完整 `ConversationTaskList` 事实。

`ContextCompiler` 只为**当前存在且 active 的**任务清单按实际序列化内容预留 Token；不存在或已关闭的清单预留为零，不能为了尚未创建的计划提前挤占历史预算。每项标题在模型块中最多 120 个字符，阻塞/失败原因最多 240 个字符，持久化原值不改；任务工具创建或更新清单后，下一次 `beforeModel` 仍重新读取并注入当前版本。该尾部消息带有明确的 Runtime 包装语义，不代表用户新增了聊天输入，也不会出现在用户可见历史中。〔FACT｜`apps/desktop/src/main/agent/task-list-context.ts`；`apps/desktop/src/main/agent/agent-runtime.ts`；`apps/desktop/src/main/agent/context-compiler.ts`〕

```json
      "content": "当前会话工作区、权限和任务状态"
    },
    {
      "role": "system",
      "content": "较早历史的结构化摘要"
    },
    {
      "role": "user",
      "content": "最近一轮用户消息"
    },
    {
      "role": "assistant",
      "content": "最近一轮模型回复"
    },
    {
      "role": "system",
      "content": "根据当前请求检索到的相关旧历史"
    },
    {

    }

```

上面是逻辑结构；Provider Adapter 会将其转换为 OpenAI、Anthropic 或 Gemini 的原生请求格式。已发送图片在持久历史里始终表示为包含附件名称、ID 和来源的稳定文字引用；当前最新用户输入另在请求尾部追加一次带原图数据的临时用户消息，确保模型仍能看图，而下一轮不需要改写原历史消息。运行中到达的 Steer 图片遵循相同规则。该转换只影响模型上下文视图，不修改 SQLite、ThreadLog、Timeline、原附件文件或用户可见消息；当前图片无法被模型接收时保留真实错误，不能假装文本模型读取过图片。

原图消息由 `CompiledContext.transientMessages` 单独返回，并通过 `beforeModel.contextMessages` 注入当次请求；它不进入 LangGraph `messages` 或执行图 Checkpoint。工具循环中原图持续位于尾部，下一次用户输入后可移除而不改动前面的工具历史。只查询用量时不读取图片字节，但保留相同图片 Token 估算，避免预览预算低于实际请求。

### 4.1 跨 Agent 回执与按需读取

持久 Agent 的执行对话是完整事实来源。`send_agent_message(expectReply=true)` 建立一次完成回执关系；接收方用单独一行 Markdown `---` 分隔回执和详细结果，Run 结束时只向发送方模型历史写入分隔线前最多 1000 字符、执行 Conversation ID 和原协作消息 ID。成员的完整 Assistant 最终回答、工具结果和过程仍只保存在成员对话，不复制到 Team Lead 或其他调用方上下文。临时 Subagent 对复杂任务使用同一“完成回执 + 分隔线 + 详细内容”结构，Runtime 向父 Agent 隐藏投递分隔线前最多 2000 字符；简单短答不强制分隔，旧输出未分隔时使用同一长度上限兜底。发送方需要更多证据时先用 `list_agent_conversations` 判断状态，再调用 `read_agent_conversation(maxTokens, query?, runId?, beforeSequence?, historyScope?)`；该工具也允许当前 Agent 查询自己的持久历史。`maxTokens` 默认 4096，允许 256–12288。`historyScope` 默认 `compressed`：存在最新 Checkpoint 时，只在 `coveredThroughSequence` 及之前的原始 JSONL 消息中检索；没有 Checkpoint 时自动回退到全部历史；显式传 `all` 时查询整条持久历史。压缩仅改变后续模型上下文装配，不删除这些原始消息。提供 `query` 时直接检索 JSONL，不使用 SQLite FTS。命中轮次能放下时保留完整上下文；超出预算时优先保留该轮最近消息和最终回答，较早内容通过游标继续读取。单条超长消息仍是带截断标记的摘录，不是全文导出。无命中或省略 `query` 时回退到同范围的有界快照。返回的 `pagination.hasMore=true` 时，将 `pagination.nextBeforeSequence` 作为下一次 `beforeSequence` 继续读取较早内容；游标依据实际选入消息生成，不能把被预算排除的整轮内容标记为已返回。指定 `runId` 时读取该轮原文、忽略压缩边界，续读保留原 `runId/query`。该工具可以在目标仍运行时执行，且不会绕过 Token 预算完整复制对话。回执分隔和限长不修改执行对话原文，也不创建第二份 Timeline。〔FACT｜`apps/desktop/src/main/agent/conversation-reference.ts`；`agent-communication-tool.ts`〕

查询当前对话时省略 `conversationId`，Main 直接绑定调用者自己的 Conversation；查询其他对话时才传目标 UUID。

## 5. 消息选择规则

### 5.1 没有超过预算时

如果系统指令、工具定义、附件、输出预留、Checkpoint 和未覆盖历史全部能放入阈值，则发送全部未覆盖历史，不人为按固定条数截断。

```text
稳定系统上下文
+ 当前运行上下文
确有 Checkpoint 时：+ Checkpoint
+ Checkpoint 之后的全部原始消息
+ 相关历史动态块（有命中时）
```

### 5.2 超过预算时

顺序固定为：

1. 旧的超长 Tool Result 先保留开头、结尾、错误/警告行，并标记已裁剪；
2. 最近约两次用户发起的完整对话轮优先保留；
3. 更早且尚未覆盖的完整轮次作为压缩候选；
4. 压缩成功后，用新 Checkpoint 代表候选前缀；
5. 重新按剩余预算从最新完整轮次向前选择；
6. 任何时候都不拆开 Assistant Tool Call 与对应 Tool Result。

压缩请求本身采用三级信息密度：已有 Checkpoint 代表很久以前的历史；待合并的中间轮次优先使用每个已完成 Run 的隐藏结构化轮次摘要；最近两次用户发起的轮次不进入摘要请求，继续以完整原文保留。轮次摘要按整轮同时概括输入、Assistant 结果和必要工具证据，并明确标记 `[User input]`、`[Steer input]`、`[Agent input: 来源]`、`[Assistant result]` 与 `[Tool evidence]`，不能把其他 Agent 或工具内容改写成用户要求。摘要模型门槛按本轮存在的来源动态计算：单一有效来源的单项门槛约 448 tokens，每多一种来源下降约 48 tokens，最低 320 tokens；整轮总量上限是当前单项门槛的两倍。越过任一门槛时，在 `run.finished` 之后异步追加一次无工具的短摘要请求，不阻塞用户看到本轮完成；边界内的小幅波动仍直接本地封装，不额外调用模型。本地封装会压平空白并把每个字段限制在 720 字符内；本来已经足够短的内容不会被再次改写。轮次摘要不在 Timeline 展示，也不替代原始历史；它是后续压缩的可再生成加速数据。

这里的“最近两轮”是保护下限，不是固定最终条数。最终结果由 Token 预算决定：

```text
可用历史预算
= 压缩阈值
 - 系统内容
 - 工具定义
 - 输出预留
 - Skill 正文预留
 - 可变任务清单预留
 - Checkpoint 摘要
 - 附件和相关历史动态块
```

### 5.3 已有 Checkpoint 时

```text
covered_through_sequence = 36

序号 1..36   原始记录仍在数据库，但由 Checkpoint 代表
序号 37..N   作为新的原始上下文候选
```

如果旧序号 1..36 中有与当前请求高度匹配的事实，关键词检索可以把它作为动态相关历史重新带回本次请求；这不会改变 Checkpoint 覆盖范围。

### 5.4 相关历史检索

当前不依赖 Embedding 模型。请求文本中的以下内容作为关键词：

- 文件路径；
- 函数、类、变量和工具名；
- 错误码和命令；
- 英文、数字、路径和标识符词；
- 中文连续文本拆成有限的二/三字符片段，避免把整句当成一个不可命中的词；
- 两个字符的中文或短标识符使用 `LIKE` 兜底，检索文本同时包含消息正文和 `tool_calls_json`。

检索约束：

1. 默认只检索当前 `conversation_id`；
2. 排除已经位于最近原文窗口的消息，避免重复；
3. 路径、错误码、数字或大小写/下划线标识符以及较长中文原句优先保留为高辨识度词；SQLite FTS5 再按 BM25 和时间取得最多请求上限四倍、且不超过 100 条的有界候选。候选按高辨识度精确命中和实际命中词数做强匹配过滤、排序；没有高辨识度精确命中且查询词超过两个时，至少命中两个词，并随查询词数量提高门槛，避免一个普通词把无关旧消息带回；
4. 命中消息格式化为一个独立的“相关历史”动态块，插在稳定历史之后、最新用户回合之前，确保模型回答当前问题前已经看到引用事实；
5. Runtime 单次最多接收 24 条强匹配结果，Context Manager 最多注入 12 条、12,000 字符；相关历史有独立 Token 上限，超限时直接减少命中，不影响当前请求和最近原文；
6. 相关历史计入 `estimatedReferenceTokens`，与跨对话/项目引用使用同一用量口径；
7. 检索结果只影响本次请求，不写入聊天 Timeline，不伪装成新的用户消息。

这样即使摘要没有保留某个早期具体路径，也可以按当前问题把原始事实临时取回。

## 6. 压缩维护

### 6.1 增量压缩

压缩只处理尚未进入 Checkpoint 的较早前缀，不每轮重新总结整个会话：

```text
第 1..18 条 -> checkpoint-001，covered_through_sequence=18
第 19..35 条增长后
旧摘要 + 第 19..若干条 -> checkpoint-002，covered_through_sequence=35
```

生成摘要使用严格 JSON 字段，至少保留目标、要求、约束、决定、文件、命令、测试、错误、未完成事项、附件引用和被否定方案。

每次真正压缩仍由摘要模型把“旧 Checkpoint + 中间轮次摘要（缺失时回退完整轮次）”合并、去重并处理跨轮相关性，而不是机械拼接。第一次失败会缩小到更少的完整轮次再试，不能拆开一个 Run；手动强制压缩会继续逐级缩小旧前缀，直到某个完整前缀成功或只剩单轮仍失败。当前未完成任务、最近保护轮次，以及压缩期间新到达的 Steer/Agent 输入始终位于覆盖边界之外；普通任务内的自动压缩结束后由原 Run 消费，独立手动压缩则在完成后启动后续 Run 消费。

压缩属于短结构化整理任务：对协议明确支持关闭推理的模型使用 `reasoning=none`，其他模型保持其兼容默认值；输出最多 2,048 tokens，并要求完整 JSON 控制在约 1,800 tokens 内。这样避免把普通 Agent 的高推理档位原样用于摘要，同时不改变用户当前选择的正常回答推理强度。

摘要解析成功不等于压缩已经成功。只有 SQLite Checkpoint 与 ThreadLog 写前事件均成功持久化后，才累计“已压缩消息数”并向界面报告完成；模型、解析或持久化任一步失败时计数不得提前增加，失败活动应保存脱敏错误分类以便排障。

自动超过阈值与用户输入 `/compact` 共用该流程。手动触发忽略“尚未达到自动阈值”这一条件，但仍只选择最近两轮之前的完整轮次；没有符合条件的旧轮次时不调用压缩模型，也不创建空 Checkpoint。`/compact` 的用户可见操作保留在 Timeline，但作为 Runtime Control Message 从后续模型上下文中过滤。压缩生命周期另以 `runtime_activity_updated` 写入 ThreadLog，并幂等投影成名为 `compact_context` 的 Timeline-only Activity：它可以复用 Tool 形状的状态合同，但不产生 Assistant Tool Call 或模型可见 ToolMessage。Renderer 将运行中、完成、失败和暂停分别显示为居中的说明分割线；运行中显示实时耗时，终态继续直接显示本次压缩最终耗时，完成文案只显示“已压缩”，处理条数放入文字悬停提示，压缩运行期间不再同时显示普通的“已处理”计时分割线。失败和暂停文案只陈述压缩终态，不在界面中推断原始记录是否受影响，真实错误也只在文字悬停提示中展示。失败后的“强制压缩”和手动暂停后的“继续压缩”都以单个重试图标呈现，操作含义由悬停提示和无障碍名称提供。用户一旦发送其他新消息，该入口即消失，避免对已经变化的上下文执行旧操作。

手动压缩被停止时不回滚已经成功写入的增量 Checkpoint，也不把它提升为新的 Run 状态；当前 `/compact` Run 仍以 `cancelled` 终止，Runtime Activity 通过 `trigger=manual` 将其解释为可续做的“暂停”。此时压缩期间收到的 Queue、Steer 和未读 Agent 输入保持持久等待，不能由 `finally` 自动启动。继续压缩会重新编译最新 Checkpoint 之后的候选前缀；若上一段已经落盘就从下一段开始，若停止发生在模型尚未形成有效摘要时则安全重做该段。全部压缩完成后，Steer 优先于 Queue 进入后续模型 Run。

### 6.2 不压缩时

没有达到阈值时，不生成 Checkpoint；Context Builder 直接使用当前已有 Checkpoint（如有）和未覆盖的原始消息。

因此“没有发生压缩”有两种正常状态：

- 没有旧 Checkpoint，且全部历史放得下；
- 已有旧 Checkpoint，但 Checkpoint 之后的新消息尚未达到下一次压缩阈值。

### 6.3 压缩失败

压缩模型返回非法 JSON、请求失败或被取消时：

- 不移动 `covered_through_sequence`；
- 不删除或修改原始消息；
- 仍可使用旧 Checkpoint、裁剪工具输出和最近完整轮次；
- 如果本轮最低预算仍无法满足，向用户返回可操作错误。

## 7. 前缀缓存约束

Provider 的缓存是前缀匹配，不是语义相似匹配。因此上下文构建必须遵守：

1. 稳定系统规则放在最前面，内容不能包含当前时间、随机 ID、Token 用量或本轮动态结果；
2. 工具定义保持稳定顺序和稳定 JSON 序列化；
3. Runtime 固定系统文本和 Tool Schema 使用英文；输出语言规则同样用英文表达，并把当前应用语言作为稳定值写入前缀；
4. Checkpoint、历史消息按确定性顺序输出，不按每次检索分数重新插入历史主序列；
5. 关键词检索结果只放在稳定历史之后、最新用户回合之前的动态尾部，不能插入稳定前缀或重排既有历史；
6. 当前 Run 的 Agent/Steer、Tool Call 和 Tool Result 按发生顺序追加；已激活 Skill 的临时正文作为 `user` 运行上下文放在请求尾部，加载集合变化只能使该动态尾部之后失配；
7. 任务清单只包含确定性顺序的状态、标题以及阻塞/失败项的有界原因，并作为临时 `user` 运行上下文放在当次请求末尾；任务更新或关闭时只改变尾部，不能打断稳定系统规则、Checkpoint、历史消息和本轮已有工具结果组成的长前缀；
8. 超过模型侧长度上限的 Tool Result 从第一次进入 Provider 请求起就使用同一套确定性头部、错误行和尾部摘要；完整结果只保留在本地 Timeline/ThreadLog，不能等到后续压缩时才改变历史表示；
9. 不把审计 ID、时间戳、模型名称变化塞进稳定系统正文；
10. 只有发生真正压缩、模型配置或工作区规则变化时才接受前缀后段失效；
11. 不能为了“相关性”每次从历史中重新排序全部消息，否则会让每次请求从很早位置开始失配并增加费用。

单个 Run 内的模型/工具循环也受同一预算约束。每次新模型调用前，Runtime 以初始编译请求为稳定基线，加上 Skill、任务清单预留和真实剩余上下文空间计算允许增长量；越界时先完成当前工具批次，再在模型调用安全边界重新编译。若同一用户轮次已有至少两组完整 Tool Call/Tool Result，较早工具迭代可以进入增量 Checkpoint，最新工具迭代继续保留原文，且任何时候都不拆开调用与结果。

重新检查以单调增长的模型回合号去重，不能使用压缩后会减少的消息数量。单个 Run 的待摘要前缀超过摘要输入预算时，按完整工具迭代分批；该 Run 的摘要失败时也可缩小为更少的完整迭代重试，不能因为只剩一个 Run 就放弃所有缩批机会。

Provider 返回的最近和累计 `cachedInputTokens`、`cacheCreationInputTokens` 与命中率是缓存效果的诊断依据。这些数据只保存在本地用量记录并由界面读取，不能写回系统提示或历史消息，否则诊断本身会破坏待诊断的缓存前缀。

缓存明细漏报时，底栏保留同一 `apiFormat + baseUrl + modelId` 上次有效值并标为“上次命中率”，输入/输出 Token 仍显示最近请求；真实 0% 或低命中率直接更新。平均值仅按有缓存明细的输入 Token 加权，不以 90% 为保底。

OpenAI Chat/Responses、Anthropic 的实际 HTTP 请求在兼容转换后生成本地 `providerState.payload.requestFingerprint`：请求整体、独立系统字段、工具、模型参数及前 32 条消息的 SHA-256，另存请求字节数和消息数。单次记录小于 3 KB，超过 4 MiB 或非字符串请求不采集；Gemini SDK 未经过该 fetch 边界，暂不采集。指纹不含原文、请求头或密钥，不回放给模型，也不修改原请求。比较相邻记录可定位本地前缀变化；指纹不是供应商缓存键，不能反推服务端缓存命中，更不能据此承诺 90% 以上。

目标请求前缀：

```text
稳定系统规则
-> 当前会话固定规则
-> 当前 Checkpoint
-> 已经发送过的历史前缀
```

动态内容：

```text
相关历史块
-> 当前用户消息
-> 本轮模型/工具循环
-> 当前 Skill 正文
-> 当前任务清单
-> 当前用户图片原图（仅本次请求）
```

## 8. 当前版本的非目标

- 不引入本地 Embedding 模型；
- 不引入向量数据库或跨项目语义记忆；
- 不把完整 Subagent 对话复制到父 Agent 上下文；
- 不让摘要覆盖原始事实；
- 不把模型 ID、Run ID 或 Tool Call ID作为普通上下文文本发送；
- 不用固定“最近 N 条”替代 Token 预算。

## 9. 验收标准

1. 重启数据库后原始消息、Checkpoint 和关键词索引仍可读取；
2. 压缩后原始历史数量不减少，Checkpoint 覆盖序号只前进；
3. 未超预算时发送全部未覆盖完整历史；超预算时保留最近完整轮并压缩较早轮次；
4. 相关关键词可从已覆盖的旧历史中命中，且不会重复最近原文；
5. 相关历史只出现在稳定历史与最新用户回合之间的动态尾部，不改变稳定前缀或既有历史顺序；
6. 工具调用与结果的 `tool_call_id` 关系在裁剪、压缩和重放后仍有效；
7. 模型请求快照可验证稳定前缀、Checkpoint、原始历史、相关历史和本轮新增消息的边界。
