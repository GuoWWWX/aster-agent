# 多 Agent 团队与任务调度设计

> 文档状态：核心能力基线  
> 更新时间：2026-08-30
> 关联文档：[AI Agent 产品与技术方案总览](./00-AI-Agent产品与技术方案总览.md)、[第一阶段需求与验收标准](./01-第一阶段需求与验收标准.md)

## 1. 目标

产品需要支持一个长期存在的 AI 团队。用户可以持续把想法、问题和任务投递给团队负责人，不必每次先决定该找哪个 Agent。团队负责人负责：

- 接收并澄清任务。
- 判断任务使用单成员短路径还是多成员协作。
- 选择已有 Agent，或按需创建临时 Agent。
- 管理任务依赖、并发、权限、进度和失败恢复。
- 汇总各 Agent 的结果，并对最终交付负责。

团队不能为了“看起来像组织”而让全部岗位同时运行。普通主对话仍可直接完成简单任务；任务一旦明确交给默认团队，Team Lead 至少委派一位最匹配的持久专业成员，只有可分解、可并行或确实需要不同能力/权限时才增加参与成员。

## 2. 主流方案中的可用设计点

### 2.1 管理者保持最终所有权

OpenAI Agents SDK 区分两种模式：

- `handoff`：把当前分支的对话所有权交给专业 Agent。
- `agent as tool`：管理者把专业 Agent 当成有边界的能力调用，最终回答仍由管理者负责。

本产品默认使用第二种。团队负责人始终拥有用户任务和最终交付，临时 Agent 返回结构化结果。只有用户明确进入某个常驻 Agent 的持续对话时，才使用类似 handoff 的体验。

### 2.2 临时 Subagent 与协作团队分开

Claude Code 将两者区分为：

- Subagent：独立上下文完成一个支线任务，返回摘要，适合搜索、调查、验证和单次实现。
- Agent Team：多个独立会话通过共享任务列表和 mailbox 协作，适合真正并行且需要互相沟通的工作。

这一区分适合本产品。不能把每次文件搜索都升级成完整团队，也不能把需要多轮协作的长期任务塞进一次性工具调用。

### 2.3 共享任务列表必须有依赖和领取机制

Claude Agent Teams 使用 `pending`、`in progress`、`completed` 状态、任务依赖和原子领取；AutoGen 的 Selector Group Chat 使用 Agent 名称、职责描述和当前上下文选择下一位执行者，并要求明确终止条件和最大轮次。

本产品采用持久化任务图和任务租约，不采用无限自由群聊。Agent 可以互发消息，但真正决定进度的是任务状态、依赖、交付物和验收结果。

### 2.4 角色描述用于候选匹配，不用于制造组织层级

AutoGen 会根据参与者的名称和职责描述选择下一位 Agent，也支持先用候选函数缩小范围，再让模型选择。这个两阶段思路比“把所有 Agent 全塞给模型选择”更稳定：

1. 代码先按项目权限、工具、能力、状态和预算过滤候选。
2. 评分器或模型在少量候选中选择，并记录理由。

### 2.5 团队规模必须受控

Claude Code 官方文档指出，多 Agent 的 Token 成本随活跃成员增长，协调开销和文件冲突也会增加，普通任务使用单会话更划算。其建议通常从少量成员开始，只在工作确实可并行时扩容。

本产品不允许 Agent 无限递归招募。MVP 只有团队负责人能创建或停止 Worker；Worker 可以建议增员，但不能自行再创建团队。

## 3. 推荐组织模型

```text
AI Team Instance（用户显式创建、长期存在）
├─ Scope（global / project / conversation）
├─ Team Lead（唯一负责人；在实例内复用持久执行对话）
├─ Team Inbox（持续接收用户任务）
├─ Project Registry（团队可服务的项目）
├─ Agent Profiles（可复用能力定义）
├─ Standing Agents（可休眠的常驻成员）
└─ Work Items
   └─ Tasks / Task DAG
      ├─ Short path（Team Lead + 1 位专业成员）
      ├─ Ephemeral Subagent（仅普通 Agent 的一次性支线）
      └─ Coordinated Workers（持久 Agent 对话与消息协作）
```

### 3.1 Team Lead

团队只有一个主负责人身份。团队设置中的 Team 只是创建模板，实际工作必须由用户或界面先显式创建 `TeamInstance`。实例分为全局、项目和对话三种作用域；WorkItem 通过 `teamInstanceId` 精确选择一个可见实例，不能根据模板、项目或来源对话静默派生新实例。Team Lead 在实例内保存团队级配置、当前优先级和任务总览，WorkItem 仍是独立的调度、来源审计和验收单元，并在实例执行根上串行执行，避免两个工作项混淆当前运行策略。默认开发团队的 Team Lead 不替代专业成员实现：每个 WorkItem 至少向一位持久成员发出 `expectReply=true` 的任务，简单任务只走一位成员的短路径，主要负责：

- 任务澄清和项目绑定。
- 拆分任务并定义验收标准。
- 分配或回收任务。
- 处理冲突和阻塞。
- 汇总交付，不代替用户批准高风险操作。

### 3.2 Ephemeral Subagent

临时 Subagent 服务于一个有边界的任务，完成后释放模型和进程资源，但保留独立 Agent Thread、用户可见消息、工具与审批事件、摘要和 Artifact。典型场景：

- 搜索代码并定位实现。
- 调查某个错误的可能原因。
- 独立做安全、性能或测试审查。
- 在隔离工作区完成一个明确文件集合的修改。

### 3.3 Standing Agent

常驻 Agent 是可持续对话、可多次接单的成员，但空闲时不占用模型或进程资源。它保留：

- 稳定的 Agent Profile。
- 与项目隔离的长期摘要和经验。
- 已完成任务、能力表现和用户反馈。
- 可恢复的 Agent Thread。

不在初始化时创建完整岗位表。某类临时 Agent 被多次使用且持续产生价值后，用户或负责人才能建议将其转为常驻成员。

### 3.4 Agent Profile 与 Agent Instance 分离

- `AgentProfile`：职责、能力标签、允许工具、模型策略、Skill、输出合同和适用项目范围。
- `AgentInstance`：一次实际运行或一个可恢复的常驻成员实例。

“招聘”本质是从模板生成或复用 Profile，再启动 Instance，不是动态生成无约束的系统提示词。

### 3.5 最小角色策略

默认开发团队固定六个易理解的岗位，但任务到来时只激活必要成员：

- `Team Lead`：分诊、调度、验收和汇总，不替代专业成员实现。
- `需求分析师`：澄清范围、非目标和验收条件。
- `架构师`：定义最小技术方案、接口边界和风险。
- `前端开发`：负责界面、交互、前端状态和对应测试。
- `后端开发`：负责运行时、接口、数据、工具和持久化。
- `测试工程师`：独立核对验收条件、回归风险和测试证据。

简单任务由 Team Lead 选择最匹配的一位成员并等待结果；常规任务按需要串联需求或架构、开发和测试；只有跨端或可并行工作才同时调度前后端。用户自定义团队仍可采用其他岗位组合，发布复核等专用团队不必复制这六个角色。

### 3.6 Agent 逻辑对话与模型

每个 Team Lead、持久团队成员和临时 Subagent 都有独立的逻辑对话 Thread。它是 SQLite 中的对话与事件归属，不是独占的 OS 线程、Node `worker_threads` 或进程。创建 TeamInstance 时建立该实例自己的 `team_lead` 根 Thread 和配置成员的持久 `agent` Thread；全局实例可被任意项目主对话选择，项目实例只对同项目主对话可见，对话实例只对所属来源对话可见。后续 WorkItem 始终复用所选实例的身份与消息谱系。Team Lead 通过 `send_agent_message` 与 `wait_for_agent_message` 分派、等待和汇总，成员消息与任务分派记录共同构成可审计事实；团队内禁止把成员创建为 `subagent_tasks`。团队面板只读取这些持久关系和消息分派，不嵌入或复制成员 Timeline。用户点击成员时，成员消息、工具、审批、Artifact 和结果使用其原生 Conversation；运行中的输入只可作为同一 Run 的 `steer`，不能更换 Agent 或开启一个独立 Run。没有运行的成员要继续工作时使用 WorkItem 的返工/验收流程。临时 Subagent 完成后 Thread 仍可查看；用户继续对话时创建新 Run，不修改历史 Run。〔FACT｜`apps/desktop/src/main/teams/team-work-item-runtime.ts`；`apps/desktop/src/main/agent/agent-runtime.ts`；`apps/web/src/features/workspace/right-sidebar-workspace.tsx`〕

持久 Agent 的“完整对话”和“跨 Agent 回执”是两个边界：成员在最终回答开头按 `replyInstruction` 写简述，以单独一行 Markdown `---` 分隔详细结果；完整回答只写入成员 Thread，`expectReply=true` 仅向发送方投递分隔线前最多 1000 字符的完成回执、终态和成员 Conversation ID。发送方可随时用 `list_agent_conversations` 查看成员状态，并按自己选择的 `maxTokens` 调用 `read_agent_conversation` 取回运行中或已完成成员对话的有界快照。回执、状态查询和主动读取都不创建第二份成员 Timeline，也不把完整成员输出复制进 Team Lead 上下文。

左侧“团队”分组统一列出用户创建的全局实例和项目实例；项目实例在团队名后显示其关联项目的当前名称。团队分组的创建入口允许选择“不关联项目”或一个已注册项目。项目三点菜单提供“在项目中显示团队”开关，默认关闭；开启后项目实例才会作为同一数据的快捷入口出现在该项目普通对话列表中。对话实例继续直接显示在来源对话展开后的协作树中，不增加“对话团队”中间目录。项目标题行和普通对话的悬浮操作仍可分别创建项目实例和对话实例。实例默认采用模板名，重名自动追加 `(1)`、`(2)`，并支持重命名、归档和删除。全局/项目实例的团队名行支持持久化自定义排序，单击团队名只展开或收起成员；选中态只属于实际打开的成员 Conversation。全局/项目实例直接展示模板中的全部成员；对话实例只展示已经被该实例 WorkItem 实际启用的成员。成员行打开实例自己的原生持久 Conversation，不创建 WorkItem 或 Run，也不复制 Timeline。`@实例名` 只列当前对话可见的真实实例；模板本身不出现在投递菜单，投递也绝不自动创建实例。

空闲 Agent 不占用模型连接、执行线程或子进程。任务到来时才创建 Run，由共享异步调度器和受限 Worker/进程池执行；Agent 数量因此不直接受 CPU 线程数限制，活动 Run 数量则受内存、供应商限流、工具进程和用户预算共同约束。

Agent 模型默认继承创建它的父对话当前模型，也可以由 Profile、创建请求、ModelRouter 或用户指定。当前 Main Agent 可先调用 `list_models` 获取不含凭据的已配置模型目录、已启用思考选项和带时间的健康状态，再向 `spawn_subagent` 显式传入 `providerId`、`modelId` 和可选思考选项；未传时保持继承。Subagent 的选择不反向更新“最近一次用户选择”。用户通过对话或模型选择器的明确设置具有最高优先级；自动路由不能解除用户锁定。完整规则见[模型接入、MCP、Skill 与 Agent 对话设计](./08-模型接入、MCP、Skill与Agent对话设计.md)。

`spawn_subagent` 还接受独立于任务正文的简短 `name` 和可选 `icon`。`icon` 只能使用 Agent Profile 共用的稳定枚举；未提供时优先使用所选 Agent 的预设图标，否则按子 Conversation ID 选择稳定回退。名称和图标进入子对话身份投影，便于在父对话树和工具结果中区分并行 Subagent。

## 4. 任务分级与是否组队

当前主对话先判断是否需要交给团队；进入默认团队后，Team Lead 再选择最短可验证路径。

| 模式 | 适用条件 | 执行方式 |
| --- | --- | --- |
| 主对话直接模式 | 用户没有交给团队，且范围明确、步骤连续、修改集中 | 当前主 Agent 完成 |
| 团队短路径 | 已交给默认团队，但只需一种专业能力 | Team Lead 委派 1 位最匹配成员，验收后汇总 |
| 轻量委派 | 有独立调查、搜索、验证或审查支线，不需要 Agent 互相协调 | 创建 1 至 2 个临时 Subagent，返回结构化结果 |
| 团队模式 | 存在两个以上独立工作流、不同专业能力或可并行交付物 | 建立任务 DAG，启动少量 Worker 协作 |
| 持续转交 | 用户需要长期与某个专业成员沟通 | 打开常驻 Agent Thread，负责人仍保留任务总览 |

### 4.1 AI 主动创建动态任务列表

Team Lead 或单个执行 Agent 可以根据任务复杂度主动把一个 `WorkItem` 拆成 Task 列表，并在对话中展开任务面板。创建任务列表不等于创建 Subagent：同一个 Agent 可以按依赖顺序逐项完成，只有适合并行或需要不同能力时才委派。

应创建任务列表的典型条件：

- 存在多个可独立验收的交付步骤。
- 涉及多个模块、项目或明显的先后依赖。
- 需要先调查、再实现、最后验证或审查。
- 预计会跨越多轮模型调用、审批或长时间工具执行。
- 用户明确要求列任务、逐项执行或持续汇报进度。

不应创建任务列表的情况：

- 一次读取、查询、命令或单文件小改即可完成。
- 只是把“读取文件、调用工具、回复用户”等内部动作拆成形式化 Todo。
- 每个条目没有独立完成条件，拆分后不能提升可见性或恢复能力。

每个 Task 至少包含：标题、目标、验收标准、项目、依赖、优先级、状态和预期交付物。AI 可以在执行中新增、拆分、合并、重排、阻塞或取消未完成 Task，但必须生成修订事件和简短理由。已完成 Task 需要重新打开时必须保留原完成记录并说明原因，不能静默改写历史。

用户可以调整优先级、取消或要求重新规划。任务列表默认显示状态数量和依赖，不伪造无法可靠估计的完成百分比或 ETA。应用重启后列表、修订记录、当前项和完成证据必须恢复。

任务列表的数据来源就是 `tasks`、`task_dependencies` 和事件，不新增另一份独立 Todo 状态。对话中的列表、任务详情和任务板必须读取同一投影。

以下情况不应组队：

- 单文件小改动。
- 一条命令或一次确定性查询能完成。
- 子任务强顺序依赖，无法真正并行。
- 多个 Agent 必须反复编辑同一批文件。
- 协调成本预计高于实际执行成本。

## 5. 持续任务收件箱

用户在项目普通对话中以 `@团队` 指明目标团队后，当前模型可调用 `submit_team_work_item` 交办需求；没有选择团队的直投控件。每次投递先形成独立 `WorkItem`，持久化来源 Conversation ID、项目、模型快照和权限模式，不会直接打断正在运行的 Agent；开始执行后，它才建立自己的 Team Lead 执行对话和其下的成员对话树。团队看板只展示和编辑已入箱 WorkItem，不提供第二个需求发送入口。

```text
inbox
  -> triaging
  -> needs_clarification | planned
  -> queued | running
  -> waiting_user | blocked | reviewing
  -> completed | failed | cancelled
```

规则：

- 用户可标记优先级、截止时间和目标项目。
- 用户可在 Team Lead 领取前编辑 `queued` WorkItem 的标题和需求；保存必须与状态检查原子进行并追加审计事件，领取后只能通过返工/验收流程继续。
- 未指定项目时，负责人只能依据明确线索推荐项目；存在歧义必须询问。
- 新任务默认进入队列，不抢占已运行任务；用户明确设为紧急时才触发重新排程。
- 已启用团队在提交后立即自动分发：有可用容量时，为该 WorkItem 创建独立的 Team Lead 执行实例；容量已满时保持 `queued`，在任一执行实例完成后再按优先级和入队顺序分发。团队暂停时仍可接收并保留 WorkItem，但不创建 Run；恢复启用后重新触发队列调度。
- 负责人接受任务后必须返回“已接收、绑定项目、当前状态、下一步”，不能静默排队。
- 应用重启后，收件箱、队列、任务依赖和 Agent 状态必须恢复。

## 6. 多项目承接范围

推荐采用“一个团队服务多个项目，但一个可执行任务只有一个主项目”的模型。

### 6.1 边界

- `Team` 可以注册多个 `Project`。
- `WorkItem` 在收件阶段可以暂未绑定项目。
- 每个可执行 `Task` 必须绑定且只能绑定一个主项目。
- 跨项目需求使用一个总 WorkItem，按项目拆成多个 Task，再由负责人汇总。
- Agent 的文件、Shell、Git、浏览器权限都从当前 Task 的项目绑定派生。

### 6.2 上下文隔离

- 团队级记忆只保存用户偏好、通用规范和项目目录索引。
- 项目技术栈、代码事实、历史修改和构建命令保存在项目记忆中。
- 默认项目执行 Conversation 可复用历史中已确认的项目事实、架构决定和验证结论，但每个 WorkItem 的当前需求仍是唯一任务指令，历史未完成任务不得自动续做。
- Agent 执行时只加载当前项目上下文，不把其他项目完整历史混入模型。
- 同名文件、分支和命令必须包含项目 ID，不能依赖当前 UI 选中的目录推断。

### 6.3 跨项目修改

跨项目任务必须生成独立子任务、独立审批和独立 Diff。任何 Agent 不得在一次工具调用中跨越两个项目根目录。

## 7. Agent 选择与自动扩容

### 7.1 候选过滤

调度器先用确定性规则过滤：

1. 是否有权访问目标项目。
2. 是否具备所需工具和能力标签。
3. 当前状态是否可接单。
4. 是否满足模型、上下文和成本预算。
5. 是否与其他写任务存在文件所有权冲突。

### 7.2 排序依据

候选 Agent 按以下信息排序：

- 能力与任务类型匹配度。
- 对目标项目、模块和文件的熟悉度。
- 近期同类任务成功率和用户反馈。
- 当前负载、预计完成时间和模型成本。
- 是否已经拥有完成任务所需的上下文。

模型只在过滤后的候选集中选择。每次分配保存 `routingReason`，UI 可以解释“为什么交给它”。

### 7.3 扩容条件

同时满足以下条件才创建新 Agent：

- 有未被依赖阻塞的可执行任务。
- 现有合适 Agent 都在忙，或缺少明确能力。
- 新任务可以与现有任务并行，不会竞争同一文件或独占资源。
- 剩余时间、Token 和并发预算足够。
- 创建 Agent 的预期收益高于启动和协调成本。

### 7.4 MVP 限制

- 默认最多同时运行 `3` 个 Worker，不含 Team Lead。
- 单个 WorkItem 最多创建 `5` 个 Agent Instance，包括失败后的替补。
- 委派深度为 `1`：只有 Team Lead 能启动 Worker。
- 每个 Worker 必须有最大轮次、Token/时间预算和空闲超时。
- 达到上限时任务排队，不继续递归扩容。
- 自动创建临时只读 Agent 可以按团队策略允许；具备写入或命令能力的 Agent 仍受原有逐次审批约束。

这些是控制模型成本、内存、工具冲突和浏览器资源的初始安全值，不是 CPU 线程数量限制。后续通过真实任务指标和机器能力调整，不作为永远固定的产品限制。

## 8. 分配合同与结果回收

负责人不能只发送一句模糊指令。每次委派至少包含：

```ts
type DelegationPacket = {
  workItemId: string;
  taskId: string;
  projectId: string;
  objective: string;
  acceptanceCriteria: string[];
  relevantPaths: string[];
  constraints: string[];
  allowedTools: string[];
  contextRefs: string[];
  budget: { maxTurns: number; maxDurationMs: number; maxInputTokens?: number };
  expectedOutput: "finding" | "patch" | "review" | "test_result" | "artifact";
};
```

Worker 必须返回结构化结果：状态、摘要、证据、改动、验证、未决问题和推荐下一步。完整日志写入 Artifact，不把整个子对话重新塞回负责人上下文。

## 9. 协作与写入冲突

- 只读调查可以共享同一项目快照。
- 当前普通对话和 Agent 直接使用用户主工作区，不强制绑定 Git worktree。
- 每个写任务可以声明预期文件集合用于提前避让，但正确性由文件路径互斥和 `expectedContent` 乐观并发检查保证。
- 同文件冲突时，先取得协调权的请求执行；后续已基于旧内容生成的请求立即作废。占用结束后，模型必须重新读取最新文件并生成新 Diff，不排队或自动重放旧参数。
- 不同文件可以并行修改；可能修改项目的命令默认与项目写操作互斥。
- 每次实际写入仍按当前对话的权限模式执行：审批模式等待用户确认，完全放开模式直接写入。
- Worktree 仅作为未来的可选隔离能力，用于并行尝试不同方案或明确要求分支交付的任务，不作为当前冲突处理前提。
- Agent 之间的消息不能携带或转授用户审批；被拒绝的操作不能换一个 Agent 重试来绕过权限。

## 10. 状态与持久化

团队能力必须建立在 SQLite 事件和可查询状态上，不能只存在模型上下文中。核心实体：

```text
teams
projects
team_projects
work_items
tasks
task_dependencies
agent_profiles
agent_instances
agent_threads
delegations
agent_messages
task_leases
team_events
```

任务领取使用带过期时间的租约，防止应用崩溃后任务永久显示为运行中。重启恢复时：

- 已完成任务保持完成。
- 正在执行的 Agent Instance 标记为 `interrupted`。
- 无副作用的只读任务可以由用户或负责人选择重试。
- 写入、命令和网页提交不得自动重放。
- 已保留执行根的 Team WorkItem 以及任何未完整绑定任务关系的 `subagent` queued Run 都标记失败；对应 WorkItem 进入阻塞，必须由用户明确处理，不能因为它们在崩溃时仍是 `queued` 而恢复。
- 常驻 Agent 恢复历史摘要和任务记录，但不假装原进程仍在运行。

## 11. UI 信息架构

在 `md-king` 工作台上增加以下视图：

- **团队收件箱**：持续输入任务，显示已接收、待澄清和排队状态。
- **任务板**：按项目和状态查看 WorkItem、Task、依赖和优先级。
- **对话内任务列表**：AI 主动拆解后在相关消息处显示可折叠的实时列表、当前项、依赖和修订理由。
- **团队面板**：按选中 WorkItem 显示需求、阶段、Task、验收/返工动作、团队状态和真实成员状态，而不是把团队配置成员伪装成正在工作。它不嵌入成员聊天或维护第二份对话缓存；执行成员的来源只能是 WorkItem 根执行 Conversation 与持久化 `subagent_tasks` 谱系，普通侧边对话不进入此视图。
- **项目对话树**：每个开始执行的 WorkItem 显示为来源主对话下的 Team Lead 与成员协作层级；从团队面板或成员行点击 Team Lead 或成员时保持该来源主对话，并在右侧打开成员 Tab。原生对话页显示模型来源、Run 分界、消息、工具、审批和 Artifact。
- **受管执行会话**：Team Lead 根及由持久化委派关系确认的成员 Conversation 由 WorkItem 生命周期保留，不能直接归档、删除、改项目或改 Agent。右侧 Tab 与普通对话一致，保留输入、队列、停止、模型/思考、权限、审批和任务清单关闭入口；模型/思考和权限选择器更新 WorkItem 的后续 Run 策略，模型/思考同时更新当前 Tab 的展示快照，但不能追溯改变当前 Run 或已经出现的审批。运行中输入被路由为当前 Run 的 `steer`，不生成脱离 WorkItem 的新 Run；Run 终止后遗留审批显示为已失效；普通侧边对话不受 WorkItem 生命周期限制。
- **任务详情**：在团队面板中显示分解依据、分配理由、状态、Artifact、Diff、验证结果和用户验收；完整 Agent 消息不在任务详情中重复展示。
- **统一审批中心**：显示任务、项目、Agent、真实路径、命令和副作用，不让多 Agent 审批淹没主对话。

没有交给团队的简单任务仍在主对话中完成；已经形成 WorkItem 的简单任务使用 Team Lead 加一位专业成员的短路径，不强迫跑完整六岗位流程。

## 12. 第一阶段实现顺序

1. 先完成单 Agent 的文件、工具、审批和恢复闭环。
2. 增加持久化 Team、Project、WorkItem 和 Task，不立即并发。
3. 使用 `MockModelAdapter` 验证负责人拆分、候选过滤和任务状态机。
4. 增加一个临时 Subagent，验证独立上下文和结果回收。
5. 增加最多三个 Worker、任务依赖、租约和失败替补。
6. 增加多项目注册、按任务绑定项目和跨项目拆分。
7. 最后接入真实模型做自动扩容和路由评测。

历史基线曾决定不直接引入 LangGraph；该决定已由 2026-08-19 的技术选型更新取代。当前采用 LangGraph 作为 `AgentRuntime` 内部执行图，但本地权限、SQLite 业务事实、工作区隔离和事件合同仍由项目 façade 控制。AutoGen/CrewAI 仍不作为核心运行时。具体边界和迁移顺序见[LangChain 与 LangGraph 改造方案](./15-LangChain与LangGraph改造方案.md)。

## 13. 验收场景

1. 投递一个单文件修复，负责人不创建 Subagent，直接完成。
2. 投递一个复杂缺陷，负责人并行创建调查和测试 Agent，最终只返回一份汇总结论。
3. 连续投递三个任务，旧任务继续执行，新任务进入队列并可调整优先级。
4. 某类任务没有合适成员时，负责人创建临时 Agent，并展示招聘理由和预算。
5. 两个 Agent 基于同一旧版本修改同一文件时，只允许先取得协调权的请求写入；后一个请求被作废并在重新读取后生成新 Diff，不发生静默覆盖。
6. 注册两个项目并分别投递任务，文件权限、会话和 Diff 不串项目。
7. 投递跨项目任务，系统拆成项目级子任务并分别审批。
8. 强制退出应用后恢复，任务和团队状态可见，副作用操作不自动重放。
9. 达到并发或预算上限后任务排队，不继续创建 Agent。
10. 临时 Agent 完成后释放运行资源，常驻 Agent 可在后续任务中恢复持续对话。
11. 新 Agent 未指定模型时继承父对话模型；用户修改常驻 Agent 模型后，下一 Run 生效且历史 Thread 不变化。
12. 任一临时 Agent 的独立 Thread 在完成和重启后仍可打开，来源任务、模型和用户可见过程完整。
13. 投递一个多阶段任务，AI 主动建立任务列表并由同一 Agent 逐项完成，不因创建列表而自动组队。
14. 执行中发现新前置条件时，AI 新增或调整未完成 Task 并记录理由；已完成项和完成证据不被覆盖。
