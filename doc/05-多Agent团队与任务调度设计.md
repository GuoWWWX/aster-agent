# 多 Agent 团队与任务调度设计

> 文档状态：核心能力基线  
> 更新时间：2026-08-15  
> 关联文档：[AI Agent 产品与技术方案总览](./00-AI-Agent产品与技术方案总览.md)、[第一阶段需求与验收标准](./01-第一阶段需求与验收标准.md)

## 1. 目标

产品需要支持一个长期存在的 AI 团队。用户可以持续把想法、问题和任务投递给团队负责人，不必每次先决定该找哪个 Agent。团队负责人负责：

- 接收并澄清任务。
- 判断任务直接执行、轻量委派还是组建团队。
- 选择已有 Agent，或按需创建临时 Agent。
- 管理任务依赖、并发、权限、进度和失败恢复。
- 汇总各 Agent 的结果，并对最终交付负责。

团队不能为了“看起来像组织”而预设大量岗位。简单任务应由负责人或一个通用执行 Agent 直接完成，只有可分解、可并行或确实需要不同能力/权限的任务才增加 Agent。

## 2. 主流方案中的可用设计点

### 2.1 管理者保持最终所有权

OpenAI Agents SDK 区分两种模式：

- `handoff`：把当前分支的对话所有权交给专业 Agent。
- `agent as tool`：管理者把专业 Agent 当成有边界的能力调用，最终回答仍由管理者负责。

本产品默认使用第二种。团队负责人始终拥有用户任务和最终交付，临时 Agent 返回结构化结果。只有用户明确进入某个常驻 Agent 的持续对话时，才使用类似 handoff 的体验。

### 2.2 临时 Subagent 与协作团队分开

Claude Code 将两者区分为：

- Subagent：独立上下文完成一个支线任务，返回摘要，适合搜索、调查、验证和单次实现。
- Agent Team：多个独立会话通过共享任务列表和 mailbox 协作，适合真正并行且需要互相沟通的工作。

这一区分适合本产品。不能把每次文件搜索都升级成完整团队，也不能把需要多轮协作的长期任务塞进一次性工具调用。

### 2.3 共享任务列表必须有依赖和领取机制

Claude Agent Teams 使用 `pending`、`in progress`、`completed` 状态、任务依赖和原子领取；AutoGen 的 Selector Group Chat 使用 Agent 名称、职责描述和当前上下文选择下一位执行者，并要求明确终止条件和最大轮次。

本产品采用持久化任务图和任务租约，不采用无限自由群聊。Agent 可以互发消息，但真正决定进度的是任务状态、依赖、交付物和验收结果。

### 2.4 角色描述用于候选匹配，不用于制造组织层级

AutoGen 会根据参与者的名称和职责描述选择下一位 Agent，也支持先用候选函数缩小范围，再让模型选择。这个两阶段思路比“把所有 Agent 全塞给模型选择”更稳定：

1. 代码先按项目权限、工具、能力、状态和预算过滤候选。
2. 评分器或模型在少量候选中选择，并记录理由。

### 2.5 团队规模必须受控

Claude Code 官方文档指出，多 Agent 的 Token 成本随活跃成员增长，协调开销和文件冲突也会增加，普通任务使用单会话更划算。其建议通常从少量成员开始，只在工作确实可并行时扩容。

本产品不允许 Agent 无限递归招募。MVP 只有团队负责人能创建或停止 Worker；Worker 可以建议增员，但不能自行再创建团队。

## 3. 推荐组织模型

```text
AI Team（长期存在）
├─ Team Lead（唯一负责人，长期会话）
├─ Team Inbox（持续接收用户任务）
├─ Project Registry（团队可服务的项目）
├─ Agent Profiles（可复用能力定义）
├─ Standing Agents（可休眠的常驻成员）
└─ Work Items
   └─ Tasks / Task DAG
      ├─ Direct execution
      ├─ Ephemeral Subagent
      └─ Coordinated Workers
```

### 3.1 Team Lead

团队只有一个主负责人。它长期存在并保存团队级对话、用户偏好、当前优先级和任务总览。它可以执行简单任务，但在有 Worker 运行时主要负责：

- 任务澄清和项目绑定。
- 拆分任务并定义验收标准。
- 分配或回收任务。
- 处理冲突和阻塞。
- 汇总交付，不代替用户批准高风险操作。

### 3.2 Ephemeral Subagent

临时 Subagent 服务于一个有边界的任务，完成后释放模型和进程资源，但保留独立 Agent Thread、用户可见消息、工具与审批事件、摘要和 Artifact。典型场景：

- 搜索代码并定位实现。
- 调查某个错误的可能原因。
- 独立做安全、性能或测试审查。
- 在隔离工作区完成一个明确文件集合的修改。

### 3.3 Standing Agent

常驻 Agent 是可持续对话、可多次接单的成员，但空闲时不占用模型或进程资源。它保留：

- 稳定的 Agent Profile。
- 与项目隔离的长期摘要和经验。
- 已完成任务、能力表现和用户反馈。
- 可恢复的 Agent Thread。

不在初始化时创建完整岗位表。某类临时 Agent 被多次使用且持续产生价值后，用户或负责人才能建议将其转为常驻成员。

### 3.4 Agent Profile 与 Agent Instance 分离

- `AgentProfile`：职责、能力标签、允许工具、模型策略、Skill、输出合同和适用项目范围。
- `AgentInstance`：一次实际运行或一个可恢复的常驻成员实例。

“招聘”本质是从模板生成或复用 Profile，再启动 Instance，不是动态生成无约束的系统提示词。

### 3.5 最小角色策略

初始团队只固定两个概念，不预建前端、后端、测试、产品、架构等完整岗位：

- `Team Lead`：接单、拆分、调度、验收和汇总。
- `Generalist Executor`：默认执行范围明确的开发任务，可以是负责人自身能力，也可以启动为 Worker。

其余角色按任务临时形成能力模板，而不是永久组织岗位：

- `Explorer`：只读搜索、项目理解和事实核对。
- `Implementer`：在明确文件边界内完成修改和验证。
- `Reviewer`：从安全、性能、测试或需求符合性中的一个明确视角审查。

“前端 Agent”“数据库 Agent”“发布 Agent”等名称只有在项目长期反复出现对应任务时才注册为常驻 Profile。角色数量由实际工作模式长出来，不在产品初始化时一次性设计完。

### 3.6 Agent 逻辑对话与模型

每个 Team Lead、常驻 Agent 和临时 Subagent 都有独立的逻辑对话 Thread。它是 SQLite 中的对话与事件归属，不是独占的 OS 线程、Node `worker_threads` 或进程。用户可以从团队面板打开任何 Agent 的对话，查看来源任务、实际模型、消息、工具、审批、Artifact 和结果。临时 Agent 完成后 Thread 仍可查看；用户继续对话时创建新 Run，不修改历史 Run。

空闲 Agent 不占用模型连接、执行线程或子进程。任务到来时才创建 Run，由共享异步调度器和受限 Worker/进程池执行；Agent 数量因此不直接受 CPU 线程数限制，活动 Run 数量则受内存、供应商限流、工具进程和用户预算共同约束。

Agent 模型默认继承创建它的父对话当前模型，也可以由 Profile、创建请求、ModelRouter 或用户指定。用户通过对话或模型选择器的明确设置具有最高优先级；自动路由不能解除用户锁定。完整规则见[模型接入、MCP、Skill 与 Agent 对话设计](./08-模型接入、MCP、Skill与Agent对话设计.md)。

## 4. 任务分级与是否组队

团队负责人先把请求分类，不能默认拆分。

| 模式 | 适用条件 | 执行方式 |
| --- | --- | --- |
| 直接模式 | 范围明确、步骤连续、修改集中、预计一个上下文可完成 | 负责人或一个通用 Agent 完成 |
| 轻量委派 | 有独立调查、搜索、验证或审查支线，不需要 Agent 互相协调 | 创建 1 至 2 个临时 Subagent，返回结构化结果 |
| 团队模式 | 存在两个以上独立工作流、不同专业能力或可并行交付物 | 建立任务 DAG，启动少量 Worker 协作 |
| 持续转交 | 用户需要长期与某个专业成员沟通 | 打开常驻 Agent Thread，负责人仍保留任务总览 |

### 4.1 AI 主动创建动态任务列表

Team Lead 或单个执行 Agent 可以根据任务复杂度主动把一个 `WorkItem` 拆成 Task 列表，并在对话中展开任务面板。创建任务列表不等于创建 Subagent：同一个 Agent 可以按依赖顺序逐项完成，只有适合并行或需要不同能力时才委派。

应创建任务列表的典型条件：

- 存在多个可独立验收的交付步骤。
- 涉及多个模块、项目或明显的先后依赖。
- 需要先调查、再实现、最后验证或审查。
- 预计会跨越多轮模型调用、审批或长时间工具执行。
- 用户明确要求列任务、逐项执行或持续汇报进度。

不应创建任务列表的情况：

- 一次读取、查询、命令或单文件小改即可完成。
- 只是把“读取文件、调用工具、回复用户”等内部动作拆成形式化 Todo。
- 每个条目没有独立完成条件，拆分后不能提升可见性或恢复能力。

每个 Task 至少包含：标题、目标、验收标准、项目、依赖、优先级、状态和预期交付物。AI 可以在执行中新增、拆分、合并、重排、阻塞或取消未完成 Task，但必须生成修订事件和简短理由。已完成 Task 需要重新打开时必须保留原完成记录并说明原因，不能静默改写历史。

用户可以调整优先级、取消或要求重新规划。任务列表默认显示状态数量和依赖，不伪造无法可靠估计的完成百分比或 ETA。应用重启后列表、修订记录、当前项和完成证据必须恢复。

任务列表的数据来源就是 `tasks`、`task_dependencies` 和事件，不新增另一份独立 Todo 状态。对话中的列表、任务详情和任务板必须读取同一投影。

以下情况不应组队：

- 单文件小改动。
- 一条命令或一次确定性查询能完成。
- 子任务强顺序依赖，无法真正并行。
- 多个 Agent 必须反复编辑同一批文件。
- 协调成本预计高于实际执行成本。

## 5. 持续任务收件箱

用户可以在团队执行旧任务时继续投递新想法。每次投递先形成 `WorkItem`，不会直接打断正在运行的 Agent。

```text
inbox
  -> triaging
  -> needs_clarification | planned
  -> queued | running
  -> waiting_user | blocked | reviewing
  -> completed | failed | cancelled
```

规则：

- 用户可标记优先级、截止时间和目标项目。
- 未指定项目时，负责人只能依据明确线索推荐项目；存在歧义必须询问。
- 新任务默认进入队列，不抢占已运行任务；用户明确设为紧急时才触发重新排程。
- 负责人接受任务后必须返回“已接收、绑定项目、当前状态、下一步”，不能静默排队。
- 应用重启后，收件箱、队列、任务依赖和 Agent 状态必须恢复。

## 6. 多项目承接范围

推荐采用“一个团队服务多个项目，但一个可执行任务只有一个主项目”的模型。

### 6.1 边界

- `Team` 可以注册多个 `Project`。
- `WorkItem` 在收件阶段可以暂未绑定项目。
- 每个可执行 `Task` 必须绑定且只能绑定一个主项目。
- 跨项目需求使用一个总 WorkItem，按项目拆成多个 Task，再由负责人汇总。
- Agent 的文件、Shell、Git、浏览器权限都从当前 Task 的项目绑定派生。

### 6.2 上下文隔离

- 团队级记忆只保存用户偏好、通用规范和项目目录索引。
- 项目技术栈、代码事实、历史修改和构建命令保存在项目记忆中。
- Agent 执行时只加载当前项目上下文，不把其他项目完整历史混入模型。
- 同名文件、分支和命令必须包含项目 ID，不能依赖当前 UI 选中的目录推断。

### 6.3 跨项目修改

跨项目任务必须生成独立子任务、独立审批和独立 Diff。任何 Agent 不得在一次工具调用中跨越两个项目根目录。

## 7. Agent 选择与自动扩容

### 7.1 候选过滤

调度器先用确定性规则过滤：

1. 是否有权访问目标项目。
2. 是否具备所需工具和能力标签。
3. 当前状态是否可接单。
4. 是否满足模型、上下文和成本预算。
5. 是否与其他写任务存在文件所有权冲突。

### 7.2 排序依据

候选 Agent 按以下信息排序：

- 能力与任务类型匹配度。
- 对目标项目、模块和文件的熟悉度。
- 近期同类任务成功率和用户反馈。
- 当前负载、预计完成时间和模型成本。
- 是否已经拥有完成任务所需的上下文。

模型只在过滤后的候选集中选择。每次分配保存 `routingReason`，UI 可以解释“为什么交给它”。

### 7.3 扩容条件

同时满足以下条件才创建新 Agent：

- 有未被依赖阻塞的可执行任务。
- 现有合适 Agent 都在忙，或缺少明确能力。
- 新任务可以与现有任务并行，不会竞争同一文件或独占资源。
- 剩余时间、Token 和并发预算足够。
- 创建 Agent 的预期收益高于启动和协调成本。

### 7.4 MVP 限制

- 默认最多同时运行 `3` 个 Worker，不含 Team Lead。
- 单个 WorkItem 最多创建 `5` 个 Agent Instance，包括失败后的替补。
- 委派深度为 `1`：只有 Team Lead 能启动 Worker。
- 每个 Worker 必须有最大轮次、Token/时间预算和空闲超时。
- 达到上限时任务排队，不继续递归扩容。
- 自动创建临时只读 Agent 可以按团队策略允许；具备写入或命令能力的 Agent 仍受原有逐次审批约束。

这些是控制模型成本、内存、工具冲突和浏览器资源的初始安全值，不是 CPU 线程数量限制。后续通过真实任务指标和机器能力调整，不作为永远固定的产品限制。

## 8. 分配合同与结果回收

负责人不能只发送一句模糊指令。每次委派至少包含：

```ts
type DelegationPacket = {
  workItemId: string;
  taskId: string;
  projectId: string;
  objective: string;
  acceptanceCriteria: string[];
  relevantPaths: string[];
  constraints: string[];
  allowedTools: string[];
  contextRefs: string[];
  budget: { maxTurns: number; maxDurationMs: number; maxInputTokens?: number };
  expectedOutput: "finding" | "patch" | "review" | "test_result" | "artifact";
};
```

Worker 必须返回结构化结果：状态、摘要、证据、改动、验证、未决问题和推荐下一步。完整日志写入 Artifact，不把整个子对话重新塞回负责人上下文。

## 9. 协作与写入冲突

- 只读调查可以共享同一项目快照。
- 当前普通对话和 Agent 直接使用用户主工作区，不强制绑定 Git worktree。
- 每个写任务可以声明预期文件集合用于提前避让，但正确性由文件路径互斥和 `expectedContent` 乐观并发检查保证。
- 同文件冲突时，先取得协调权的请求执行；后续已基于旧内容生成的请求立即作废。占用结束后，模型必须重新读取最新文件并生成新 Diff，不排队或自动重放旧参数。
- 不同文件可以并行修改；可能修改项目的命令默认与项目写操作互斥。
- 每次实际写入仍按当前对话的权限模式执行：审批模式等待用户确认，完全放开模式直接写入。
- Worktree 仅作为未来的可选隔离能力，用于并行尝试不同方案或明确要求分支交付的任务，不作为当前冲突处理前提。
- Agent 之间的消息不能携带或转授用户审批；被拒绝的操作不能换一个 Agent 重试来绕过权限。

## 10. 状态与持久化

团队能力必须建立在 SQLite 事件和可查询状态上，不能只存在模型上下文中。核心实体：

```text
teams
projects
team_projects
work_items
tasks
task_dependencies
agent_profiles
agent_instances
agent_threads
delegations
agent_messages
task_leases
team_events
```

任务领取使用带过期时间的租约，防止应用崩溃后任务永久显示为运行中。重启恢复时：

- 已完成任务保持完成。
- 正在执行的 Agent Instance 标记为 `interrupted`。
- 无副作用的只读任务可以由用户或负责人选择重试。
- 写入、命令和网页提交不得自动重放。
- 常驻 Agent 恢复历史摘要和任务记录，但不假装原进程仍在运行。

## 11. UI 信息架构

在 `md-king` 工作台上增加以下视图：

- **团队收件箱**：持续输入任务，显示已接收、待澄清和排队状态。
- **任务板**：按项目和状态查看 WorkItem、Task、依赖和优先级。
- **对话内任务列表**：AI 主动拆解后在相关消息处显示可折叠的实时列表、当前项、依赖和修订理由。
- **团队面板**：Team Lead、常驻成员、临时 Agent、状态、负载和当前任务。
- **Agent 对话**：打开任意成员的独立 Thread，显示模型来源、Run 分界、消息、工具、审批和 Artifact，并允许修改后续模型。
- **任务详情**：分解依据、分配理由、Agent 消息、Artifact、Diff 和验证结果。
- **统一审批中心**：显示任务、项目、Agent、真实路径、命令和副作用，不让多 Agent 审批淹没主对话。

简单任务仍在主对话中完成，不强迫用户进入任务板查看额外流程。

## 12. 第一阶段实现顺序

1. 先完成单 Agent 的文件、工具、审批和恢复闭环。
2. 增加持久化 Team、Project、WorkItem 和 Task，不立即并发。
3. 使用 `MockModelAdapter` 验证负责人拆分、候选过滤和任务状态机。
4. 增加一个临时 Subagent，验证独立上下文和结果回收。
5. 增加最多三个 Worker、任务依赖、租约和失败替补。
6. 增加多项目注册、按任务绑定项目和跨项目拆分。
7. 最后接入真实模型做自动扩容和路由评测。

历史基线曾决定不直接引入 LangGraph；该决定已由 2026-08-19 的技术选型更新取代。当前采用 LangGraph 作为 `AgentRuntime` 内部执行图，但本地权限、SQLite 业务事实、工作区隔离和事件合同仍由项目 façade 控制。AutoGen/CrewAI 仍不作为核心运行时。具体边界和迁移顺序见[LangChain 与 LangGraph 改造方案](./15-LangChain与LangGraph改造方案.md)。

## 13. 验收场景

1. 投递一个单文件修复，负责人不创建 Subagent，直接完成。
2. 投递一个复杂缺陷，负责人并行创建调查和测试 Agent，最终只返回一份汇总结论。
3. 连续投递三个任务，旧任务继续执行，新任务进入队列并可调整优先级。
4. 某类任务没有合适成员时，负责人创建临时 Agent，并展示招聘理由和预算。
5. 两个 Agent 基于同一旧版本修改同一文件时，只允许先取得协调权的请求写入；后一个请求被作废并在重新读取后生成新 Diff，不发生静默覆盖。
6. 注册两个项目并分别投递任务，文件权限、会话和 Diff 不串项目。
7. 投递跨项目任务，系统拆成项目级子任务并分别审批。
8. 强制退出应用后恢复，任务和团队状态可见，副作用操作不自动重放。
9. 达到并发或预算上限后任务排队，不继续创建 Agent。
10. 临时 Agent 完成后释放运行资源，常驻 Agent 可在后续任务中恢复持续对话。
11. 新 Agent 未指定模型时继承父对话模型；用户修改常驻 Agent 模型后，下一 Run 生效且历史 Thread 不变化。
12. 任一临时 Agent 的独立 Thread 在完成和重启后仍可打开，来源任务、模型和用户可见过程完整。
13. 投递一个多阶段任务，AI 主动建立任务列表并由同一 Agent 逐项完成，不因创建列表而自动组队。
14. 执行中发现新前置条件时，AI 新增或调整未完成 Task 并记录理由；已完成项和完成证据不被覆盖。
