# 第一阶段需求与验收标准

> 文档状态：开工基线  
> 更新时间：2026-08-16  
> 目标版本：MVP  
> 关联文档：[AI Agent 产品与技术方案总览](./00-AI-Agent产品与技术方案总览.md)、[前后端模块与编码规范](./06-前后端模块与编码规范.md)、[界面迁移与设计系统规范](./07-界面迁移与设计系统规范.md)

## 1. 第一阶段目标

第一阶段交付一个 Windows 本地编码 Agent 团队。用户持续向 Team Lead 投递想法和任务；Team Lead 能直接完成简单任务，也能为复杂任务创建临时 Subagent 或调度少量 Worker。团队在授权范围内读取项目、搜索内容、提出并应用补丁、执行命令、展示 Diff，并将团队、任务和对话完整持久化。

第一阶段同时保留 `md-king` 的视觉与交互合同、Markdown 编辑和预览能力，并保证同一套 React UI 能在普通浏览器中以开发预览模式运行。

本阶段的目标不是做一个功能齐全的 Codex 或 Claude Code 替代品，而是证明以下闭环真实可用：

```text
登记项目
  -> 向 Team Lead 投递任务
  -> 判断直接执行或委派
  -> Agent 读取与搜索
  -> 展示工具过程
  -> 用户审批写入或命令
  -> Agent 修改并验证
  -> 用户审查 Diff
  -> 会话持久化并可恢复
```

## 2. 开工默认假设

以下内容作为第一阶段实现基线；后续变更必须更新本文档：

- 首要场景是本地编码 Agent，文档处理是复用能力，不与编码闭环争夺第一优先级。
- 桌面端是首个完整交付目标；Web 端先保证 UI 可独立渲染和使用 Mock 数据。
- 模型通过 `ModelProviderAdapter` 接入；MVP 至少验证 OpenAI-compatible 与另一类真实 Provider Adapter，用户可以配置多个供应商、端点和模型。
- API Key 使用 Electron `safeStorage` 保护，不写入 SQLite、日志和普通配置文件。
- 工作区内读取与搜索默认允许；文件写入、Patch、命令执行逐次审批。
- 第一阶段只支持 Windows 本地项目和 PowerShell 非交互命令。
- WSL、SSH、Bash 和交互式 PTY 按后续优先级实现；基础 MCP Client 与本地 Skill 管理进入 MVP，受管浏览器必须先通过技术 PoC，完整多标签、下载和上传能力后续实现。
- `md-king` 的 AppShell 视觉合同在 `apps/web` 重新实现；编辑器、预览、文件树和标签页按最小依赖闭包迁移，并保留相关测试基线。
- DOCX 转换和 Word/WPS 快捷粘贴不进入 MVP；原 `md-king` 项目继续保留这些能力。
- 会话主数据使用 SQLite，长日志和截图使用 Artifact 文件；JSON/JSONL 用于导出或诊断，不作为第一阶段主数据源。
- 用户选择的文件和图片先复制到应用数据目录形成只读快照，SQLite 只保存附件元数据和消息绑定，不保存图片 Base64。
- Team Lead 长期存在并持续接收任务；新任务进入可恢复收件箱，不会静默打断正在运行的任务。
- 团队可登记多个本地项目；每个执行 Task 必须绑定一个主项目，跨项目需求拆成项目级子任务。
- 简单任务不组队；MVP 最多并发三个 Worker，只有 Team Lead 能启动 Worker。

## 3. 用户主流程

### 3.1 首次启动

1. 用户启动桌面应用。
2. 应用显示沿用 `md-king` 风格的工作台，而不是营销首页。
3. 用户创建默认团队并登记一个或多个本地项目目录。
4. 应用分别建立项目授权，并显示项目和文件树。
5. 用户在模型中心登记供应商、端点、凭据和一个或多个模型。
6. 应用验证 Provider 和模型能力，密钥经系统能力加密后保存。
7. 用户可以按需登记 MCP Server、启用 Skill，并选择其适用 Team、Project 或 Agent。

### 3.2 执行任务

1. 用户在团队收件箱或 Team Lead 对话中投递任务，并选择目标项目；未选择且无法唯一判断时，Team Lead 请求澄清。
2. Team Lead 判断直接执行、轻量委派或团队模式，并展示接单状态。
3. 直接任务由一个 Agent 执行；复杂任务形成带依赖的 Task，并分配给合适的 Agent。
4. Agent 读取必要文件并搜索代码。
5. UI 逐条显示任务、Agent、工具调用、目标路径和结果摘要。
6. Agent 请求修改文件时，UI 展示 Patch 和审批操作。
7. 用户批准后写入工作区。
8. Agent 请求执行命令时，UI 展示完整命令和工作目录。
9. 用户批准后执行，UI 流式展示 stdout、stderr 和退出码。
10. Agent 根据结果继续修正或结束任务，Team Lead 回收并核验结果。
11. UI 展示统一的最终 Diff、验证结果和未完成事项。

### 3.3 持续投递

1. 旧任务运行期间，用户继续投递新任务。
2. 新任务立即形成 WorkItem，并显示已接收、待澄清、排队或运行状态。
3. Team Lead 可以复用空闲成员、创建临时 Agent 或等待容量释放。
4. 用户可以调整优先级；除非明确要求紧急抢占，新任务不打断运行中的副作用操作。

### 3.4 恢复任务

1. 用户关闭并重新打开应用。
2. 团队、项目、WorkItem、Task 和会话列表恢复标题、绑定关系、更新时间和状态。
3. 打开 Team Lead 或 Agent Thread 后能看到原始消息、工具调用、审批和结果。
4. 中断中的 Run 显示为 `interrupted`。
5. 应用不得自动重放文件写入和命令执行。

## 4. 功能需求

### MVP-01 工作区

- 用户通过系统目录选择器登记项目工作区。
- 项目会话自动继承项目根目录；临时对话可以显式附加、替换或移除一个持久工作目录。
- 每个项目文件树只展示其授权根目录及其子目录。
- 支持打开文本文件和 Markdown 文件。
- 支持用 Glob 按文件名跨层查找，并支持按文本内容搜索。
- 规范化路径后再执行边界校验，拒绝目录穿越。
- 工作区外读取必须重新审批。

**验收：** 选择一个包含 Git 仓库的测试项目，能够展开目录、打开文件并搜索指定字符串；临时对话附加目录后重启应用仍能使用该目录；构造 `..` 和符号链接逃逸路径时请求被拒绝。

### MVP-02 会话

- 支持新建、重命名、打开、停止和删除会话。
- 会话归属于一个 Team；Team Lead Thread 可以跨项目接单，Task/Agent Thread 必须绑定一个 Project。
- 每条用户请求创建一个 Run。
- 消息、工具、审批和状态事件按顺序持久化。
- 支持流式显示模型输出。

**验收：** 创建 Team Lead Thread 和两个项目级 Agent Thread 后重启应用，列表顺序、标题、团队、项目绑定和内容保持一致；删除一个会话后相关 Artifact 被清理。

### MVP-03 模型接入

- 建立统一 `ModelProviderAdapter`，支持兼容协议和供应商原生协议的流式请求与 Tool Calling。
- 配置包含协议 Adapter、Base URL/请求路径、凭据引用、模型 ID、别名、能力、上下文窗口、输出上限和基础请求参数。
- 提供 Provider 与模型连接测试；失败配置可以保存为未验证草稿，但不能静默设为默认可用模型。
- 模型错误转换为统一错误结构。
- 支持取消当前模型请求。

**验收：** 使用至少两类真实 Provider Adapter 和两个自定义请求地址分别完成流式消息和结构化工具调用；手工上下文窗口参与预算计算；错误密钥、超时和用户取消均转换为同一错误合同并显示可理解状态。

### MVP-04 Agent Loop

- 支持模型消息、工具请求、工具结果和后续模型调用的循环。
- 每个 Run 有最大循环次数、超时和取消信号。
- 工具参数必须通过 Zod Schema 校验。
- 工具失败作为结构化结果返回，不导致应用退出。
- Run 结束状态只能是 `completed`、`failed`、`cancelled`、`blocked` 或 `interrupted`。

**验收：** 用模拟模型稳定复现“读取 -> 搜索 -> 修改 -> 测试 -> 完成”，并覆盖非法参数、工具失败、循环上限和取消。

### MVP-05 文件修改与 Diff

- Agent 优先使用 Patch 修改文件。
- 写入前展示目标文件、修改区块和权限提示。
- 用户批准后才应用 Patch。
- 文件已被外部修改时拒绝覆盖并要求重新读取。
- UI 区分建议修改、已写入修改和 Git 已有修改。

**验收：** 对测试仓库修改一个文件，审批前磁盘不变化；审批后内容正确；外部修改同一文件后，旧 Patch 不得静默覆盖。

### MVP-06 命令执行

- 第一阶段支持 PowerShell 非交互命令。
- 请求展示命令、工作目录和超时设置。
- 用户批准后启动进程并流式返回输出。
- 支持超时、取消和进程树终止。
- 记录退出码、开始时间、结束时间和输出是否截断。

**验收：** 覆盖成功命令、失败命令、长输出、超时和取消；取消后检查无残留测试进程。

### MVP-07 Git

- 支持读取仓库根目录、分支、状态和 Diff。
- Git 读取操作可在工作区授权内自动执行。
- 第一阶段不提供 Agent 自动 commit、push、reset 或 clean。

**验收：** 测试仓库存在用户预先修改时，Agent 修改后能分别展示整体 Git 状态和本轮相关 Diff，不覆盖用户修改。

### MVP-08 审批

- 审批对象至少区分工作区外读取、文件写入、Patch 和命令执行。
- 审批卡展示真实路径、命令、工作目录和操作摘要。
- 支持批准和拒绝。
- 拒绝结果返回 Agent，由 Agent 决定改用只读方案或结束。
- 审批事件持久化。

**验收：** 分别拒绝一次写入和命令，确认磁盘与进程均未变化，Agent 收到明确拒绝结果。

### MVP-09 Markdown 与 UI 复用

- 按 `md-king` 的视觉与交互合同重新实现 AppShell、标题栏、活动栏和主题，不复制原有宿主调用与页面结构。
- 按最小依赖闭包迁移文件树、文档标签和 `LiveMarkdownEditor`，保留实时预览、表格、图片、Mermaid、Callout 和链接能力。
- 在既有测试保护下迁移 `WordPreviewPage` 的纯前端预览能力。
- 保留长文档预览暂停保护。
- Agent 页面与原 UI 使用同一套视觉变量和布局交互。

**验收：** 现有 Markdown 编辑器定向测试通过；普通文档渲染效果与迁移前对比无明显差异；超过既有阈值的长文档不全量生成 Word 预览页。

### MVP-10 浏览器渲染模式

- `apps/web` 可由 Vite 在普通浏览器中启动。
- Web 开发模式使用 Mock `AgentClient`，不要求本机工具权限。
- Electron 加载相同的 `apps/web` 构建产物。
- UI 组件不得直接调用 Node、Electron 或 Tauri API。

**验收：** 同一页面分别在浏览器和 Electron 中打开；浏览器模式无 `window.electron` 也不崩溃，桌面模式能通过 Preload 完成受控调用。

### MVP-11 对话压缩与附件上下文

- 按模型 Token 预算构造上下文，不按固定消息条数截断。
- 当前 Run、未完成审批和用户明确约束不压缩。
- 旧工具长输出先 Artifact 化，再对早期对话生成结构化摘要。
- 摘要记录覆盖事件范围，原始消息继续保存在本地。
- 用户能看到发生过压缩并查看摘要。
- 对话框支持一次添加最多 10 个文件或图片，单个附件不超过 25 MB，也支持只发送附件。
- 项目文件和项目外文件被明确添加到对话时，都复制为消息时点快照并走同一附件处理链；未添加到对话的项目文件仍由文件工具按需读取，不自动塞入上下文。
- 文本、代码、PDF 和 DOCX 提取文本；长文本只注入头尾预览，模型可通过 `read_attachment` 分段读取全文；图片按模型协议作为多模态内容发送。
- 附件 Token 单独统计但参与同一压缩阈值。先压缩旧历史；若“本轮文字、附件、系统与工具定义、输出预留”自身仍超过阈值，则发送前阻止请求并保留附件草稿。
- 附件元数据和消息绑定写入 SQLite，原文件快照与提取文本写入 `<ASTER_HOME>/attachments/<conversationId>/`；删除会话或归档到期清理无引用文件。

**验收：** 构造超过测试上下文预算的会话，压缩后任务目标、文件路径、附件来源、用户约束和未完成事项仍存在；原始消息和已发送附件仍可查看。分别发送文本、长文本、图片、PDF、DOCX 和纯附件消息；上下文用量包含附件 Token；超出本轮最低预算时不创建 Run，附件仍保留为草稿。

### MVP-12 受管浏览器技术门禁

- 在最小 Electron 壳完成后立即验证浏览器方案，不等待 Agent 主体完成。
- 使用独立 Profile 打开本地固定测试站点。
- 完成导航、语义快照、点击、输入和截图。
- 用户看到的页面与自动化控制的是同一页面状态。
- 关闭页面和应用后清理浏览器进程。
- PoC 可以先使用固定脚本驱动，不要求接入真实模型或形成完整产品 UI。

**验收：** 固定脚本在可见页面完成表单操作并生成截图；页面状态一致、Profile 隔离、退出后无残留进程。若 Playwright/CDP 无法稳定控制 Electron 可见页面，必须在 Electron CDP 直控和独立 Playwright Chromium 之间记录并选择一种方案。

### MVP-13 多 Agent 团队与持续接单

- Team Lead 使用长期可恢复 Thread，持续接收 WorkItem。
- Team Lead 或执行 Agent 可以根据复杂度主动将 WorkItem 拆成可恢复 Task 列表，并在对话中逐项更新。
- 创建任务列表与创建 Subagent 分离；同一 Agent 可以顺序完成全部 Task。
- 支持直接模式、临时 Subagent 和最多三个并发 Worker。
- Task 支持依赖、分配、领取、取消、阻塞、失败和完成状态。
- 只有 Team Lead 能创建 Worker；Worker 可以建议增员，但不能递归组队。
- 调度必须记录候选过滤和分配理由。
- 临时 Agent 完成后释放运行资源；常驻 Agent 空闲时休眠并保留摘要。
- 用户在团队运行期间可以继续投递、排队和调整任务优先级。

**验收：** 单步骤任务不创建形式化任务列表或 Subagent；多阶段顺序任务由同一 Agent 主动建表并逐项完成；可并行复杂任务创建至少两个独立 Worker 并由 Team Lead 汇总；连续投递三个任务时状态和优先级正确；达到并发上限后任务排队；重启后团队、任务列表、修订和完成证据可恢复。

### MVP-14 多项目任务边界

- 一个 Team 可以登记多个本地 Project。
- 每个可执行 Task 只能绑定一个主 Project。
- 任务未指定项目且无法唯一判断时必须向用户澄清。
- 跨项目 WorkItem 拆成项目级 Task，分别建立上下文、审批、Diff 和结果。
- Agent 的项目熟悉度参与调度，但不能扩大其文件权限。

**验收：** 登记两个临时 Git 项目并分别投递任务，文件、命令、会话和 Diff 不串项目；跨项目任务被拆成两个 Task；构造使用另一项目路径的工具调用时被拒绝。

### MVP-15 多模型配置与选择

- 模型中心支持多个 Provider、多个端点和多个 Model Profile。
- 用户可以为端点选择已安装的对话协议 Adapter，并为每个模型配置上下文窗口、输入/输出上限和输出预留。
- Agent 模型策略支持 `inherit`、`fixed` 和 `auto`。
- 未配置 Agent 默认模型时，继承创建它的父对话当前实际模型。
- 用户可以在创建时指定模型，也可以通过对话或模型选择器修改下一 Run 或该 Agent 后续默认模型。
- ModelRouter 只能在用户允许且能力兼容的候选中选择，并记录选择原因。
- 模型切换从下一次模型调用生效，不在一个流式 Turn 或工具调用中间混用模型。
- 每个 Run 保存不可变模型快照，切换模型后按新模型能力和上下文窗口重建上下文。

**验收：** 配置两个不同 Provider 的三个模型；分别验证继承、创建时指定、AI 自动选择和用户动态更改。切换前后的 Run 显示准确模型，Thread 历史不丢失，禁用或不兼容模型不会被静默使用。

### MVP-16 MCP、Skill 与全 Agent 对话

- 支持本地 `stdio` 和远程 Streamable HTTP MCP Server 的登记、启停、连接测试和能力发现。
- 支持 Tools、Resources 和 Prompts，并将 MCP 工具映射到统一权限与审批。
- 支持内置、用户和项目 Skill 的发现、启停、依赖检查和按需加载。
- Skill 脚本只能通过受控工具运行，不能因为 Skill 已启用而绕过审批。
- Team Lead、常驻 Agent 和临时 Subagent 都有独立持久的逻辑对话 Thread，用户可以从团队面板打开对话窗口；它不对应独占 OS 线程或进程。
- 临时 Agent 释放运行资源后，历史对话、工具、审批、模型和 Artifact 仍可查看并可显式继续。

**验收：** 分别调用一个本地和远程 MCP 固定测试服务；启用一个依赖 MCP 的 Skill；验证权限拒绝、取消、Server 崩溃和重启恢复。打开任一临时 Agent Thread 能看到来源任务与完整用户可见过程，并可在同一 Thread 创建后续 Run。

## 5. 权限默认矩阵

| 操作 | MVP 默认策略 |
| --- | --- |
| 列出工作区目录 | 自动允许 |
| 读取工作区文件 | 自动允许 |
| 搜索工作区 | 自动允许 |
| Git status/diff/log | 自动允许 |
| 读取工作区外路径 | 每次审批 |
| 新建、修改、删除文件 | 每次审批 |
| 应用 Patch | 每次审批 |
| 执行命令 | 每次审批 |
| Git commit/push/reset/clean | MVP 不提供 |
| 添加对话文件或图片附件 | 用户主动选择；应用保存只读快照 |
| Agent 向网页上传文件、提交网页表单 | MVP 不提供 |
| MCP/Skill 发起的工具调用 | 按映射后的读取、写入、执行或联网策略处理 |

## 6. 非功能验收

### 6.1 稳定性

- 任一模型或工具错误不会导致桌面进程整体退出。
- 强制关闭应用后，已提交的会话事件保持可读。
- 中断 Run 不自动重放有副作用的操作。
- 应用退出时清理其启动的临时进程。
- Team Lead、WorkItem、Task、依赖和 Agent 状态在异常退出后保持一致；过期任务租约可以恢复。

### 6.2 性能

- 使用发布构建测试，不以开发态结果代替用户体验。
- 长会话消息列表和工具输出采用虚拟化或分段加载。
- 大型终端输出不得完整挂载到 DOM。
- 迁移后的 Markdown 长文保护不得低于 `md-king` 当前行为。
- 建立冷启动、首次可交互、大目录、长会话、大 Diff 和长输出基线；具体阈值由首轮基准确定后回填。
- 大量空闲 Agent 只保留持久状态，OS 线程、子进程和浏览器页面不得随 Agent 数量线性增长。
- 活跃 Run 通过全局并发器调度；超过上限时排队，不能为每个 Agent 创建常驻 `worker_threads`。

### 6.3 安全

- Renderer 开启 `contextIsolation`，关闭 `nodeIntegration`。
- Preload 只暴露具名 API，不暴露原始 IPC 或任意命令执行函数。
- API Key 不出现在日志、SQLite、错误详情和导出会话中。
- 所有跨进程输入经过 Schema 校验。

### 6.4 可测试性

- Agent Loop 可使用模拟模型完成确定性测试。
- 本地工具在临时工作区和临时 Git 仓库中测试。
- SQLite Migration、事务和恢复有集成测试。
- Electron 主流程有 Playwright 端到端测试。
- 团队调度使用模拟模型覆盖直接执行、委派、扩容、并发上限、依赖、失败替补和多项目隔离。
- ModelAdapter 使用合同测试覆盖至少两类 Provider，验证流式事件、Tool Calling、取消和错误映射。
- MCP 使用固定本地测试 Server 覆盖 `stdio`、Streamable HTTP、能力变化、超时和崩溃恢复。
- Skill 使用固定夹具覆盖发现、版本冲突、依赖、按需加载和权限不提升。
- 调度测试覆盖大量空闲 Agent、活动 Run 上限、共享 Worker Pool、排队、取消和资源释放。

## 7. MVP 完成演示

MVP 完成时必须现场执行以下流程，不能只展示单元测试：

1. 启动发布构建。
2. 选择预置测试仓库。
3. 创建会话，要求 Agent 修复一个带失败测试的小缺陷。
4. Agent 自动读取和搜索项目。
5. UI 展示 Patch 审批，用户批准。
6. UI 展示测试命令审批，用户批准。
7. Agent 根据测试结果完成或再次修正。
8. UI 展示最终 Diff、测试结果和完成摘要。
9. 关闭并重新打开应用。
10. 恢复该会话，确认消息、审批、工具结果和 Artifact 完整。
11. 在普通浏览器中启动 `apps/web`，确认同一 UI 能以 Mock 数据渲染。
12. 运行受管浏览器 PoC，确认固定页面操作、Profile 隔离和进程清理通过。
13. 投递一个简单任务，确认 Team Lead 不创建 Subagent。
14. 在第一个任务运行时连续投递两个新任务，确认收件、排队和优先级可见。
15. 投递一个可并行的复杂任务，确认至少两个 Worker 独立执行并由 Team Lead 汇总。
16. 登记第二个测试项目，确认项目级上下文、审批和 Diff 不串项目。
17. 重启应用，确认 Team、WorkItem、Task、Agent Thread 和队列状态恢复。
18. 配置两个不同 Provider、两种对话协议和自定义请求地址/上下文窗口，创建继承当前对话模型的 Subagent，再创建一个指定其他模型的 Agent。
19. 在常驻 Agent 对话中修改后续模型，确认下一 Run 切换且历史 Thread 不变。
20. 打开一个临时 Agent 的独立对话，确认模型、消息、工具、审批、Artifact 和来源任务可查看。
21. 连接本地与远程 MCP 固定服务并调用工具，确认权限和失败恢复生效。
22. 启用一个依赖 MCP 的 Skill，确认按需加载和 Run 快照记录正确。
23. 投递一个多阶段但不需要并行的任务，确认 AI 主动创建任务列表、同一 Agent 按依赖逐项完成，并在重启后恢复列表和证据。

## 8. MVP 完成定义

只有同时满足以下条件才称为第一阶段完成：

- 第 7 节演示完整通过。
- P0 单元、集成和端到端测试通过。
- `pnpm` 类型检查、Lint、测试和发布构建通过。
- 没有已知的工作区逃逸、未审批写入或密钥明文落盘问题。
- 文档与实际目录、命令、数据结构一致。
- 未完成能力明确留在后续列表，不以空按钮或假数据宣称可用。
