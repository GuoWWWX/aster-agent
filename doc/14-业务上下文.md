# 业务上下文

> 文档角色：产品与领域语义的长期维护入口  
> 当前快照：2026-08-27
> 适用范围：桌面 AI Agent 工作台、项目/临时对话、Agent/Subagent/团队、工具、上下文和会话资产  
> 当前实现事实以代码、Protocol、Migration 和测试为准；本文负责说明“为什么”和“应该保持什么业务语义”

## 1. 如何维护本文档

本文档不是一次性需求清单。发生以下变化时必须在同一个改动批次中更新：

- Agent、Subagent、团队或对话的定义变化。
- 用户主流程、权限、消息投递或任务状态变化。
- 上下文压缩、附件、归档和删除策略变化。
- 新增工具能力、MCP/Skill 或模型选择规则。
- 代码行为与本文档不一致，并已决定以哪一方为准。

维护规则：

1. “目标语义”和“当前实现状态”分开写，不能把规划写成已完成。
2. 已确认的业务决定写入第 13 节决策记录，不只修改正文。
3. 代码是当前运行行为的事实源；本文档和验收标准是产品意图的事实源。
4. 发现差异时先新增“待处理差异”，再通过测试修代码或修正过期文档。
5. 不在多份文档重复完整规则；接口字段链接到 `02`，工具细节链接到 `11`，编码要求链接到 `13`。

## 2. 产品定位

本产品是一款本地优先的桌面 AI Agent 工作台。用户可以直接抛出想法或任务，让当前 Agent 在授权项目中读取、搜索、编辑文件并执行命令；简单任务直接处理，复杂任务可建立任务清单、创建一次性 Subagent，或交给长期团队中的合适 Agent。

核心不是“聊天”，而是以下闭环：

```text
接收目标
  -> 理解项目和权限
  -> 规划或直接执行
  -> 调用受控工具
  -> 展示过程、Diff、命令和错误
  -> 持久化结果与上下文
  -> 可恢复地继续后续任务
```

UI 复用 `md-king` 的布局和 Markdown 渲染体验，但产品主对象已经从 Markdown 文档变为 Agent 对话、任务、工具过程和项目工作区。

## 3. 核心用户诉求

### 3.1 真正执行

Agent 不能只给建议。获得权限后，它应能搜索项目、读取文件、创建/编辑/删除文件、应用 Patch、执行命令、等待长任务并根据结果继续。

### 3.2 过程透明

用户需要看到：

- Agent 当前是否工作、等待、失败或完成。
- 实际执行的命令和 stdout/stderr。
- 读取了哪些文件和范围。
- 创建、删除、修改了哪些文件；修改用 Diff 展示。
- Task 进行到哪一步，Subagent 在做什么。
- 错误属于哪个操作，是否可重试。

工具结果默认折叠；用户主动展开查看详情。错误显示在所属工具或 Assistant 输出位置，不形成长期悬浮的无归属错误。
模型接口错误在 Assistant 时间线显示 md-king 风格的静态引用块，直接展示网络、认证、额度、超时、上游、响应或内部错误分类以及脱敏后的详情；工具错误留在对应工具行内，工具卡片的原始参数和长结果仍可展开，错误正文不再二次折叠；普通界面操作失败显示在当前工作区操作区域。错误编号只用于关联本次错误实例，不代表 HTTP 状态或模型错误码，也不展示给用户。

### 3.3 操作可控

文件写入、Patch、命令和会产生外部副作用的网络操作遵守当前权限模式。公共只读 `web_search` 可以直接查询，但查询词、来源和结果仍进入工具审计。模型提出需要审批的工具调用不等于获得批准。用户可以取消 Run、停止长命令、关闭任务清单、调整待发送消息和修改后续 Agent 的模型。

### 3.4 可恢复和长期使用

项目、对话、消息、Run、任务清单、Subagent、Agent 消息、附件和上下文 Checkpoint 都要持久化。应用重启后不能只恢复聊天文字而丢失任务、工具状态或来源关系。

### 3.5 简单任务保持简单

任务清单、Subagent 和团队不是每次对话的强制流程。单步骤任务由当前 Agent 直接执行；只有存在多阶段验收、独立支线、专业分工或真实并行收益时才增加协调成本。

## 4. 领域词汇

| 名称 | 业务含义 | 关键边界 |
| --- | --- | --- |
| Project | 用户登记的本地文件夹 | 提供默认工作区根目录，不等于把全项目塞入上下文 |
| Conversation / Thread | 可查看、持久化的逻辑对话 | 每个 Agent 有独立对话；不对应 OS 线程 |
| Agent | 能独立维护上下文并执行 Run 的逻辑角色 | 使用统一上下文和会话管理逻辑 |
| Main Agent | 用户当前直接交流的 Agent | 可直接执行、规划、委派和汇总 |
| Subagent | 为一次明确任务临时创建的 Agent | 本次任务完成后停止工作，但对话和结果继续保存 |
| Standing Agent | 团队中的长期 Agent | 可持续接收后续任务，拥有独立对话 |
| Team Lead | 长期团队的负责人 Agent | 接收 WorkItem、判断直接做还是委派、汇总结果 |
| Run | 一次模型与工具循环 | 有明确开始、终态、模型快照和取消语义 |
| WorkItem | 用户持续投递的一项想法或需求 | 可跨项目，但执行前拆成项目级 Task |
| Task | 可调度、可验收的执行单元 | 绑定一个主项目，可有依赖和负责人 |
| Task List | 当前对话内的执行步骤投影 | 用于多阶段任务，不等于创建 Subagent |
| Pending Message | Agent 忙时用户继续发送的消息 | 使用 Queue 或 Steer 语义 |
| Tool Call | 模型请求执行的受控操作 | 经过 Schema、权限、工作区和生命周期管理 |
| Artifact | 长日志、Diff、截图等大结果 | 数据库保存索引，正文存应用数据目录 |
| Attachment | 用户显式添加到消息的文件/图片快照 | 与项目文件工具读取不同，参与上下文预算 |
| Context Checkpoint | 对旧对话前缀的结构化压缩结果 | 不删除 UI 原始历史，覆盖范围只能前进 |
| Conversation Deletion Task | 会话树与附件的可恢复删除事实 | 先隐藏待删会话，文件成功后再原子删除数据库记录 |
| Model Profile | Provider 下一个可选模型及能力配置 | 包含上下文窗口、输出限制、思考程度选项和供应商品牌展示标识 |
| MCP | 外部工具/资源/提示的标准接入协议 | 不能绕过本地权限与项目边界 |
| Skill | 可发现、启用的任务说明和能力组合 | 不能直接获得 Node/Shell 权限 |

## 5. 项目与对话

### 5.1 项目对话

- 用户添加 Project 时登记一个本地文件夹。
- 在 Project 下创建的对话默认知道该项目根目录，不需要模型先调用工具查询“当前目录”。
- 工作区路径由 Runtime 根据 `conversationId -> projectId` 动态解析，不能硬编码进 Prompt 或让模型提供任意根路径。
- 项目可以有多层目录。Agent 通过 `list_directory`、`find_files`、`search_text` 和 `read_file` 按需探索，不自动读取全项目。
- 左侧导航展示项目和对话；右侧文件栏展示项目实际文件，两种树的业务职责不同。

### 5.2 临时对话

- 不添加项目也可以创建临时对话并正常与模型交流。
- 临时对话只是没有关联项目工作区，不等于不能使用工具。`run_command`、`read_external_file`、`wait_for_commands`、`stop_command`、`web_search`、Agent/Subagent、任务清单和已配置的附件工具仍可用。
- 临时对话的命令在该对话独立的系统临时目录执行，不访问项目目录，也不能读取或停止其他临时对话的命令会话；命令仍遵守只读、询问或完全访问权限模式。
- 依赖授权项目路径的目录、文件、项目搜索、文件变更和项目冲突工具仍不可用；`read_external_file` 只接受绝对路径，正文读取前必须逐次审批。
- 用户可通过系统目录选择器显式附加、替换或移除一个会话工作目录。
- 附加目录后，其路径随会话持久化；模型使用方式与项目工作区一致。

### 5.3 对话状态

- 正在运行时在列表和输入框显示工作状态。`activeRunId` 只表示当前可取消的模型 Run；父对话即使自身 Run 已结束，只要仍有直接 Subagent 或右侧侧边聊天处于 `queued` 或 `running`，左侧父对话项仍必须保持运行中。切换对话或收起工作区不能丢失正在运行的进度提示。
- 主对话或其右侧侧边聊天完成时，左侧父对话项显示蓝色未读圆点；失败时显示红色未读圆点。即使用户一直停留在该对话，运行结束时也先显示标记；用户之后点击父对话，或在主对话、任一侧边聊天中点击、输入、发送或主动滚动，才确认该组结果并清除标记。模型输出导致的自动滚动不算用户确认。
- 归档对话不再接收新 Run、Agent 消息或 Subagent。
- 归档可恢复；当前保留期为 30 天，超过保留期进入自动删除。
- 删除必须包含对话树、无引用附件和相关运行数据，并采用可恢复清理流程。

### 5.4 对话 Fork 与侧边对话

- Assistant 回复下方的分叉按钮创建同一项目或临时分组内的普通同级对话，不创建右侧侧边聊天，也不创建 `subagent_tasks`；这是一次物化复制，不建立源对话与新对话之间的继承关系。
- 同级分叉名称以源对话当前名称为基准，依次使用 `源名称 (1)`、`源名称 (2)`；新对话 `parentConversationId = null`，因此删除源对话不会级联删除同级分叉。
- 回复分叉只冻结截至该轮最终回复的模型消息，后续消息和工具过程不能进入分支；右侧菜单创建侧边聊天时冻结父对话当前有效模型上下文和已绑定 Agent 身份：没有 Checkpoint 时继承全部消息，已有 Checkpoint 时继承摘要和其后未覆盖消息。
- 指定回复之前存在可用 Context Checkpoint 时，将该摘要和其后未覆盖消息复制到新对话；如果源对话当前 Checkpoint 已覆盖到该回复之后，则不复制这个未来摘要，而是保留截至该回复的原始模型消息。
- 同级回复分叉会把边界内的用户消息、Assistant 回复、工具过程和附件完整复制到新 Timeline，因此用户可以看到分叉点之前的全部历史；消息、Run 和附件均使用新 ID，后续编辑或再次分叉只作用于新对话。
- 右侧侧边聊天的继承历史仍只进入模型上下文，不复制到侧边 Timeline，界面只显示侧边聊天创建后的新消息和工具过程。
- Fork 后源对话、新同级对话和右侧侧边对话均独立写入；源对话后续新增消息不会自动同步。
- 右侧侧边对话继续使用普通 `agent` 身份和 `parentConversationId`，只存在于父对话右侧标签区，不进入左侧对话树；任务 Subagent 使用 `threadKind = subagent` 并以持久 `subagent_tasks` 记录作为生命周期事实，不能仅凭父子关系把侧边对话识别成 Subagent。
- 用户关闭右侧侧边聊天标签时，关闭即删除该侧边聊天及其临时 ThreadLog JSONL；删除成功后不再提供“重新打开”入口，也不会在下次进入父对话时恢复。普通文件和配置文件标签仍只关闭标签，不删除文件。
- 右侧工作区可打开 Git 工作区、项目 PTY 终端和隔离浏览器标签。Git 工作区采用提交工作区布局：顶部集中分支与同步操作，中部按已跟踪更改和未跟踪文件分组，复选框表示暂存状态，底部固定提交说明以及“提交”“提交并推送”；按文件展示状态与右对齐的增删行数，使用向右/向下箭头在对应文件行下方收起或展开结构化 Diff。该 Diff 与对话中修改文件工具共用同一渲染组件，代码正文沿用项目代码块的语法高亮，新增/删除只叠加浅绿/浅红色带并为行号保留对应语义色，不把整行代码正文染成状态色。文件树、Git 审阅、标签、附件、文件引用、文件搜索结果和 Markdown 文件链接共用文件类型图标映射；Word、Excel、PowerPoint 等办公文档按扩展名显示对应图标，现代格式使用实心色块，旧格式和 CSV/TSV 使用彩色描边、白色中间的版本，普通网页链接不伪装成文件。它允许用户显式暂存、提交、创建/切换本地分支、快进拉取和普通推送；项目目录位于仓库子目录时仍以仓库根目录解析 Git 路径。它不暴露任意 Git 参数，也不提供丢弃修改、硬重置或强推。终端以项目根目录和用户设置的默认 Shell 启动；浏览器使用 Electron 自带的 Chromium 内核，只允许无凭据的 HTTP/HTTPS 导航，拒绝权限和下载。默认首页和地址栏文本搜索使用 Google；域名、IP、`localhost` 和显式 HTTP/HTTPS 地址仍直接导航。浏览器标签独立保存当前缩放，支持 `Ctrl + 鼠标滚轮` 和菜单调整；设置页保存新标签的默认缩放。当前活动的对话或工具页始终保活；非活动页最多保留 8 个、最长 1 小时。短期切换保留 Git 快照/Diff、终端 PTY 和浏览器 View；超时或超量后释放资源，重新打开时 Git 重新加载、终端重新启动、浏览器从上次 URL 加载。三点菜单显示期间保持实时网页持续可见，不切换快照、不隐藏 View，也不重载或重建浏览器会话。三者是用户工作区能力，不自动成为模型可调用工具。
- 项目对话中的模型可使用持久终端工具：`create_terminal(name?)`（`open_terminal` 为兼容别名）创建与用户共享的可见 PTY，`execute_terminal_command` 向同一 PTY 写入命令，`read_terminal_output` 以游标读取有界新增输出。普通非交互命令、构建、检查和测试默认使用 `run_command`，不会打开侧边标签；只有用户明确要求可见/右侧/交互终端，或任务确实需要持续 PTY 时才使用持久终端工具。创建和命令先按 `command-run` 应用策略及当前对话权限模式审批，批准后才进入项目操作协调并产生可见副作用；读取已有输出不审批。它与一次性、可等待的 `run_command` 生命周期互不替代；模型不能指定 Shell、工作目录，也不能接管其他对话或用户手动打开的终端，只能复用终端工具在当前应用会话中返回给当前对话的活动 ID。PTY 与 `terminalId` 只在当前桌面主进程和终端进程存活期间有效；失效后工具返回 `TERMINAL_UNAVAILABLE` 与重建指令，模型创建新终端后再重试。即时输出等待超过 5000 毫秒时按 5000 毫秒采样，不把整次命令判为参数失败。标签与现有文件、聊天和工具标签重名时，Renderer 使用 `名称 (1)`、`名称 (2)` 生成唯一名称，并把实际 `resolvedName` 返回给模型。
- `agent.browser` 是首方浏览器工具插件：模型创建的隔离浏览器同样会成为用户可见的侧边标签，模型按“观察有界 DOM 文本和元素引用 → 以引用进行导航、点击、填写、选择、按键、滚动或等待 → 再观察”的循环操作。打开、导航、交互和关闭均按独立 `browser-control` 策略审批，默认询问；观察和等待只读取有界状态。它不提供任意 JavaScript 执行、凭据 URL、权限申请或下载；浏览器只归属创建它的项目对话，模型关闭时同步关闭该侧边标签。
- Git 审阅中的复选框只表示用户当前选择，不会在勾选时修改 Git 暂存区；“未跟踪文件”组右侧的加号会跟踪并暂存已选路径，“已跟踪更改”组右侧的减号会取消跟踪已选路径但保留其本地文件。提交操作会只处理已选路径，且不得带入其他已暂存但未选的文件。

### 5.6 一轮多工具调用

- 模型可以在同一轮混合返回最多 32 个 Tool Call；超过上限时整批不执行。Runtime 将连续只读调用按最多 8 个一组并发执行，并按调用 ID 保持结果对应关系。
- 文件写入、消息投递和任务状态操作不因为同轮返回多个调用就自动并发；非 `read_only` 权限下，同一连续组的独立命令默认并行，依赖命令可用 `parallel=false` 强制串行，并且每组最多同时运行 4 个命令。询问模式仍逐条审批，但已批准的独立命令可以并行。
- 同一批文件变更先固定各自读取时的文件版本。若多个调用指向同一文件，先完成的变更生效，后续旧变更作废并要求模型重新读取；不同文件逐个审批/写入，当前不提供多文件事务回滚。

### 5.5 消息复制、分支与重新生成

- Assistant 的每轮最终回复提供复制和分叉操作；复制按该回复的 `runId` 导出同一 Run 的 Assistant Markdown、命令及 stdout/stderr、文件 Diff 和其他有界工具结果，使用 Markdown 代码块保留命令输出；不导出用户消息、隐藏 reasoning 或内部工具 JSON。分叉以该回复为上下文边界创建并打开左侧同级对话，不把回复转换成 Markdown 引用插入输入框。
- 对话中的一次性命令结果使用代码块式紧凑表面，标题只显示实际 Shell 名称，不展示输出编码、状态或内部命令 ID；右上角复制按钮复制当前可见的命令与输出。Assistant Markdown 围栏代码块同样在右上角提供复制按钮。
- 用户消息显示发送时间并提供复制操作；时间按用户本地日历显示为当天时分、昨天时分、同年日期时分或跨年完整日期；只有最后一条已经发送给模型的用户消息可以编辑，排队消息继续使用队列自身的编辑能力。
- Assistant 最终回复在悬停时于回复左下角显示完成时间、复制和分叉操作；回复上方常驻显示整轮总耗时并以下分割线与正文分开，耗时依次使用秒、分、小时、天的紧凑组合。该元信息只呈现持久 Run 事实，不展示模型私有推理。
- 模型供应商主动返回的 Reasoning 按语义展示：完整思考内容在 Assistant 消息内以折叠块实时展开，完成后收起并保留；思考摘要只在当前请求期间实时显示，正文开始、工具开始或 Run 结束后清除。两者都不混入 Assistant 正文或复制结果，也不采集供应商未返回的私有推理。
- 编辑重新发送会复用原用户消息 ID 和附件，删除该消息所属旧 Run 在其后产生的 Assistant/工具 Timeline 与模型上下文，再创建新 Run 重新回答。
- 旧 Run 仍作为审计事实保留。已经执行的命令、文件写入和其他外部副作用不会随消息编辑自动回滚。
- 若旧 Run 正在回答，Runtime 先取消并等待其完成清理，再原子替换消息并启动新 Run；替换期间不能让旧 Run 自动消费待发送队列。

## 6. Agent、Subagent 与团队

### 6.1 所有 Agent 使用同一会话核心

无论通过普通对话、项目对话、Subagent 还是团队创建，Agent 都使用同一套：

- 消息与 Timeline 持久化。
- Run 状态机。
- 模型选择和 Run 快照。
- 工具、权限和项目边界。
- 上下文预算、压缩和附件处理。
- 错误、取消和恢复。

不同类型 Agent 的差异由生命周期、来源任务和调度关系表达，不复制另一套聊天后端。

### 6.2 Subagent 生命周期

- Main Agent 只在任务可独立、需要专门上下文或有并行收益时创建 Subagent。
- Subagent 有自己的 Conversation、模型、工作区和 Run。
- 创建 Subagent 时，模型可以分别提供简短显示名称和受控图标 ID；图标只能来自 Agent 共用的预设目录。未指定时优先继承所选 Agent 的预设图标，否则由系统生成稳定回退。名称和图标随子 Conversation 持久化，任务正文不充当唯一身份字段。
- Subagent 完成本次任务后进入完成/停止状态，不能像 Standing Agent 一样继续长期接单。
- 子对话和完整用户可见过程继续保存，用户可以从父对话或对话树打开。
- 父对话接收最多约定长度的结构化完成摘要、状态和子对话引用，不把完整子对话一次性注入父上下文。
- 父 Agent 需要细节时使用 `read_agent_conversation` 按 Token 预算读取。
- 父对话可以同步等待，也可以继续自己的工作；Subagent 完成时会发送持久完成事实并激活需要继续的父对话。父 Run 已结束但仍有运行中 Subagent 时，父对话仍处于运行态；最后一个 Subagent 结束后，Runtime 先提交任务终态和结构化结果，再降低运行计数并按需创建新的父 Run。
- Subagent 完成通知只作为后台结构化事实和父 Agent 的模型上下文输入，不写入父对话 Timeline，不在主对话页面显示普通消息卡片；需要详情时按预算读取子对话。
- Subagent 的审批仍归属于子对话的 Tool 和 Run；子对话展示完整工具卡，父对话在输入框上方展示同一审批的可操作投影。任一入口提交决定后都作用于同一后台审批，不能复制审批事实或让模型代替用户批准。

### 6.3 长期团队

- Team Lead 是长期存在的团队负责人身份；同一来源主 Conversation 调用同一 Team 时复用一个 Team Lead 执行 Conversation 及其成员 Conversation。WorkItem 仍是独立的排队、运行、审计与验收单元，并在该执行根上串行推进，避免并发任务混淆当前策略。
- 普通主 Conversation 中未交给团队的简单任务仍由当前 Agent 直接完成。WorkItem 一旦交给默认团队，Team Lead 必须至少通过 `send_agent_message(expectReply=true)` 委派一位持久专业成员；简单任务只走一位成员的短路径，不强制执行完整团队流程。
- 默认团队由 Team Lead、需求分析师、架构师、前端开发、后端开发和测试工程师组成。常规任务按实际需要激活少量岗位，跨端或存在真实并行收益时才同时调度多个开发成员；Team Lead 负责边界、调度、验收和汇总，不替代成员完成专业实现。
- 已有合适 Standing Agent 时优先复用；确实缺少能力且有收益时才临时扩容。
- 扩容受并发、Token、时间、项目权限和文件冲突限制。
- 一个团队可登记多个 Project，但每个可执行 Task 只绑定一个主项目。
- 跨项目需求拆为多个项目级 Task，各自建立工作区、审批、Diff 和结果。

当前“完整团队 Supervisor、自动招聘、租约和多 Worker 调度”仍属于目标能力，不能因为已有 Subagent 工具就宣称团队模式已完整实现。

当前已实现的第一条团队执行竖切以 `WorkItem` 为调度和验收边界：用户在项目主 Conversation 中以 `@团队` 明确交办，当前模型才可调用 `submit_team_work_item` 创建 WorkItem；前端没有直投下拉或第二个发送入口。工具验证来源 Conversation 是同一项目、未归档且非受管的主 Conversation，并持久化来源 ID、模型/推理快照和权限模式。需求持久化后按团队 `maxWorkers` 进入容量调度；同一来源主 Conversation 与 Team 复用一个绑定 Team/Project 的 `team_lead` Conversation，并在其下保留 Team 配置成员的持久 `agent` Conversation。已启用团队在有容量时自动分发新的 WorkItem；同一执行根有运行中 WorkItem 时后续需求保持 `queued`，其余来源可在容量内并行。暂停团队仍可入箱但不会启动 Run，设置恢复启用时重新检查队列。用户可在 Team Lead 领取前编辑 `queued` 需求；保存原子地检查状态、更新标题和正文，并写入审计事件，领取后必须走返工/验收流程。实际成员位于 Team Lead 下，左侧项目导航将其作为来源主 Conversation 下的协作层级显示。执行 Conversation 继续使用统一 AgentRuntime，Team Lead 通过 `send_agent_message` / `wait_for_agent_message` 向持久成员分派、等待与汇总；团队 Conversation 不注册 `spawn_subagent`。根 Run 成功时不会立刻推进验收：必须先确认持久成员没有排队或运行中的 Run，且 Team Lead 已消费所有已送达的成员结果；否则 WorkItem 保持 `running`，等待自动协调 Run。条件满足后才进入 `waiting_user`，用户明确验收后才进入 `completed`；返工在同一执行 Conversation 创建新 Run 并递增修订号。受管成员 Tab 与普通对话同样可改模型、思考和权限：选择模型/思考会原子写回当前成员 Conversation 和 WorkItem，供后续返工或自动汇总 Run 使用；权限写回 WorkItem。当前已启动的 Run 与已经展示的审批继续使用其不可变快照。冻结配置失效时显式标记阻塞，终态 WorkItem 不会因迟到成员消息重新启动。WorkItem 根和其持久化成员不能被直接归档、删除、改项目或改 Agent，普通侧边对话不受此限制。〔FACT｜`apps/desktop/src/main/teams/team-work-item-runtime.ts`；`apps/desktop/src/main/agent/agent-runtime.ts`〕

团队页按 WorkItem 的持久 Team Lead/成员关系以及成员消息分派显示真实参与者，但只承担需求、任务、阶段、验收和成员状态的控制台职责，不在中间区域嵌入成员原生 Conversation。用户从 WorkItem 或成员状态行打开成员时，主 Conversation 保持选中和可输入，成员原生 Timeline 在右侧以侧边 Tab 打开；左侧协作层级中的成员点击也是同一行为。受管成员 Tab 与主/普通侧边对话使用同一套输入框、模型与思考选择、权限选择、排队显示、停止、审批和任务清单关闭入口。运行中发送的补充或纠正仍强制作为当前 Run 的 `steer` 在安全边界消费；当前 Run 的模型、思考和权限快照不追溯改变，新的模型/思考与权限分别用于后续团队执行。成员不在运行时，用户必须从 WorkItem 返工/验收入口继续，不能由该输入框新建脱离生命周期的 Run。Agent、项目、归档和删除仍受 WorkItem 锁定。Run 停止、失败或重启恢复后，仍为 `awaiting_approval` 的工具卡必须持久化为已失效，不能继续显示审批按钮；Task List 中残留的 `running` 步骤也不能继续显示转圈。仅凭 `parentConversationId` 关联的普通侧边聊天不属于团队成员，不能混入团队状态。〔FACT｜`apps/desktop/src/main/teams/team-work-item-runtime.ts`；`apps/web/src/features/projects/project-navigator.tsx`；`apps/web/src/features/workspace/right-sidebar-workspace.tsx`〕

## 7. Agent 间通信与唤醒

### 7.1 消息身份

Agent 消息必须保存：

- 来源 Conversation/Agent ID 和显示名称。
- 目标 Conversation/Agent ID。
- 消息类型、正文、创建时间和处理状态。
- 如为回复，能够定位原来源。

接收方 UI 按用户消息的气泡逻辑显示，但在气泡上方标注来源 Agent；点击可跳转来源对话。它不能伪装成用户，也不能携带用户审批权限。

### 7.2 接收与回复

- 目标 Agent 空闲时，Agent 消息按一次外部输入创建 Run 并调用模型。
- 目标 Agent 正忙时，消息进入待处理队列，在安全边界消费。
- 回复可显式调用 `send_agent_message` 发回来源。
- 对于 Subagent 完成，系统还提供结构化完成通知；不要求 Subagent 把全部输出复制成普通对话消息。

### 7.3 取消中的流式内容

- 模型请求在尚未产生 Assistant 文本或工具调用时，如果遇到可重试网络错误、限流、服务端错误或空响应，按退避规则最多重试 5 次。
- 已经收到 Assistant 文本或工具调用后不得自动重放本次模型请求，避免重复展示内容或重复触发副作用。
- 用户取消 Run 时，已经收到的 Assistant 文本必须以 `status=cancelled` 的 Assistant Timeline 和模型消息保留；未收到内容不补写。
- 如果本轮 Assistant 内容已经因工具回合提交，则取消不会重复插入同一段内容；后续工具过程仍按已发生事实保留。

### 7.4 读取其他对话

- 用户在输入框中 `@` 某个对话时，当前 Agent 获得一个有上限的对话引用。
- 未压缩对话按预算读取最近相关内容；已压缩对话从最新 Checkpoint 加未覆盖的新消息开始。
- 不能一次把另一个对话全部注入，避免撑满当前模型上下文。
- Agent 可用 `list_agent_conversations` 和 `read_agent_conversation` 主动按页/预算读取更多。

### 7.5 等待与激活

- `wait_for_subagents` 等待一个或多个子任务完成。
- `wait_for_agent_message` 等待其他对话消息。
- `wait_for_commands` 等待一个或多个后台命令。
- `wait_for_project_operation` 等待冲突的项目写操作。
- 等待是 Runtime 状态，不占用 OS 线程轮询。
- 对话即使暂时没有活动 Run，收到 Subagent/Agent 完成事实后也能被标记待处理并重新激活。

## 8. 用户消息 Queue 与 Steer

### 8.1 Queue 模式

Queue 是初始默认模式。Agent 忙时用户发送的多条消息按顺序保存并逐条消费。

用户可以：

- 查看队列。
- 编辑某条消息，保持原顺序不变。
- 调整消息顺序。
- 删除未消费消息。
- 把某条消息提升为下一条发送。

### 8.2 Steer 模式

Steer 表示“尽快把新信息交给当前 Agent”，不是强制打断正在执行的副作用。

- 已开始的文件写、命令、审批和工具结果先到安全边界。
- 下一次模型调用构造上下文时注入 Steer 消息。
- Steer 消息作为新的用户输入保存，不覆盖原始请求。
- 多条 Steer 消息按创建顺序合并/注入，且必须能追溯。
- 如果当前 Run 已到终态，则按新 Run 处理。

设置页配置新对话默认模式；对话输入区可临时切换当前发送方式。

## 9. 任务清单

### 9.1 何时创建

任务需要多个可观察步骤、存在依赖或用户需要阶段进度时，Agent 可以主动创建 Task List。简单问答、单文件小改和一步命令不创建形式化列表。

### 9.2 操作

Agent 工具至少支持：

- `create_task_list`：创建步骤。
- `update_task_list`：修改步骤、内容和状态。
- `close_task_list`：关闭当前列表；当前语义等同删除活动 Task List 记录并从对话界面移除。

用户也可以手动关闭；受管 Team 成员的侧边 Tab 也保留此入口。关闭不删除整个对话、既有消息或已经落入 Timeline/工具结果的过程记录。

### 9.3 状态与 UI

- 未开始（`pending`）：不显示运行图标。
- 运行中（`running`）：显示转圈状态。
- 已完成（`completed`）：显示对号。
- 阻塞（`blocked`）：等待用户审批、外部输入或其他可恢复依赖；必须保存并显示一条简短 `reason`，不能被 Run 终态自动改写。
- 失败（`failed`）：当前步骤无法继续；必须保存并显示一条简短 `reason`，详细错误仍以对应 Assistant/工具事实为准，不能被 Run 终态自动改写。
- `running` 只在该 Conversation 仍有活动 Run 时转圈。Run 被用户停止、失败或已完成但清单尚未更新时，Renderer 分别显示“已停止”“已中断”或“待继续”，不把这个展示投影反写为模型控制的 Task 状态。
- 列表位于输入框上方，可展开/收起。
- 若任务修改了文件，列表摘要可以显示变更数量或入口，但 Diff 仍以工具/文件事实为准。

任务清单与 Subagent 分离：同一 Agent 可以按列表顺序完成全部步骤，不因创建列表自动创建新 Agent。

Task List 是模型控制的持久工作事实。Run 成功结束只表示本次模型执行结束，不表示计划步骤已经完成；状态只能由 `update_task_list`、明确的运行时失败/阻塞事件或用户操作推进。

## 10. 文件、附件和工具

### 10.1 项目文件与消息附件

二者对模型最终都是“文件内容”，但生命周期不同：

| 类型 | 获取方式 | 内容时点 | 存储 |
| --- | --- | --- | --- |
| 项目文件工具 | Agent 按路径读取 | 读取时的实时内容 | 原项目目录 |
| 消息附件 | 用户从输入框选择，或直接粘贴文件/截图 | 发送时点不可变快照 | `userData/conversation-files/<conversationId>/` |
| `@文件` 引用 | 用户输入匹配后选择 | 当前工作区文件，按引用时规则读取/快照 | 由消息合同记录引用 |

输入 `@` 或 `/` 时，用户尚未输入匹配文字不加载和展示全部文件/对话；开始输入后只返回有限匹配结果，避免大型项目卡顿。

### 10.2 附件限制

- 每条消息最多 10 个附件。
- 单个附件最多 25 MB。
- 选择和粘贴共用同一附件草稿列表；发送前可以逐个移除，发送成功后随消息固定并清空草稿。
- 文本、代码、PDF、DOCX 提取 UTF-8 预览；长文本按头尾截断，全文通过 `read_attachment` 分段读取。
- 图片不把 Base64 写入 SQLite；构造模型请求时按协议生成多模态块。
- 文本模型明确拒绝图片时，若当前消息没有新图片且请求尚未输出，历史图片可在模型适配层降级为可审计的附件文字说明并重试一次；当前消息的新图片不允许静默降级。
- 附件 Token 与文字、工具 Schema 一起参与本轮上下文预算。
- 本轮内容自身超出最低预算时，不创建 Run、不绑定草稿附件，并给出可操作错误。

### 10.3 内置项目工具

当前工具合同包括：

```text
list_directory
read_file
search_text
find_files
write_file
delete_file
replace_in_file
apply_patch
run_command
list_project_operations
wait_for_project_operation
wait_for_commands
stop_command
read_attachment
web_search
```

- `search_text` 使用应用内置 ripgrep 做内容搜索。
- `find_files` 用于路径/文件名匹配。
- 模型仍可在需要复杂参数或组合查询时通过 `run_command` 执行 `rg`，但不能假设用户系统 PATH 已安装。
- 多处编辑优先使用结构化 Patch 或批量替换，不通过脆弱的整文件字符串拼接。

### 10.4 冲突协调

- 并行读取通常允许。
- 同项目的文件写、Patch 和可能修改文件的命令进入项目操作协调。
- 不同对话即使以不同 ID 挂载同一物理目录，也属于同一冲突域。
- Agent 尝试冲突操作时应获得占用 operation/conversation 信息。
- 冲突请求立即作废；Agent 可以等待或联系占用方，但完成等待后必须基于最新状态生成新请求，不能原样重放旧参数。
- 锁是冲突提示和一致性保护，不是把每个 Agent 绑定到独立线程。

## 11. 模型、权限和扩展

### 11.1 模型选择

- 用户可以配置多个 Provider、Base URL、API 格式、Key 和模型。
- 支持 OpenAI Chat Completions、OpenAI Responses、Anthropic Messages、Google Gemini 四种 API 格式。
- Provider 可选择主流模型厂商或中转站的品牌图标；未选择时按供应商名称显示 1 至 2 个字符。该标识只影响设置、模型选择和列表展示，不改变模型请求、认证或 Run 快照语义。
- 模型可配置上下文窗口、输入/输出上限、思考程度选项和默认值。
- 设置中的默认模型是最终兜底，不强制覆盖每个新对话。普通新对话优先继承最近一次用户在普通或侧边对话中手动选择的 Provider、模型和思考程度；没有有效最近选择时才使用默认模型。
- 每个 Conversation 持久化自己的模型选择。侧边对话和新 Subagent 在创建时复制父对话当时的选择，创建后互不联动；Subagent 的模型使用和内部变更不更新全局最近用户选择。
- 切换对话、折叠或重新展开右侧工作区时，只恢复目标 Conversation 已持久化的模型选择；最近选择和默认模型不能再次覆盖一个已经初始化的 Conversation。
- Renderer 保活当前 Conversation 以及最近一小时内访问过的最多 8 个页面；其他页面重新从持久化数据加载。页面缓存只用于切换体验，不是消息、模型选择或运行状态的事实源，归档、删除或移除项目后必须立即停止渲染对应缓存页面。
- Main Agent 可通过 `list_models` 按需读取不含凭据的模型目录、已启用思考选项、连接状态、状态更新时间和最近成功时间。`spawn_subagent` 未显式指定时继承父对话；显式指定时必须同时提供已配置的 `providerId` 与 `modelId`，并校验思考选项。
- 连接测试和真实对话成功都会把模型标记为可用并更新最近成功时间；失败更新当前状态和状态时间，但保留上一次成功时间，供后续选择判断新鲜度。
- 每个 Run 保存不可变模型快照。配置变化只影响后续模型调用。
- 对话输入区只显示当前模型和已解析的思考程度；完整选项在设置中配置。

### 11.2 权限模式

当前业务模式：

- `read_only`：只读，不允许文件变更和命令副作用。
- `ask_before_changes`：变更前逐次询问。
- `full_access`：在授权项目范围内按用户配置执行；仍不能越界或泄漏密钥。

权限模式不能扩大工作区。即使 Full Access，也不能访问未授权目录、伪造用户审批或跳过稳定安全校验。

审批中的副作用工具可以选择“本次允许”“本会话允许”“Agent 一直允许”或“拒绝”。本会话授权只保存在 Main 内存并绑定 conversation；Agent 长期授权保存到对应 Agent Profile 的 `permissions.allow`，可在 Agent 配置页查看和编辑。命令规则支持完整命令精确匹配，或仅在末尾使用 `*` 的前缀匹配，例如 `mvn package *`；不匹配的命令和文件变更仍需审批。工作区外文件读取无论权限模式如何都只能本次允许，审批前不读取正文。

当所属 Run 已停止、失败或因应用重启被中断时，仍未决定的审批会持久化为“已失效”；Timeline 不再渲染允许/拒绝操作，避免向已经不存在的 LangGraph interrupt 提交决定。

Subagent 创建时继承父 Run 的权限模式，但不会继承父对话的一次性或会话授权；`scope=session` 始终绑定实际执行工具的子 conversation。只有子对话绑定同一个 Agent 时，持久的 Agent allow 规则才会共享；界面在父对话代理审批时使用“允许该 Subagent 会话”避免歧义。

### 11.3 MCP 与 Skill

- MCP 和 Skill 是必须保留的扩展方向。
- MCP Tools、Resources、Prompts 进入统一 Tool/Context 合同。
- MCP/Skill 继承 Agent 当前项目、权限、超时、取消和审计约束。
- Skill 是说明和能力组合，不直接执行任意 Node/Shell。
- Skill Runtime 已接入 AgentRuntime/LangGraph：模型先看到目录摘要，再通过 `load_skill` 激活 `SKILL.md`；正文只作为本轮模型上下文，不写入聊天 Timeline。`SKILL.md` 的 Frontmatter `name` 必须与父目录名完全一致；首次登记以该名称生成稳定内部 `skillId`，全局重名时追加数字后缀，后续同步文档元数据不改变既有 ID。ContextManager 在历史裁剪前为正文固定预留预算，实际注入与用量估算保持一致。Agent 的 `custom skillIds` 同时限制发现、加载、reference 和恢复注入，项目/团队作用域分别要求项目工作区/团队会话。`read_skill_reference` 只允许已激活 Skill 的 `references/` 和 `templates/` 有界、严格 UTF-8 文本。MCP Runtime 仍未实现，因此带 MCP 依赖的 Skill 不会进入目录；Capability 只反映当前可用的 Skill 文档能力。

## 12. 上下文与压缩

### 12.1 两种历史

```text
UI 历史：完整保留在本地，供用户查看
模型上下文：每次按预算选择，只发送完成当前任务所需内容
```

不因模型上下文压缩删除、覆盖或隐藏原始消息、命令和工具结果。

### 12.2 每次发送给模型的内容

按优先级和 Token 预算组织：

1. 系统指令、当前 Agent 身份、权限和工作区。
2. 当前用户请求、附件和未处理的 Steer/Agent 消息。
3. 当前任务目标、任务清单、未完成事项和用户明确约束。
4. 最新 Context Checkpoint。
5. Checkpoint 后尚未覆盖的消息和最近约 2 轮完整对话；最终数量仍由 Token 预算决定。
6. 与当前任务相关的文件片段、工具结果、Agent/Subagent 摘要和 Artifact 引用。
7. 当前可用 Tool Schema 和输出预留。

不默认把所有历史、全部项目文件或另一个 Agent 的完整对话发给模型。
已经被 Context Checkpoint 覆盖的旧消息不会回到普通历史序列；命中当前请求关键词时，才以有上限的动态相关历史引用注入本次请求。

运行时维护的固定系统控制文本、上下文边界标记和内置 Tool Schema 使用简洁英文，避免同一提示层混用语言并降低本地估算占用。长而稳定的基础系统 Prompt 与压缩 Prompt 以独立 Markdown 资产维护并在构建时内嵌；TypeScript 只组合身份、权限、工作区和预算等动态事实。Tool 描述及参数 Schema 继续与工具合同共置，避免说明与真实参数漂移。输出语言由独立的英文系统规则决定：当前应用语言固定为 `zh-CN`，因此模型默认使用简体中文回答；只有用户明确要求其他语言时才覆盖该默认值。用户输入、Agent/Skill 自定义正文和历史事实保持原文，不做自动翻译。

上下文用量界面按“系统上下文、当前有效会话、预留容量”展示本地 Token 估算。系统上下文包含基础系统提示词、实际发送的 Tool Schema、Skill 目录和活动任务清单；当前有效会话包含对话文本/压缩摘要、工具调用与结果、附件和相关引用；模型回复与尚未加载的 Skill 正文预算属于预留容量，不算作已使用输入。明细使用静态缩进表达层级，不改变模型请求结构。

### 12.3 压缩顺序

达到模型/用户配置阈值时：

1. 先截断或 Artifact 化旧的长工具输出。
2. 对较早、尚未覆盖的完整轮次生成增量结构化摘要。
3. 最近约 2 轮尽量原样保留。
4. 当前请求、未完成审批、用户约束、路径、命令、测试结果和错误标识不能被模糊摘要替代。
5. 摘要保存覆盖的消息序号；下次只压缩新增旧前缀。
6. 摘要写入失败时保留原始消息，不移动 Checkpoint。

结构化摘要至少保留：目标、决定、约束、改动文件、命令/结果、错误、未完成事项、附件引用和相关 Agent 来源。

### 12.4 Agent 引用预算

读取其他对话或 Subagent 时：

- 优先使用完成摘要和最新 Checkpoint。
- 再按需读取未覆盖的新消息或指定范围。
- 返回内容有字符/Token 上限和是否截断标记。
- 来源 Conversation ID 保留在上下文中，便于后续继续读取或回复。

当前不要求向量数据库。对话历史以结构化 Checkpoint、最近原文、按需工具读取和显式引用管理；只有未来出现跨大量项目的语义检索需求并完成效果评测后，才考虑本地 Embedding/向量索引。
